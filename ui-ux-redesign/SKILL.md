# 界面优化设计（UI / UX 优化与重构）

## 摆放位置（工作区特定的值从配置读）

本技能只写流程与规则，**值读 `<工作区根>/Docs/工作区配置.json` 与同目录 `工作区配置.md`**（装了 `工作区配置` 技能就按它走；没装就按下面的默认值）：

| 要什么 | 读哪 |
| --- | --- |
| 工作区设计规范 / 规范源 | `工作区配置.md › 规范源` |
| 原型落盘目录 | json `paths.uiPrototype`；**没有就默认 `Docs/设计稿/{需求id或yyyyMMdd}-{标题}/`**，并在汇报里写一句「用了默认路径」 |
| 需求拆解（有就作为设计输入） | json `paths.requirementBreakdown` |

**缺项：可以建议，不擅自写配置**（"我建议原型落在 X，要我写进配置吗？"）。

---

## 第一步：先找设计规范（硬顺序，不许跳）

1. **配置 `规范源`** 里指向的设计规范文件（工作区自己的规矩优先）。
2. **项目内规范**：`DESIGN.md` / `DESIGN_GUIDE.md` / `docs/design*` / `Docs/设计规范*`。
3. **现有实现即事实规范**：CSS 变量 / token（颜色、间距、字号、圆角、阴影）、组件库（Element / Ant / 自研）、全局样式与既有页面写法。
4. **都没有 → 问用户一句**：「有没有设计规范或 token 文件？没有的话我按现有界面风格 + 通用可用性原则做」。

- **规范压过我的审美**：规范与个人判断冲突 → 按规范，并在方案里注明「依据：规范 §x」。
- **规范没覆盖的地方** → 用通用原则补，并明确标「规范未覆盖，按通用原则」。
- **绝不自己编一套规范**（不虚构色板、间距体系、品牌色）。

## 第二步：现状诊断（先证据，后观点）

素材从哪来：用户截图 / 线上 URL / 现有代码 / `类人测试` 采集（装了就用它跑一遍拿 DOM 与控制台证据）。**没有素材就请用户给截图或地址，不凭想象诊断。**

按 **7 个维度**列问题，每条写「位置 + 现象 + 影响 + 依据」：

| 维度 | 看什么 |
| --- | --- |
| **信息架构** | 层级与分组、主次关系、命名是否一眼懂、是否堆在一屏 |
| **布局** | 对齐、间距节奏、留白、栅格、内容密度、横向滚动 |
| **视觉** | 颜色语义、字号字重层级、对比度、圆角/阴影一致性、图标风格 |
| **交互** | 可发现性（按钮认不认得）、点击区域、hover / active / focus、危险操作防误触 |
| **反馈** | loading / 空态 / 错误 / 成功 / 禁用 / 超时，是否每个状态都有交代 |
| **状态与边界** | 长文本、空数据、超量数据、窄屏、超长标题、多语言长度 |
| **可访问性** | 对比度 ≥ 4.5:1（正文）、键盘可达、焦点可见、语义标签、不靠颜色单一传达 |

## 第三步：方案（改什么 / 为什么 / 多大代价）

一张表定稿，别写散文：

```
| # | 改动点 | 现状 | 改为 | 依据 | 优先级 |
|---|--------|------|------|------|--------|
| 1 | 主按钮位置 | 右下角浮动、与返回键打架 | 表单底部固定操作栏 | 规范 §操作区 / Fitts | P0 |
```

- 优先级只三档：**P0 必改**（影响完成任务）/ **P1 建议**（影响效率与理解）/ **P2 可选**（打磨）。
- **不动需求边界**：需求拆解写了「不做什么」的，设计也不越界。

## 第四步：交付可视化原型（强制，禁止只给文字）

**交付物 = 一个能打开的单文件 HTML 原型 + 关键屏截图**。只有文字描述 / 伪代码 / 截图标注，视为**没交付**。

### 原型硬要求

| 项 | 要求 |
| --- | --- |
| 形态 | **单个 `index.html`**，CSS / JS 内联，**离线双击可开**，不依赖 CDN、外部字体、外链图片 |
| 三视图 | ① **现状（Before）** 按现有实现还原；② **方案（After）** 改版效果；③ **交互演示（Flow）** 关键操作可点击（至少覆盖 loading / 空态 / 错误态之一） |
| 顶部说明条 | 需求一句话 + 依据规范 + P0 改动点摘要 |
| 响应式 | 桌面（≥1280）与窄屏（≤430）各给一版，可切换或并排 |
| token | 用 CSS 变量集中定义颜色 / 间距 / 字号 / 圆角，**与项目 token 对齐**（找不到就按现有界面取值） |
| 图标 | 内联 SVG，字体用系统字体栈 |
| 附带 | 页内附「改动点对照表」（与第三步表格一致） |

### 交付方式（必须让人看见）

1. 落盘到原型目录（默认 `Docs/设计稿/{需求}-{标题}/index.html`）；
2. **用浏览器打开并截图关键屏**（`TRAE-browseruse` / `类人测试` 装了就用；没有浏览器能力就说明并给可点击路径）；
3. 汇报里给 `computer://` 可点链接 + 截图 + 3~5 条「最值得先看的改动」；
4. 用户要真机效果 → 再给「直接在仓库里改」的落地建议（不默认动手）。

## 第五步：落地（用户明确要求才做）

- 用户说「就按这个改」→ 走 `界面设计规范`（改 UI 文件前必读）改真实代码，改完用 `类人测试` 自测验收。
- 本技能**默认只产设计与原型，不改业务代码**。

## 与其他技能的关系（条件引用）

| 技能 | 关系 |
| --- | --- |
| `界面设计规范` | **分工**：本技能做设计与原型；它约束真实代码的落地（对齐、场景基调、禁止项） |
| `类人测试` | 装了就用来采现状证据（截图 / DOM / console）与验收改版效果 |
| `需求拆解`（公司库） | 有拆解就拿它的边界与验收标准当设计输入；没装不影响 |
| `工作区配置` | 设计规范位置、原型落点从配置读 |
| `改动记录` / `知识沉淀` | 设计决策要留痕时挂载 |

## 红线

1. **不编规范**：没有设计规范就问，不虚构品牌色 / 间距体系。
2. **不只给文字**：没有可打开的原型 = 没交付。
3. **不擅自改业务代码**（用户说「直接改」才动，且先读 `界面设计规范`）。
4. **不动需求边界**：设计不扩需求、不改业务规则。
5. **原型必须自包含**：外链资源在离线环境会挂，一律内联。

## 触发示例

- 「这个订单列表页太难用了，帮我优化一下」+ 截图 → 诊断 → 方案 → **before/after 原型** + 截图
- 「把设置页重新设计一版，要能看效果」→ 先找规范 → 原型三视图 → 给可点击链接与关键屏截图
- 「登录流程交互优化，给我个 demo」→ Flow 视图（含 loading / 错误态）→ 截图
- 「这个页面 UI 太老了，视觉升级」→ 视觉层改造方案 + 原型对照（不动信息架构则写明「不动」）
