# 界面优化设计（UI / UX 优化与重构）

## 摆放位置（工作区特定的值从配置读）

本技能只写流程与规则，**值读 `<工作区根>/Docs/工作区配置.json` 与同目录 `工作区配置.md`**（装了 `工作区配置` 技能就按它走；没装就按下面的默认值）：

| 要什么 | 读哪 |
| --- | --- |
| 工作区设计规范 / 规范源 | `工作区配置.md › 规范源` |
| 原型落盘目录 | json `paths.uiPrototype`；**没有就默认 `Docs/设计稿/{需求id或yyyyMMdd}-{标题}/`**，并在汇报里写一句「用了默认路径」 |
| 需求拆解（有就作为设计输入） | json `paths.requirementBreakdown` |

**缺项：可以建议，不擅自写配置**（"我建议原型落在 X，要我写进配置吗？"）。

## 零、只说「优化一下」时先判指向（2026-10-30 用户口径）

用户常不点名 UI/UX，只说「把这块优化一下」「这个模块优化一下」「这部分重新弄一下 / 好看点 / 好用点」——**先判「这块」指的是什么**：

| 指向 | 走哪 |
| --- | --- |
| **界面呈现 / 布局 / 视觉 / 交互 / 展示模块**（含截图里圈出的一块） | **本技能**：诊断 → 方案 → 原型 |
| 代码质量 / 性能 / 结构（"这段逻辑优化一下"） | `改动建议`（只分析）→ 确认后走 `开发中规范` |
| 纯文案措辞 / 数字口径 | 直接改文案（极轻档），不动结构、不出原型 |
| **判不出** | **问一句**：「你要的是界面重做，还是代码 / 文案层面的优化？」 |

- **有截图或圈选区域 → 默认按界面**（素材即意图），直接进诊断，不再反问「要不要做 UI」。
- **指向界面但范围不清**（整页还是局部、含不含相邻模块）→ 问一句范围就开工，不猜。
- 判成界面后，**流程与产出要求不变**（规范 → 诊断 → 方案 → 可视化原型 + 截图）。

## 第一步：先找设计规范（硬顺序，不许跳）

1. **配置 `规范源`** 里指向的设计规范文件（工作区自己的规矩优先）。
2. **项目内规范**：`DESIGN.md` / `DESIGN_GUIDE.md` / `docs/design*` / `Docs/设计规范*`。
3. **现有实现即事实规范**：CSS 变量 / token（颜色、间距、字号、圆角、阴影）、组件库（Element / Ant / 自研）、全局样式与既有页面写法。
4. **都没有 → 问用户一句**：「有没有设计规范或 token 文件？没有的话我按现有界面风格 + 通用可用性原则做」。

- **规范压过我的审美**：规范与个人判断冲突 → 按规范，并在方案里注明「依据：规范 §x」。
- **规范没覆盖的地方** → 用通用原则补，并明确标「规范未覆盖，按通用原则」。
- **绝不自己编一套规范**（不虚构色板、间距体系、品牌色）。

## 第二步：现状诊断（先证据，后观点）

素材从哪来：用户截图 / 线上 URL / 现有代码 / `类人测试` 采集（装了就用它跑一遍拿 DOM 与控制台证据）。**没有素材就请用户给截图或地址，不凭想象诊断。**

按 **7 个维度**列问题，每条写「位置 + 现象 + 影响 + 依据」：

| 维度 | 看什么 |
| --- | --- |
| **信息架构** | 层级与分组、主次关系、命名是否一眼懂、是否堆在一屏 |
| **布局** | 对齐、间距节奏、留白、栅格、内容密度、横向滚动 |
| **视觉** | 颜色语义、字号字重层级、对比度、圆角/阴影一致性、图标风格 |
| **交互** | 可发现性（按钮认不认得）、点击区域、hover / active / focus、危险操作防误触 |
| **反馈** | loading / 空态 / 错误 / 成功 / 禁用 / 超时，是否每个状态都有交代 |
| **状态与边界** | 长文本、空数据、超量数据、窄屏、超长标题、多语言长度 |
| **可访问性** | 对比度 ≥ 4.5:1（正文）、键盘可达、焦点可见、语义标签、不靠颜色单一传达 |

## 第三步：方案（改什么 / 为什么 / 多大代价）

一张表定稿，别写散文：

```
| # | 改动点 | 现状 | 改为 | 依据 | 优先级 |
|---|--------|------|------|------|--------|
| 1 | 主按钮位置 | 右下角浮动、与返回键打架 | 表单底部固定操作栏 | 规范 §操作区 / Fitts | P0 |
```

- 优先级只三档：**P0 必改**（影响完成任务）/ **P1 建议**（影响效率与理解）/ **P2 可选**（打磨）。
- **不动需求边界**：需求拆解写了「不做什么」的，设计也不越界。

## 第四步：选形态 + 选载体（2026-10-30 用户口径）

### 4.1 先看手头工具能力，定精度上限

| 能力 | 能做什么 |
| --- | --- |
| 只能写文件 | 单文件 HTML 原型（离线可开）+ 说明 |
| 能开浏览器（`TRAE-browseruse` / `类人测试`） | **必须**补「关键屏截图」 |
| 能生成图片（`GenerateImage`） | 可补视觉参考图，**不替代可交互原型** |

### 4.2 再选形态（拿不准一律选高精度，不许为省事降级）

| 判据（满足任一） | 形态 |
| --- | --- |
| **≥2 个页面 / ≥3 个关键状态 / 有流程跳转 / 信息架构或布局重构 / 新增交互（弹窗·抽屉·上传·分步）** | **高精度原型** |
| 单页单区块、只调样式 / 文案 / 间距 / 颜色，或单组件微调、**≤3 个改动点** | **优化清单可视化** |

**高精度原型**必须：覆盖主流程每一屏、关键状态（默认 / 加载 / 空 / 错误 / 禁用 / 成功至少 3 个）、真可交互（弹窗开合、tab 切换、表单输入、危险操作二次确认）、UX 细节（点击区、焦点态、hover/active、防重复提交、错误位置）、数据增删改后结果可见。

**优化清单可视化**：一屏内 before / after（并排或切换），改动点带编号对应第三步清单；不做多屏与状态机。

### 4.3 再选载体（优先①）

| 载体 | 什么时候用 |
| --- | --- |
| **① 项目内原型分支（默认）** | 项目能本地跑 + 有组件库 / token + 需求就在该仓落地——**能复用真组件、真样式、真规范校验**，落地零偏差 |
| ② 单文件 HTML | 项目跑不起来 / 只做视觉探索 / 跨仓或对外展示 / 需要独立分发 |

#### ① 项目内原型分支（纯本地 · 不推远程）

**分支规则**：

```
{仓前缀}{id段}-Proto        # 例：UF0947-Proto
· 只在本地：不 push、不设 upstream、不开 PR、不合入任何分支
· 需求分支照常先建（`create-requirement-branch`）；原型分支在它之后按需建
```

建法（在目标业务仓根执行；`创建分支` 的一条龙脚本目前只支持需求 / 合并分支，**原型分支手工建、不硬改脚本**）：

```bash
git fetch origin <主分支>
git worktree add "<原仓父目录>/<仓前缀><id段>-Proto" -b "<仓前缀><id段>-Proto" "origin/<主分支>" --no-track
cd "<原仓父目录>/<仓前缀><id段>-Proto"
pnpm install
dev <id后4位>          # 起服务；撞端口/定位到错误 worktree → 停下上报，不自行改端口
```

- **绝不 `git push -u`**：它没有远程对应分支（这点与需求分支相反）。
- **核心原则：原型 = 新建一个可丢弃的页面，不是改原页面**（2026-10-30 用户口径）。原型是轻量探索；直接改原文件那叫实现，不叫原型。

| 规则 | 做法 |
| --- | --- |
| **新建、不改原文件** | 原型页放独立位置（跟项目惯例，如 `src/views/<模块>/__prototype__/<页面>-proto.vue` 或 `prototype/`；拿不准就问用户）；**原页面文件零改动** |
| **可以复用** | 复制原页面为**新文件**后再改；或 import 现有组件 / 样式模块 / token / 工具函数（**读用不改**） |
| **能访问** | 加临时路由 / 独立入口（开发环境限定），**不进正式路由表**；必须进时标 `// PROTOTYPE` 并在交付里说明 |
| **不碰** | 接口契约、业务逻辑、测试目录、**公共组件源码**（要改公共组件 → 先说明，通常说明设计不可行） |
| **mock 数据** | 独立文件 + `// PROTOTYPE` 标记，不写进原页面 |
| **自检** | 收尾 `git diff --stat`：**原页面文件不得出现在 diff 里**；出现即回退，改成新建文件 |

- **本地提交可选**：为对比 / 回退可本地 commit（message 加 `proto:` 前缀），**但绝不 push**。
- **起服务先错峰**：原型分支与需求分支 id 后 4 位相同，pm2 名 / 端口会撞 → 先停需求分支服务，再起原型服务。
- **用完即删**（不进入合入 / 清理流程）：

```bash
git worktree remove "<原仓父目录>/<仓前缀><id段>-Proto"
git branch -D "<仓前缀><id段>-Proto"
```

- **原型代码要留 → 用户决定**：由人确认后复制进需求分支，**不自动合并、不自动 cherry-pick**。

#### ② 单文件 HTML（硬要求）

| 项 | 要求 |
| --- | --- |
| 形态 | **单个 `index.html`**，CSS / JS 内联，**离线双击可开**，不依赖 CDN、外部字体、外链图片 |
| 视图 | 高精度：现状 / 方案 / 交互演示（按屏切换）；清单：改动前 / 改动后 |
| 顶部说明条 | 需求一句话 + 依据规范 + P0 改动点摘要 |
| 响应式 | 桌面（≥1280）与窄屏（≤430）各给一版，可切换或并排 |
| token | CSS 变量集中定义颜色 / 间距 / 字号 / 圆角，**与项目 token 对齐**（找不到按现有界面取值） |
| 图标 | 内联 SVG，字体用系统字体栈 |
| 附带 | 页内附「改动点对照表」（与第三步表格一致） |

### 4.4 交付方式（必须让人看见）

1. **汇报里写明选了什么**：形态（高精度 / 清单）+ 载体（项目内原型 / 单文件 HTML）+ 依据哪几条判据；
2. 载体①：给 `dev` 服务地址 + **关键屏截图**；载体②：落盘 `Docs/设计稿/{需求}-{标题}/index.html` + 可点击路径；
3. 统一再给：`computer://` 链接 + 截图 + 3~5 条「最值得先看的改动」；
4. 用户要正式落地 → 走「第五步」；原型分支的代码不自动搬进需求分支。

## 第五步：落地（用户明确要求才做）

- 用户说「就按这个改」→ 走 `界面设计规范`（改 UI 文件前必读）改真实代码，改完用 `类人测试` 自测验收。
- 本技能**默认只产设计与原型，不改业务代码**。

## 与其他技能的关系（条件引用）

| 技能 | 关系 |
| --- | --- |
| `界面设计规范` | **分工**：本技能做设计与原型；它约束真实代码的落地（对齐、场景基调、禁止项） |
| `类人测试` | 装了就用来采现状证据（截图 / DOM / console）与验收改版效果 |
| `需求拆解`（公司库） | 有拆解就拿它的边界与验收标准当设计输入；没装不影响 |
| `工作区配置` | 设计规范位置、原型落点从配置读 |
| `改动记录` / `知识沉淀` | 设计决策要留痕时挂载 |

## 红线

1. **不编规范**：没有设计规范就问，不虚构品牌色 / 间距体系。
2. **不只给文字**：没有可打开的原型 = 没交付。
3. **不许为省事降级形态**：判据够高精度原型（≥2 页 / ≥3 状态 / 有流程 / 布局重构 / 新增交互）就不许退成优化清单；拿不准按高精度。
4. **不擅自改业务代码**（用户说「直接改」才动，且先读 `界面设计规范`）。
5. **不动需求边界**：设计不扩需求、不改业务规则。
6. **原型必须自包含**：单文件 HTML 载体下，外链资源在离线环境会挂，一律内联。
7. **原型分支不落地到远端**：`{仓前缀}{id段}-Proto` 只在本地——**不 push、不设 upstream、不开 PR、不合入任何分支**；原型代码搬进需求分支必须由人确认，不自动 merge / cherry-pick。
8. **原型不改原文件**：一律**新建页面 / 新文件**，原页面、公共组件、接口**零改动**（用 `git diff --stat` 自检）。直接改原文件 = 实现，不再是原型。

## 触发示例

- 「这个订单列表页太难用了，帮我优化一下」+ 截图 → 诊断 → 方案 → **before/after 原型** + 截图
- 「把设置页重新设计一版，要能看效果」→ 先找规范 → 原型三视图 → 给可点击链接与关键屏截图
- 「登录流程交互优化，给我个 demo」→ Flow 视图（含 loading / 错误态）→ 截图
- 「这个页面 UI 太老了，视觉升级」→ 视觉层改造方案 + 原型对照（不动信息架构则写明「不动」）
- 「把这块优化一下」+ 圈出某个卡片 / 列表区域 → 判为界面 → 诊断 + 方案 + 原型
- 「这个模块看着有点乱」→ 同上（界面）；「这段代码优化一下」→ 转 `改动建议`，不做原型
