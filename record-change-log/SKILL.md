# Record Change Log

## 触发时机

当用户在一次开发、排查或修改之后，说出以下或相近表达时，使用本 skill：

- “将上述改动过程编成日志”
- “把上述改动过程编成日志”
- “把刚才的改动写成日志”
- “将这次修改整理成日志”
- “生成一条修改日志”

## 核心目标

将此前相关的上下文、问题、原因和解决方式整理成一份简短日志文稿，保存到当前项目根目录的 `Logs/` 文件夹下。

## 保存位置

- 固定保存到当前项目根目录下的 `Logs/` 文件夹。
- 如果 `Logs/` 不存在，需要先创建。
- 文件名使用日期和简短 slug：

```text
Logs/YYYY-MM-DD-short-topic.md
```

示例：

```text
Logs/2026-05-30-save-api-fix.md
Logs/2026-05-30-env-config-update.md
```

如果同名文件已存在，在文件名后追加 `-2`、`-3` 等序号。

## 内容要求

1. **尽量简单简短**
   - 正文尽量控制在 100 个中文字符以内。
   - 不写成长篇复盘，不展开大段背景。

2. **主题结构固定**
   - 必须包含：
     - 什么问题
     - 什么原因
     - 怎么解决
   - 可选包含：
     - 问题发散/举一反三

3. **基于已有上下文**
   - 优先使用当前对话、最近改动、已查看文件、报错信息和执行结果。
   - 如果上下文不足，先简短询问用户，不要凭空编造。

4. **不改动业务代码**
   - 触发本 skill 时，只允许创建或编辑 `Logs/` 下的 Markdown 日志。
   - 除非用户另有明确要求，不要修改源代码或其他文档。

5. **避免敏感信息**
   - 不写入明文密钥、token、密码、私有凭据等敏感信息。
   - 如需提及配置值，使用 `<redacted>` 或“已脱敏”。

## 建议文档格式

```markdown
# {简短标题}

> 记录时间: YYYY-MM-DD HH:mm

## 日志

什么问题：{一句话说明问题}
什么原因：{一句话说明原因}
怎么解决：{一句话说明解决办法}
问题发散/举一反三：{可选，一句话}
```

如果为了控制在 100 字以内，也可以写成单段：

```markdown
# {简短标题}

什么问题：...；什么原因：...；怎么解决：...；举一反三：...
```

## 操作流程

1. 判断用户是否是在要求把此前改动过程编成日志。
2. 收集此前相关上下文，包括用户需求、修改过的文件、关键问题、原因和处理方式。
3. 如果信息不足，向用户提出一个简短确认问题。
4. 在项目根目录创建 `Logs/` 文件夹（如不存在）。
5. 创建一篇新的 Markdown 文件，内容简短自然，优先控制在 100 字以内。
6. 完成后告诉用户日志文件路径，并简要说明已记录。

## 质量检查

写入前后检查：

- 是否保存在项目根目录 `Logs/` 下。
- 是否包含“什么问题 / 什么原因 / 怎么解决”。
- 是否尽量控制在 100 字以内。
- 是否没有泄露敏感信息。
- 是否没有修改 `Logs/` 以外的代码或文档，除非用户另有明确要求。
