# Record Change Log（改动/问题沉淀）

一个技能、两种模式——**短记**（日志）与**长记**（开发博客）。**先判断模式，再落笔。**

> 本技能前身是两个独立技能（`record-change-log` + `record-development-blog`），已合并。`record-development-blog` 仍作为兼容壳存在，指向本技能。

## 触发时机

在一次开发、排查、修改之后，或遇到相对复杂的问题/需求时，用户说：

- 短记类：「将上述改动过程编成日志」「把刚才的改动写成日志」「将这次修改整理成日志」「生成一条修改日志」
- 长记类：「记录这个问题」「记录这个需求」「把这个问题/需求记录下来」「将这个问题/需求编成博客」「将这个问题编成 blog」「整理成博客」「写成博客」

## 选哪种模式

| 判据 | 短记（Logs/） | 长记（Blogs/） |
|---|---|---|
| 用户用词 | 日志、修改记录、"编成日志" | 记录、博客、blog、"记录这个问题/需求" |
| 内容体量 | 一次改动，几句话说得清 | 相对复杂的问题/需求，有排查过程与取舍 |
| 视角 | 客观三句：什么问题 / 什么原因 / 怎么解决 | **第一人称**：背景、现象、上下文、我的分析、结论、后续 |
| 落点 | `<项目根>/Logs/YYYY-MM-DD-short-topic.md` | `<项目根>/Blogs/YYYY-MM-DD-short-topic.md` |
| 长度 | **尽量 ≤100 中文字符** | 自然长度，完整可回顾 |

**判不准就问一句**：「要短记（`Logs/`，三句话）还是一篇完整记录（`Blogs/`，第一人称）？」——别默认长篇，也别把复杂排查压成三句。

## 两种模式的格式

### 短记（Logs/）

```markdown
# {简短标题}

> 记录时间: YYYY-MM-DD HH:mm

## 日志

什么问题：{一句话}
什么原因：{一句话}
怎么解决：{一句话}
问题发散/举一反三：{可选，一句话}
```

为压在 100 字内，也可写成单段：`什么问题：…；什么原因：…；怎么解决：…；举一反三：…`

### 长记（Blogs/）

```markdown
# {问题或需求标题}

> 记录时间: YYYY-MM-DD HH:mm
> 项目: {项目名或路径}

## 背景
我是在什么场景下遇到这个问题/需求的，为什么需要记录它。

## 当时的现象或目标
问题：我看到了什么异常、报错或不符合预期的行为。
需求：我想达到什么目标，用户体验或业务上希望变成什么样。

## 相关上下文
- 相关文件：`path/to/file`
- 相关函数/接口：`functionName`
- 相关配置：`ENV_NAME`（敏感值需脱敏）
- 相关命令或日志：必要时摘录

## 我的分析过程
我如何理解这个问题/需求，排查了哪些方向，哪些判断被证明有效或无效。

## 当前结论
目前的结论、决定采用的方案，或已完成的处理结果。

## 后续计划
- [ ] 还需要确认的点
- [ ] 还需要实现或验证的内容
```

## 通用要求（两种模式都适用）

1. **不改动业务代码**——只创建/编辑 `Logs/` 或 `Blogs/` 下的 Markdown；除非用户同时明确要求开发或修复。
2. **基于已有上下文**——优先用当前对话、最近改动、查看过的文件、报错与执行结果；信息不足先问一句，**不要凭空编造**。
3. **避免敏感信息**——不写明文密钥、token、密码、私有凭据；必要时用 `<redacted>` 或"已脱敏"。长记可以写文件路径、函数名、接口名和报错信息。
4. **语言自然**——长记像开发日志/技术博客草稿，保留真实的不确定、尝试与判断；短记不写成长篇复盘。
5. **文件命名**——`YYYY-MM-DD-short-topic.md`，slug 用英文小写 + 数字 + 连字符，反映主题、别过长；同名已存在则追加 `-2`、`-3`。
6. **目录不存在就先创建**（`Logs/` 或 `Blogs/`），都在**当前项目根目录**下。

## 操作流程

1. 判断用户是要沉淀记录，并**选定模式**（短记 / 长记；判不准就问一句）。
2. 收集此前上下文：用户需求、改过的文件、关键问题、原因、处理方式（长记还要收集现象、排查过程、取舍）。
3. 信息不足 → 一个简短确认问题；已经足够 → 直接落笔。
4. 在项目根创建对应目录（如不存在）。
5. 写 Markdown 文件（短记按三句结构并压到 100 字内；长记用第一人称、结构自然）。
6. 完成后告诉用户文件路径，并简述记录了哪些内容。

## 质量检查

- 模式选对了吗（短记没写成复盘长文；长记没用模板腔）？
- 落点对吗（短记 `Logs/`、长记 `Blogs/`，都在项目根）？
- 短记是否包含"什么问题 / 什么原因 / 怎么解决"，并尽量 ≤100 字？
- 长记是否第一人称、语言自然、未来回看能理解当时发生了什么？
- 有没有泄露敏感信息？
- 有没有动 `Logs/`（或 `Blogs/`）以外的代码或文档？
