# 方案讨论与记录

当用户表达"先讨论再动手"的意图时，进入 **方案讨论模式**，系统性地记录多轮对话并产出结构化文档。

## 核心规则

⚠️ **方案讨论模式 ≠ Claude Code 内置的 `EnterPlanMode`**

| | 方案讨论模式（本 skill） | Claude Code 内置 Plan Mode |
|---|---|---|
| 编辑文件 | ✅ 可读写 | ❌ 限制 Write/Edit |
| 编辑范围 | **仅限 `Plans/` 目录** | 无法编辑任何文件 |
| 编辑实际代码 | ❌ **禁止** | ❌ 禁止 |
| 目的 | 记录讨论、生成方案文档 | 设计实现方案 |

**本模式下：**
- ✅ 可以创建/编辑 `Plans/` 目录下的 `.md` 文件
- ❌ **绝对不能** 编辑任何源代码文件（`src/`、`*.rs`、`*.ts`、`*.html` 等）
- ❌ **绝对不能** 调用 `EnterPlanMode`（它会禁掉 Write/Edit，导致无法落盘）

## 方案落盘位置（强制）

⚠️ **所有方案文档必须写入项目根目录的 `Plans/` 文件夹下。**

- 路径规则：`<项目根目录>/Plans/<主题文件夹>/` → 各轮次 `.md` 文件 + 固定清单文件（见 §命名与语言规范）+ `附件/`（图片、截图、附件等讨论素材）
- 如果用户在聊天中上传了图片、截图或其他附件，且当前会话可获得其原始文件/可读路径，则必须一并保存到该主题文件夹下的 `附件/` 中
- 不得在 `Plans/` 以外的任何位置创建方案文档或讨论素材（如 `docs/`、`设计/`、桌面等）
- 这是一个**硬性约束**，无例外

## 命名与语言规范

**原则：** 主题名、各轮讨论文件名、附件文件名、独立笔记等 **默认使用中文**；仅在必要时使用英文或拉丁字符。

| 保留英文/固定名的情况 | 说明 |
|:---|:---|
| 日期前缀 | `YYYY-MM-DD` |
| 轮次序号 | `01`、`02`… |
| 三技能共用清单文件 | `execution-plan.md`、`COMPLETED.md`、`UNEXECUTED.md`（闭环检索约定，新建主题一律用此三名） |
| 子目录 | `附件/`、`Plans/归档/`、`Plans/未完成池/` |
| 文件扩展名 | `.md`、`.png` 等 |
| 技术专有名词 | 库名、协议名、用户指定的英文产品名等，按原文 |

**主题文件夹（`Plans/` 根下）：** `{YYYY-MM-DD}-{中文主题简称}`

- 简称用 **2～15 个汉字**（或常见中英混排专名），简明概括主题
- **不要**再用「英文 slug」作为默认命名方式
- 示例：`2026-05-26-剪贴板同步架构`、`2026-05-30-大文件传输模块`

**各轮讨论文件：** `{两位序号}-{中文问题摘要}.md`

- 摘要 4～20 字，概括本轮核心问题
- 示例：`01-跨平台框架选型.md`、`02-内存与性能取舍.md`

**附件（无法沿用用户原始文件名时）：** `{轮次序号}-图-{两位序号}.{ext}`

- 示例：`03-图-01.png`、`03-图-02.jpg`

**独立讨论单文件（尚未建主题夹时）：** `{YYYY-MM-DD}-{中文说明}.md`

**Plans 下固定子目录（一律中文）：**

| 路径 | 用途 |
|:---|:---|
| `Plans/归档/` | 已锁定主题 |
| `Plans/未完成池/` | 跨主题未完成事项精简摘要（非主题文件夹） |
| `{主题}/附件/` | 该主题讨论中的图片、截图等素材 |

**遗留路径（只读兼容，新建不得使用）：** `Plans/_backlog/`、`{主题}/assets/`。扫描进行中主题时，`Plans/未完成池/` 与 `Plans/_backlog/` 均排除；落盘附件一律用 `附件/`。

**未完成池摘要文件：** 与主题文件夹 **同名** 的 `.md`（含日期与中文简称），例如 `Plans/未完成池/2026-06-09-剪贴板同步.md`

**遗留：** 旧主题若仍为英文文件夹名、英文讨论文件名，或仍使用 `附件/`、`Plans/未完成池/`，不强制批量重命名；**新建与重写**一律遵循本规范。

## 工作流程

```
1. 创建主题文件夹 → 2. 多轮讨论记录 → 3. 生成待执行方案 → 4. 主题延续/新开判断 → 5. 归档锁定约定（由 plan-lock 执行）
```

## 第一步：创建主题文件夹

在项目根目录的 `Plans/` 下创建本次讨论的主题文件夹。

**进行中主题命名规则：** `{YYYY-MM-DD}-{中文主题简称}`（位于 `Plans/` 根目录，见 §命名与语言规范）

- 日期为讨论开始日期
- 简称用中文概括主题，必要时可含用户指定的英文专名
- 示例: `2026-05-26-剪贴板同步架构`、`2026-05-30-P2P传输模块`

**已锁定（已归档）主题：**

- 由 `plan-lock` 移入 `Plans/归档/{YYYY-MM-DD}-{中文主题简称}/`
- **保持原名**，不使用 `[LOCKED]` 前缀，**不创建** `STATUS.md`
- 位于 `Plans/归档/` 下即表示已锁定、只读

如果 `Plans/` 目录尚不存在，先创建该目录。

## 第二步：多轮讨论记录

### 2.1 开始讨论记录

向用户说明：
- 本次讨论主题将以文档形式记录到 `Plans/` 目录
- 每轮讨论内容都会落盘
- 最终会生成待执行方案
- ⚠️ 本模式仅编辑 Plans 文档，不会改动任何源代码

### 2.2 记录每一轮讨论

每轮讨论保存为一个独立的 `.md` 文件。文件命名：

```
{步骤序号}-{问题简短摘要}.md
```

**步骤序号** 使用两位数字（`01`、`02`、`03`...），确保按讨论顺序排列；摘要部分使用 **中文**（见 §命名与语言规范）。

### 2.3 文件内容格式

每个讨论文件 **必须** 遵循以下结构：

```markdown
# 第 N 轮：{用户问题的一句话概括}

> 时间: YYYY-MM-DD HH:MM

## 用户提问

{经识别与提取后的真实用户提问——保留实质性原话，剔除指令性语句；详见 §2.3.2}

## 背景与分析

{AI 对该问题的分析思考过程，包括搜索/调研结果}

## 建议与回答

{AI 给出的具体建议、方案、回答。保留完整内容，包括表格、列表、代码块等}

## 相关图片（如有）

- 图 1：{图片用途说明}
  ![图 1：{图片用途说明}](./附件/{轮次序号}-图-01.{ext})

## 本轮要点

- 关键决策 1
- 关键决策 2
- ...
```

**重要原则：**
- **用户提问须识别真实意图后再落盘**（见 §2.3.2）：保留实质性问题的原话措辞，剔除落盘/归档等指令性语句；纯落盘指令则向上追溯
- AI 回答部分保留完整内容，包括表格、代码块、引用链接
- 每轮讨论独立成文，便于后续查阅

### 2.3.1 图片与附件落盘

如果用户在当前主题的讨论中上传了图片、截图、流程图或其他用于说明需求的附件，则将它们视为讨论记录的一部分处理。

**保存规则：**
- 附件统一保存到当前主题文件夹下的 `附件/` 目录
- 文件命名优先保留用户原始文件名（含中文名）；若不可用，则使用 `{轮次序号}-图-{两位序号}{扩展名}`（见 §命名与语言规范）
- 多张图片按用户在消息中的出现顺序编号，如 `03-图-01.png`、`03-图-02.jpg`
- 只要本轮存在图片或附件，就必须在该轮 Markdown 中自动插入 `## 相关图片` 小节，按出现顺序列出，不可省略
- `## 相关图片` 中每张图都要包含两部分：一句用途说明 + 一条相对路径引用
- 如果同一张图片在后续轮次重复引用，优先复用已保存文件，避免重复落盘

**能力边界：**
- **能拿到原始文件/可读路径** → 必须把原图落盘到 `附件/`，并在对应轮次文件中引用
- **只能看到图片内容，但拿不到原始文件字节或路径** → 不得谎称已保存原图；需要在该轮 Markdown 中明确记录“本轮收到图片说明，但当前会话未提供可直接落盘的原始文件”，并补充图片关键信息摘要

**统一模板：**

当本轮存在图片或附件时，讨论文件优先使用以下结构：

```markdown
# 第 N 轮：{用户问题的一句话概括}

> 时间: YYYY-MM-DD HH:MM

## 用户提问

{经识别与提取后的真实用户提问——保留实质性原话，剔除指令性语句；详见 §2.3.2}

## 背景与分析

{AI 对该问题的分析思考过程，包括搜索/调研结果}

## 建议与回答

{AI 给出的具体建议、方案、回答。保留完整内容，包括表格、列表、代码块等}

## 相关图片

- 图 1：登录流程草图
  ![图 1：登录流程草图](./附件/03-图-01.png)
- 图 2：权限矩阵截图
  ![图 2：权限矩阵截图](./附件/03-图-02.png)

## 本轮要点

- 关键决策 1
- 关键决策 2
```

如果本轮无图片或附件，则省略 `## 相关图片` 小节。

### 2.3.2 用户提问识别与追溯

「用户提问」字段记录的是**本轮讨论所针对的真实问题**，而非用户整条消息的逐字拷贝。先识别消息类型，再提取实质性提问后落盘。

#### 通用原则：提取实质性提问

写入「用户提问」时，在**保留用户原话措辞**的前提下，**删除非方案讨论的指令性语句**：

| 保留 | 删除 |
|:---|:---|
| 用户关于方案、选型、设计、取舍、建议等的原话 | 落盘、归档、创建主题、开始记录等仅用于操作文档的措辞 |
| 用户的措辞与语气（不润色、不缩写、不改写语义） | 与方案讨论无关的流程/工具指令 |

**常见应剔除的指令性语句**（非穷举）：
- 「落盘到 Plans 中」「将以上讨论放到 Plans」「将以上讨论落盘」
- 「以以上讨论为基础创建主题」「创建主题文件夹」
- 「把刚才说的记下来」「开始记录」

剔除后若需衔接前后语义，仅允许做最小标点或连接词调整，**不得改动实质性内容**。

**示例：**
```
用户说：对于 xxx 问题你有什么方案，落盘到 Plans 中

错误 ❌：对于 xxx 问题你有什么方案，落盘到 Plans 中
正确 ✅：对于 xxx 问题你有什么方案
```

此原则适用于**所有**落盘场景——无论是当轮新提问、向上追溯得到的历史提问，还是从复合消息中提取的新问题。

#### 消息类型

| 类型 | 特征 | 落盘时的「用户提问」 |
|:---|:---|:---|
| **实质性问题** | 用户在问方案、选型、设计、取舍、建议等 | 提取实质性部分，保留原话措辞，剔除指令性语句 |
| **纯落盘指令** | 仅要求把已有讨论写入 Plans，无新问题 | 向上追溯至最近一条实质性问题，再按通用原则剔除指令性语句 |
| **落盘 + 新问题** | 落盘指令与新的实质性问题同条出现 | 拆成两轮（见下文），每轮均按通用原则提取 |

**常见纯落盘指令表述**（非穷举）：
- 「将以上讨论放到 Plans」
- 「以以上讨论为基础创建主题」
- 「将以上讨论落盘」
- 「把刚才说的记下来」
- 「开始记录 / 创建主题文件夹」

这类表述**不是**讨论主题本身，不得直接写入「用户提问」。

#### 规则 1：纯落盘指令 → 向上追溯

当用户消息**仅为**落盘/归档指令时：

1. 在**当前会话**中向上查找最近一条**实质性问题**
2. 按通用原则提取并写入「用户提问」（剔除其中的指令性语句）
3. 将此前针对该问题已给出的回答写入「建议与回答」
4. **不**为落盘指令本身单独开一轮（除非该指令还附带新的实质性问题）

**示例（错误 ❌）：**
```
用户先问：对于 xxx 问题你有什么建议
AI 答：1、aaa  2、bbb  3、ccc
用户说：将以上讨论放到 Plans

错误落盘：
  用户提问：将以上讨论放到 Plans
  建议与回答：1、aaa  2、bbb  3、ccc
```

**示例（正确 ✅）：**
```
用户先问：对于 xxx 问题你有什么建议
AI 答：1、aaa  2、bbb  3、ccc
用户说：将以上讨论放到 Plans

正确落盘（第 1 轮）：
  用户提问：对于 xxx 问题你有什么建议
  建议与回答：1、aaa  2、bbb  3、ccc
```

#### 规则 2：落盘 + 新问题 → 拆成两轮

当同一条消息**同时包含**落盘指令与新的实质性问题时：

1. **第一轮（补录）**：按规则 1 追溯并落盘此前尚未落盘的讨论
2. **第二轮（新讨论）**：仅将消息中的**新实质性问题**写入「用户提问」，并记录本轮新回答

从复合消息中提取新问题时：
- 去掉落盘/归档等指令性措辞，保留真实新问题的原话
- 若新问题依附于上文（如「并给出你最推荐的方案」），结合上下文补全指代，使单独阅读时语义完整（如「对于 xxx 问题，给出你最推荐的方案」）；**补全仅限消除歧义，不得改写用户本意**

**示例（正确 ✅）：**
```
用户先问：对于 xxx 问题你有什么建议
AI 答：1、aaa  2、bbb  3、ccc
用户说：将以上讨论放到 Plans，并给出一个你最推荐的方案
AI 答：（推荐方案内容）

第 1 轮：
  用户提问：对于 xxx 问题你有什么建议
  建议与回答：1、aaa  2、bbb  3、ccc

第 2 轮：
  用户提问：对于 xxx 问题，给出一个你最推荐的方案
  建议与回答：（推荐方案内容）
```

#### 规则 3：已在方案讨论模式中 → 正常记录

若用户**已进入方案讨论模式**，每轮实质性问答已实时落盘，则后续纯落盘指令通常表示「确认/继续」，**无需重复创建轮次**；仅当存在尚未落盘的会话内容时，才按规则 1 补录。

#### 规则 4：「保留原话」的适用范围

「保留原话」指保留用户对**实质性问题**的措辞，**不等于**整条消息逐字拷贝：

- **实质性内容**：保留用户原话，不润色、不缩写、不改写语义
- **指令性语句**：一律剔除，不写入「用户提问」
- **纯落盘指令**：整条消息均属于指令性内容，不写入；追溯得到的实质性问题仍按上表处理
- **复合消息中的新问题**：提取实质性部分后写入；允许为消除指代歧义做最小补全（规则 2），不得擅自扩展或改写需求

### 2.4 讨论进行中

- 每轮讨论结束后，**提醒用户** 该轮内容已落盘，并告知文件路径
- 如果本轮包含图片或附件，同时告知用户对应素材已保存到 `附件/`，或明确说明因缺少原始文件而未能落盘原图
- 询问用户是否继续下一轮讨论，还是需要生成待执行方案
- 当用户说"总结一下"、"出个方案"、"生成待执行计划"、"可以了"等时，进入第三步

### 2.5 修改已有轮次 vs 新开轮次

当前讨论可能涉及对已落盘文档的修改。判断标准：

**直接修改已有轮次文件（小修小改）** — 满足以下条件时，直接编辑该轮次的 `.md` 文件：

- 修正某个数据的错误（如数字、版本号）
- 补充遗漏的细节（如漏写了一个依赖项）
- 在「建议与回答」中追加一小段澄清或补充说明
- 在「本轮要点」中增加或删除某条要点
- 优化格式/排版（不涉及内容变更）
- 用户明确指出"更新第 N 轮的内容"

修改后，在文件中标注更新记录（在末尾加一行 `> 更新: YYYY-MM-DD — 说明`）；**但如果属于下面的“需求理解错误”场景，则不保留任何修订痕迹。**

### 2.5.1 需求理解错误时的无痕重写

如果 AI 对用户需求理解错误，导致已经落盘的讨论内容、图片说明、主题命名或 `execution-plan.md` 建立在错误前提上，而后续用户明确纠正了真实需求，则必须按**正确理解后的需求**直接重写当前未锁定主题，**不得**把错误理解产物当作“历史方案”保留下来。

**核心要求：**
- 错误理解产生的内容不属于“历史讨论资产”，而属于无效草稿
- 重写后的主题文件夹应当呈现为：讨论始终围绕用户真实需求展开
- **不得**出现“之前理解成 B、现在改成 A”“废弃原方案”“从旧方案切换到新方案”“修订记录/更正说明”之类表述
- **不得**保留从错误理解过渡到正确理解的时间线痕迹

**不适用场景（必须排除）：**
- 如果用户与 AI 已经围绕 B 方案进行了**实质性讨论**，且这些讨论本身准确反映了当时双方真实接受的方向，只是后来**用户主动决定放弃 B、转向 A**，则**不适用**本节“无痕重写”规则
- 这种情况下，B 方案属于真实讨论历史，而不是“AI 误解造成的无效草稿”
- 后续应按普通流程处理：视关联性决定是新开轮次、继续当前主题，还是新开主题；可以明确记录“用户决定放弃 B，转向 A”这一事实
- 换言之：**“AI 理解错了”要无痕清除，** 但 **“用户后来改变方向了”属于真实决策演进，应允许保留历史轨迹**

**处理方式（未锁定主题）：**
- 若某一轮完全建立在错误理解上，直接删除该轮 `.md` 文件，而不是保留并标注废弃
- 若某一轮只有部分内容受影响，直接将该轮文件改写为基于正确理解后的内容，不写 `> 更新:`、`> 更正:`、`> 修订:` 等痕迹
- 若 `execution-plan.md` 已基于错误理解生成，则直接整体重写，使其只反映正确需求下的方案
- 若主题文件夹名称、各轮文件名、图片说明、附件命名明显受错误理解影响，也一并重命名或删除重建
- 删除错误轮次后，如导致序号断裂，应重排后续轮次文件名，并同步修复 `execution-plan.md` 中的引用
- 若某些 `附件/` 中的图片、截图、附件仅服务于错误理解，且在正确方案中已无意义，应一并删除，避免形成旁证痕迹

**判断标准：**
- 用户是在补充细节、微调约束 → 走普通“修改已有轮次”或“新开轮次”流程
- 用户是在纠正 AI 对需求目标、问题边界、成功标准的根本性误解，且此前产物只是误解下的无效草稿 → 走本节“无痕重写”流程
- 用户与 AI 已对某方案进行了实质性讨论，后续只是用户主动放弃该方向、改选新方向 → **不走**“无痕重写”，而按正常讨论演进处理
- 不确定是否属于根本性误解 → 先判断旧方案是否真实承载过双方认可的讨论；若没有，按“无痕重写”处理；若有，按正常演进处理

**示例 1：适用无痕重写**
- 用户真实需求是 A，AI 误解成 B，并已产出 B 方案
- 用户随后澄清真实需求是 A
- 正确做法：删除或重写所有由 B 理解产生的内容，直接得到以 A 为中心的讨论文件与执行方案
- 错误做法：保留“B 方案已废弃，现切换到 A 方案”之类历史痕迹

**示例 2：不适用无痕重写**
- 用户与 AI 已经围绕 B 方案进行了实质性讨论，B 方案本身并非误解产物
- 后续用户经过权衡，决定放弃 B，转向 A 方案
- 正确做法：将“放弃 B、转向 A”视为真实决策演进，按正常流程记录，不删除 B 的历史讨论
- 错误做法：把真实存在的 B 方案讨论整体抹去，并伪装成从一开始就在讨论 A

**新开轮次（差异较大）** — 满足以下任一条件时，创建新的轮次文件：

- 用户提出了一个全新的问题（即使与之前轮次相关）
- 讨论方向发生明显变化（如从"选型"转向"测试策略"）
- 需要大幅重写或替换原有回答
- 新增内容超过原有内容的 30%
- 不确定 → **默认新开轮次**（安全策略）

**判断流程：**
```
当前讨论是否与某已有轮次直接相关？
  ├── 是 → 讨论内容是否仅为小修小改？
  │         ├── 是 → 直接编辑该轮次文件 + 标注更新
  │         └── 否 → 新开轮次
  └── 否 → 新开轮次
```

## 第三步：生成待执行方案

### 3.1 汇总所有讨论

回顾该主题文件夹下所有讨论文件，提取：
- 所有关键决策
- 最终确定的技术选型
- 架构设计要点
- 实现步骤与优先级

**汇总口径：**
- 只以当前主题文件夹中的**最终有效文件**为准
- 已被无痕重写替换、删除、重命名的错误理解内容，不得再以“历史方案”身份出现在汇总中
- `execution-plan.md` 的需求概述、技术决策、参考讨论，必须全部建立在用户最终确认的真实需求之上

### 3.2 撰写待执行方案

## 第四步：会话延续判断

在进入 plan 模式前，需要判断是否继续已有主题还是新开主题。

### 4.1 检查最新主题状态与延续条件

查找 `Plans/` **根目录**下最新日期的主题文件夹（排除 `Plans/归档/`、`Plans/未完成池/`；遗留 `Plans/_backlog/` 同等排除），并按以下顺序判断是**延续当前主题**还是**新开主题**。

#### 4.1.1 先判断是否已归档（锁定）

| 最新主题位置 | 行为 |
|:---|:---|
| **`Plans/归档/` 下** | 不适用延续 — 该主题已锁定；在 `Plans/` 根下**新开主题** |
| **`Plans/` 根下** | 继续进入下一步，判断是否适合延续 |

**锁定判断标准：主题位于 `Plans/归档/` 下即已锁定。** 不依赖 `STATUS.md` 或 `[LOCKED]` 前缀。

**遗留：** `Plans/` 根下若仍有带 `STATUS.md` 的旧主题，视为已锁定、不得修改；新流程不得再创建 `STATUS.md`。

#### 4.1.2 未锁定时，判断是否适合延续

对于**未锁定**的最新主题，不再一律默认延续，而是综合以下三个因素：

1. **时间间隔**：当前讨论时间距离该主题最后一轮讨论时间是否较近
2. **主题关联性**：当前用户问题与该主题的核心目标、关键决策、执行计划是否强相关
3. **讨论意图**：用户是在补充/修正/延续原方案，还是已经切换到一个新的需求方向

#### 4.1.3 默认经验规则

可按以下经验规则判断：

| 条件 | 建议行为 |
|:---|:---|
| **同一天**，且主题明显相关 | **延续当前主题** |
| **跨天（一般到第二天即可视为间隔较长）**，但主题仍然高度相关，且明显是在继续推进同一方案 | **可延续当前主题** |
| **跨天（一般到第二天即可视为间隔较长）**，且主题关联性不够强 | **新开主题** |
| 虽未跨天，但讨论目标已明显切换 | **新开主题** |
| 无法确定是否属于原主题的自然延续 | **默认新开主题** |

这里的“关联性不够强”包括但不限于：

- 当前问题虽然发生在同一模块，但目标已经从原来的“API 接入”转为“UI 配置策略/产品能力设计/测试方案”等不同方向
- 当前讨论不再围绕原主题的关键决策、执行计划或遗留事项展开
- 如果把新内容硬塞进旧主题，会导致主题标题与讨论内容明显失焦

#### 4.1.4 判断原则

优先遵循以下原则：

- **宁可多开主题，也不要把弱相关问题混入旧主题**
- 只有当“用户显然在继续上一个方案”时，才延续原主题
- “同一业务域/同一目录/同一文件” **不等于** “同一主题**

### 4.2 延续已有主题

只有在满足以下条件时，才延续已有主题：

- 最新主题**未锁定**
- 当前讨论与该主题**强相关**
- 当前讨论明显属于原方案的补充、修正、细化或继续推进

如果判定为延续已有主题：
- 继续使用已有文件夹
- 轮次序号接续（如已有 7 轮，则从 `08-*.md` 开始）
- 如果已有 `execution-plan.md`，讨论中涉及方案修改时直接编辑该文件
- 向用户说明"当前已有 X 轮讨论，继续在同一主题下记录"

### 4.3 新开主题

如果满足以下任一条件，则新开主题：

- 最新主题已在 `Plans/归档/`（或遗留 STATUS.md 已锁定）
- 当前讨论距离最新未锁定主题时间间隔较长（一般第二天即可视为较长），且关联性不够强
- 当前讨论已形成新的需求方向、设计目标或决策边界
- 无法自信判断为原主题的自然延续

如果判定为新开主题：
- 按第一步规则创建新文件夹（新日期 + 新中文主题简称）
- 如有需要，可在首轮讨论中简要说明它与上一个主题的关系（例如“从某主题演化而来，但已是独立议题”）
- **不得**自动复制上一主题的 `UNEXECUTED.md` 或 `Plans/未完成池/` 中的内容
- 若用户主动要求参考历史遗留，可引导其查阅 `Plans/未完成池/`，由用户决定纳入哪些事项

### 4.4 判断流程图

```
用户说"讨论方案"
  ↓
检查 Plans/ 根下最新主题（排除 归档/、未完成池/；遗留 _backlog/ 同等排除）
  ↓
是否在 Plans/归档/ 下（或遗留 STATUS.md）？
  ├── 是 → 已锁定 → 在 Plans/ 根下新开主题
  └── 否 → 检查时间间隔 + 主题关联性 + 讨论意图
              ├── 强相关且属于继续推进 → 延续当前主题
              └── 跨天且弱相关 / 方向切换 / 判断不清 → 新开主题
```

## 第五步：锁定与归档规则

主题锁定只能由 `plan-lock` skill 在用户明确确认后完成；本 skill **不**移动主题至 `Plans/归档/`。

### 5.1 已归档（锁定）状态

一旦主题位于 `Plans/归档/` 下，该文件夹 **不得再修改**：

- 不允许编辑已有讨论文件
- 不允许在归档文件夹中新增文件
- 不允许修改 `execution-plan.md`
- 即使未来有对该主题的延续讨论，也必须 **在 `Plans/` 根下创建新的主题文件夹**

### 5.2 不再使用的标志

- **不创建** `STATUS.md`
- **不使用** `[LOCKED]` 文件夹名前缀
- **锁定 = 位于 `Plans/归档/`**

### 5.3 归档后的行为

**新的相关讨论** → 在 `Plans/` 根下创建新文件夹。**不自动继承**遗留清单；需要时查阅 `Plans/未完成池/`。
