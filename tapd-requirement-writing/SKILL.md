# TAPD 需求编写与重整

## 何时使用
- 把讨论/会议内容落成 TAPD 需求（父 + 子）
- 需求太碎要合并，或拆分粒度不对要重整
- 改写已有需求文案、调整处理人/排期、作废并入旧需求
- 往需求正文里内嵌图片（不是附件）

## 前置
- TAPD connector 已连接
- TAPD 工具均为 deferred：先 `ToolSearch`，再 `DeferExecuteTool`
- **workspace_id 与 ID 前缀不同**：灵创_用户端 workspace_id `40677205`、灵创_工厂端 `44355585`、Agent（虾皮POD）`39230945`；**调 API 必须用 workspace_id**

## 一、需求文案结构（核心五段）

| 段 | 写什么 | 要求 |
|---|---|---|
| **问题** | 现在为什么不行 | 只写现象，不做原因分析 |
| **需求**（目的） | 要达成什么 | 一两句；简单需求可与「问题」合并成一段 |
| **功能变更** | 要改成什么样，分条编号 | 一条一个动作、可验收；写「改成什么」不写「怎么实现」 |
| **验收标准** | 怎么算做完 | 一条一句，能用眼睛验 |
| **备注** | 重要的口径、约束、待确认 | 只记要紧的；没有就整段不写 |

**其余都是附带**（谁用、依赖、工期、优先级）：可写可不写、可详可略，一般放段首一行斜体。

### 明确不写进需求
- **实现方案**（怎么改代码）
- **文件路径**（`src/...` 之类 —— 别人看不到，文件清单留在本地开发计划里）
- **字段清单**、接口参数表
- **自己推演的边界问题**（如「编码格式怎么校验」「一个编码能否对应多张图」）—— 用户说「不考虑」的，就等于不存在：不留待确认、不写风险、不加说明

### 待确认只保留
**会议材料里真实出现的口径冲突或缺口**，不推演实现细节。

## 二、粒度规范

**按「一件能独立做完、某个角色当天能用上」切，不按技术层切。**

- ❌ 不要拆成「接口模块」「图库模块」「前端交互」「后端逻辑」这类技术层条目 —— 会变成十几条碎需求
- ✅ 一条需求 = 一个完整功能（前端 + 后端都在里面），内部用分条列出前后端各做什么
- 若开发侧另有「后端实现」条目，**把它挂到对应功能下面当子需求**（功能=业务视角，子需求=实现视角）

判断标准两条：
1. 做完后对应角色当天就能用上，不是半成品等别的功能；
2. 任何一条延期，不影响已上线的其他条目。

## 三、处理人规则

| 功能性质 | 处理人 |
|---|---|
| 纯前端 | 何成标 |
| 纯后端 | 张栋栋 |
| 前后端都涉及 | 何成标、张栋栋 |

- **文案正文里不写前后端分工**（「纯前端」「后端为主」这类表述删掉），分工只看处理人字段
- 写法：`"何成标;张栋栋;"`（**分号结尾**）

## 四、TAPD 操作要点

### 建需求
```
create_story_or_task(workspace_id, name, options={
  description: "<html>", owner: "何成标;张栋栋;",
  parent_id: "父需求ID", priority_label: "Middle", status: "初稿"
})
```
- 优先级用 `priority_label`（High / Middle / Low / Nice To Have），**不要用 priority 数字**
- 描述走 **HTML 富文本**：`<h4>段名</h4>` + `<p>` / `<ol>` / `<ul>` / `<table>`
- 子需求 ID 形如 `11 + workspace_id + 7 位流水`

### 改需求
```
update_story_or_task(workspace_id, options={ id, name, description, owner, begin, due, status, parent_id })
```
- ⚠️ **所有字段都放在 `options` 里**（顶层只允许 workspace_id + options，否则报 additionalProperties 错）
- ⚠️ **`parent_id` 传入会被忽略 —— MCP 不支持改父级**。要调整层级只能：
  1. 让用户在 TAPD 网页端手动拖（推荐，保留状态/进度/评论）；
  2. 或「新建 + 把旧条置已拒绝」（会重置状态、进度、创建人）
- 日期字段：`begin` 预计开始、`due` 预计结束，格式 `YYYY-MM-DD`
- 状态取值（灵创_用户端 story）：`planning` 初稿 / `developing` 实现中 / `status_3` 评审中 / `status_4` 测试中 / `resolved` 已实现 / `rejected` 已拒绝；先调 `get_workflows_status_map` 确认

### 查询
- 查父需求下全部子需求：`get_stories_or_tasks(workspace_id, options={entity_type:"stories", parent_id:"父ID", fields:"id,name,owner,status,begin,due,created", limit:50})`
- 注意：`children_id` 字段可能不全（缓存），**以 parent_id 查询结果为准**

### 作废 / 并入旧需求（TAPD 不能删条目）
1. 改名：`（已作废）原 Fx <旧名> —— 已并入：<新功能名>（…新ID）`
2. 状态置 `rejected`（已拒绝）
3. 描述里写明**作废原因 + 归属 + 原内容摘要**（留痕）
4. 反向在新需求备注里加一行「后端实现见子需求 …00xxxx」建立双向可查

### 往需求正文内嵌图片（不是附件）
1. `upload_image(workspace_id, entry_type=story, entry_id, filename)` → 拿 `upload_url` → `curl -F "file=@图" -F "filename=原文件名" "<url>"`；或分块 `chunk_start → chunk_append（纯 base64、每块 ≤50000 字符、去掉 data:image 前缀）→ chunk_finish`
2. 取结果的 `value`（如 `/tfl/captures/2026-09/tapd_xxxx.png`）——**别用 `get_image` 的 `download_url`（只有 300 秒）**
3. 描述里写 `<p><img src="https://www.tapd.cn/<workspace_id>/tfl/captures/xxx.png" /></p>`
4. 图片必须先挂到该 entry（带 entry_id），正文才引用得到

## 五、术语与口径

- **术语以实际界面为准**：录音/转写里的错词先按界面截图校正，例如「**非转平**」实为**【转平台】**（弹窗名「转平台订单」）
- **口径变更必须做全量巡检**，不能只改当轮那份：
  1. 改口径源（主图 + 需求文档）
  2. 用被取代的关键词 grep 全部本地 `.md` / `.html`
  3. 图与方案改成新口径或加顶部口径声明；会议记录可留但顶部要指向最新；整份作废的移入 `历史版本/`（**不删**）
  4. 更新本地 `README-文档索引与口径声明.md`

## 六、推荐交付顺序

1. 先把口径谈清 → 出**需求文案**（本地 md，五段式）给用户过目
2. 用户确认后再动 TAPD（**不要先改 TAPD 再让用户看**）
3. 改完回读校验：查一次父需求的全部子需求，确认条数、名称、处理人、状态、日期都对
4. 顺手同步本地文档（流程图 / 开发计划 / 需求文档）

## 七、踩过的坑（别重犯）

| 坑 | 正确做法 |
|---|---|
| 把文件路径写进需求 | 别人看不到；文件清单留在本地开发计划 |
| 需求拆成技术层（接口/模块/前端/后端） | 按功能拆，一条需求含前后端 |
| 自己推演边界问题写进待确认 | 会议里没提到的就不写；用户说「不考虑」的直接删 |
| 一次改了 TAPD、另一次忘了同步本地文档 | 口径变更必做全量巡检 |
| 以为能改父级 | MCP 不支持，需网页端拖 |
| 用 `get_image` 的 download_url 内嵌 | 300 秒失效，要用持久路径 `value` |
| 文案里写「后端为主/纯前端」 | 分工只在处理人字段体现 |
