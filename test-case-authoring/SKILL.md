# 测试用例编写（红灯验收）

当用户说**增加 / 编写 / 补充测试或测试用例**时，默认意图是：**用测试把当前认为有问题（或即将修）的行为钉住**，而不是把套件刷绿或顺手修产品代码。

## 默认假设（最重要）

| 默认 | 含义 |
|:---|:---|
| **要写的是「会失败」的用例** | 对**当前**代码基线运行后，**预期为红（fail）** |
| **跑完是绿的** | 优先怀疑**用例写错了**（断言过弱、测错对象、mock 掉缺陷、数据/setup 不对），应**只改测试**直到能稳定复现问题，或向用户说明为何绿可能是合理的 |
| **编写完成后** | **禁止**自动修改业务/生产源码去消红；只交付用例 + 失败输出 + 简要解读 |
| **用户明确豁免** | 仅当用户明确表示 **「只编写 / 不考虑红还是绿 / 不用跑 / 不用管过不过」** 等，才可不按红灯验收、可不跑测、可不因「绿了」而返工用例 |

## 何时必须执行

满足 **任一** 即 Read 并遵守：

- 用户说：编写测试、增加测试、写测试用例、补 spec、加单元测试 / 集成测试 / E2E 用例等
- 为某个 bug、回归、需求缺口**新增**断言或新文件
- 用户描述「帮我写个测试复现 xxx」

**可不按红灯验收（但仍可读本文作参考）：**

- 用户明确：只编写、不考虑红绿、不要跑、写完即可
- 纯重构测试（拆分文件、改名）且**不改变**断言语义
- 用户紧接着要求「修到绿」——那是**新任务**，需用户**单独**提出修产品或修测试的意图

---

## 核心规则

| 必须 | 禁止 |
|:---|:---|
| 从对话归纳**预期失败点**（现象、输入、期望 vs 实际） | 无预期仍写「烟雾测试」糊弄 |
| 编写后**运行**相关测试（项目内最小命令） | 只提交文件不跑 |
| 基线结果为 **红** → 交付失败摘要并**停** | 见红后自动改 `src/` 等业务代码 |
| 基线结果为 **绿** → 按 §绿灯返工 只改测试或询问用户 | 把绿当作「任务完成」默认结束 |
| 交付时说明：命令、红/绿、失败信息在证什么 | 顺手「帮你修好了」产品 |

## 工作流程

```
1. 读取用户意图：测什么行为？当前认为哪里有问题？
  → 2. 查项目测试框架、目录约定、现有同类用例风格
  → 3. 编写/新增用例（断言对准问题，避免过度 mock）
  → 4. 运行最小范围测试命令
  → 5. 结果判定：
        红 → 交付（§交付物），结束（不修产品）
        绿 → §绿灯返工（除非用户已豁免）
  → 6. E2E 且需控制台？叠加 e2e-console-monitoring
```

---

## 绿灯返工（仅改测试，不改产品）

在**未**收到「不考虑红绿」豁免时，若对**当前基线**运行通过，按序自查并**只修改测试代码**：

1. **断言是否过弱** — 只测「不抛错」而未测错误返回值、UI 文案、状态、副作用  
2. **是否测错层** — 测了 mock/stub 而非真实模块；集成路径被替换成 fake  
3. **setup 是否掩盖问题** — 用了「正确数据」而用户场景是脏数据/边界/并发  
4. **是否测了旧行为** — 需求是错的行为应失败，却 assert 了现状  
5. **E2E 是否选错选择器/等待** — 断言到了静态占位而非失败态  

返工后**再跑**；仍绿且确信产品已正确 → 向用户说明「基线可能已修复或理解偏差」，**仍不修产品**，除非用户改口。

## 交付物（编写完成时）

```markdown
## 测试编写结果

- **文件**：…
- **运行命令**：…
- **结果**：🔴 失败（符合预期） / 🟢 通过（已返工 N 次 / 用户豁免 / 说明）

### 失败摘要（若为红）
- 用例名：…
- 关键断言/错误信息：…
- **表明的问题**（1～3 句，对应用户原始诉求）

### 说明
- 未修改业务源码（除非用户另行要求）。
- 若要修产品或修到绿，请单独说明。
```

## 用户话术对照

| 用户说法 | 行为 |
|:---|:---|
| 「写个测试复现 xxx」 | 红灯验收；红则交付 |
| 「增加测试覆盖 yy 模块」且上下文有 bug | 同上 |
| 「只写测试，别管过不过」 / 「不考虑红绿」 | 可绿即停；不因绿返工 |
| 「写完测试并修到绿」 / 「修 bug」 | **超出本 skill 默认**；需修产品，用户明确授权 |
| 「测试失败了帮我修」 | 新任务：可修产品或改测试，按用户指定 |
