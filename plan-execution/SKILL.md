# 方案执行与跟踪

当用户决定执行方案时，依照待执行方案逐步实施开发，完成后产出总结文档草稿。

---

## 工作流程

```
1. 定位待执行方案 → 2. 逐阶段执行开发 → 3. 产出总结文档
```

---

## 第一步：定位待执行方案

主题文件夹名、各轮讨论文件名等命名规则见 `plan-discussion` §**命名与语言规范**（默认中文）。

### 1.1 查找最新主题

在 `Plans/` **根目录**下查找主题文件夹（**排除** `Plans/归档/`、`Plans/未完成池/`；遗留 `Plans/_backlog/` 同等排除），按日期排序，定位**最新的、含有 `execution-plan.md` 且尚未归档**的主题。

主题是否已锁定的判断：
- 位于 `Plans/归档/` 下 → 已锁定，跳过
- 位于 `Plans/` 根下 → 未锁定，可执行

**遗留：** `Plans/` 根下若仍有含 `STATUS.md` 的旧主题，视为已锁定、跳过；新流程不得再创建 `STATUS.md`。

### 1.2 确认执行范围

**默认规则：只执行 Phase 1。**

如果 `execution-plan.md` 包含多个 Phase：
- 用户说"执行方案" / "开始执行" / "开工" → **只执行 Phase 1**
- Phase 2 及以后 → 执行完成后自动移入 `UNEXECUTED.md` 的"计划在未来版本加入"章节

用户可覆盖默认规则：
- "执行全部 Phase" → 执行所有
- "执行 Phase 1 和 2" → 执行指定的
- "执行到 Phase 3" → 执行 1–3

此外向用户确认：
- 执行哪个主题的方案
- 是否需要先更新讨论（方案与当前理解是否有偏差）

### 1.3 所有未执行 Phase 自动纳入 UNEXECUTED

执行完成后，在执行结果的 `UNEXECUTED.md` 中，所有本次未执行的 Phase 自动归入：

```markdown
## 🔮 计划在未来版本加入

| 事项 | 计划版本/Phase | 来源 |
|:---|:---|:---|
| Phase 2: 图片与文件同步 | Phase 2 | 当前方案 subsequent phase |
| Phase 3: 多设备与健壮性 | Phase 3 | 当前方案 subsequent phase |
| Phase 4: 打磨与发布 | Phase 4 | 当前方案 subsequent phase |
```

这样后续锁定主题时，这些 Phase 会进入 `UNEXECUTED.md`，并由 `plan-lock` 写入 `Plans/未完成池/` 精简摘要。

---

## 第二步：逐阶段执行

### 2.1 建立任务跟踪

每开始一个 Phase，使用 `TaskCreate` 创建对应任务，按 `execution-plan.md` 中的任务清单逐项实施。

### 2.2 执行过程中

- 严格遵循方案中的技术决策
- 如发现方案与实际情况冲突，暂停并告知用户，询问是否需要调整方案
- 如因技术原因无法完成某任务，记录原因，继续下一任务
- 关键里程碑完成后向用户汇报进度

### 2.3 执行异常处理

如果某个任务：
- **执行失败**：记录失败原因、尝试过的方案、是否可绕过
- **完成度低于预期**：记录差距和后续改进方向
- **需要推迟**：记录推迟原因，移入未执行文档

---

## 第三步：产出总结文档（草稿）

开发完成后，在当前主题文件夹中创建 **草稿版** 总结文档。**此时尚未锁定，方案仍可继续修改。**

⚠️ **此阶段不移入 `Plans/归档/`**。锁定由 `plan-lock` skill 单独完成。

### 3.1 已执行结果确认文档

创建 `COMPLETED.md`：

```markdown
# 执行结果确认

> 执行完成时间: YYYY-MM-DD
> 基于方案: [execution-plan.md](execution-plan.md)

## 执行摘要

{一两句话概括本次执行成果}

## 逐项确认

### Phase 1: {名称}

| 任务 | 状态 | 备注 |
|:---|:---|:---|
| 任务 1 | ✅ 完成 | |
| 任务 2 | ✅ 完成 | |
| 任务 3 | ⚠️ 部分完成 | {说明差距} |
| 任务 4 | ❌ 未完成 | {原因} |

### Phase 2: {名称}
...

## 整体统计

| 指标 | 数值 |
|:---|:---|
| 总任务数 | N |
| 完成 | N |
| 部分完成 | N |
| 未完成 | N |
| 完成率 | XX% |

## 变更记录

{执行过程中对方案的任何偏离，及原因}
```

### 3.2 未执行文档（产出 / 更新）

`UNEXECUTED.md` 只记录**当前主题执行结束后仍未处理完的事项**，供锁定前核对；锁定后完整版留存在主题文件夹，精简版由 `plan-lock` 写入 `Plans/未完成池/`。

执行 skill 不负责跨主题传递遗留事项。**不做继承**；新主题如需参考历史遗留，由用户主动查阅 `Plans/未完成池/`。

#### 生成 / 更新 UNEXECUTED.md 的处理流程

1. 读取当前主题已有的 `UNEXECUTED.md`（如有）和本次执行结果。
2. 如果是继续执行下一个 Phase，先识别本次执行的 Phase：
   - 本次已完成的 Phase 从“计划在未来版本加入”中移出；
   - 本次部分完成的 Phase 保留剩余任务；
   - 本次未触及的后续 Phase 继续保留。
3. 逐条检查当前遗留事项的处理结果：

| 处理结果 | 行为 |
|:---|:---|
| ✅ 本次执行中完成了 | **移出** — 不再出现在新的 `UNEXECUTED.md` 中 |
| ❌ 明确放弃（所有未来版本都不做） | **移出** — 记录到放弃清单中 |
| ⏳ 仍未处理 | **保留** — 继续留在 `UNEXECUTED.md` |
| 🔄 部分处理 | **保留** — 更新为“剩余部分” |

4. 加入本次新产生的事项：执行失败、未完成、完成度不足、主动移出本次开发节奏、未来 Phase。
5. 合并更新 `UNEXECUTED.md`。如果文件已存在，不得简单覆盖，应基于旧内容增删改：移除已完成项、保留仍待处理项、追加新遗留项。

#### UNEXECUTED.md 模板

```markdown
# 未执行 / 遗留事项

> 生成时间: YYYY-MM-DD
> 来源主题: {当前主题名称}
> 说明: 本文档记录当前主题执行后仍未完成、未处理或计划未来处理的事项

---

## ⏳ 仍待处理的遗留事项

### ❌ 执行失败

{尝试了但因技术原因失败的任务}

| 事项 | 失败原因 | 尝试的方案 | 建议 |
|:---|:---|:---|:---|

### ⚠️ 未开发完成 / 完成度不足

{开始但未完成，或完成度明显低于预期的模块}

| 事项 | 当前状态 | 差距描述 | 后续建议 |
|:---|:---|:---|:---|

### 📅 被移出本次开发节奏

{曾在当前主题讨论中出现，但主动移出本次执行的功能/模块}

| 事项 | 移出原因 | 优先级 | 参考讨论 |
|:---|:---|:---|:---|

### 🔮 计划在未来版本加入

{方案中明确标记为未来版本，或本次未执行的 Phase}

| 事项 | 计划版本/Phase | 参考讨论 |
|:---|:---|:---|

---

## 🗑️ 已放弃事项（仅记录）

| 事项 | 放弃原因 | 放弃时间 | 来源 |
|:---|:---|:---|:---|
```

## 补充规则

### 与 plan-discussion skill 的协作

- plan-discussion 发现当前主题已在 `Plans/归档/`（或遗留已锁定） → 在 `Plans/` 根下自动创建新主题（不继承遗留清单）
- plan-discussion 发现当前主题未锁定且已有 `execution-plan.md` → 视为延续讨论，可修改方案
- 本 skill 发现没有待执行方案 → 提示用户"当前没有待执行的方案，是否先讨论一个？"
- 锁定后未完成事项 → 由 `plan-lock` 写入 `Plans/未完成池/`，不在主题间自动传递
