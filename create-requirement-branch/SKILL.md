# 创建分支

从**远程主分支最新提交**拉出需求分支，上游设成**同名远程分支（自己）**。

**产出物 = 分支 + worktree 目录 + 一行进入路径 + 一次 `pnpm install` + 一次本地服务**。需求分支建完随即起服务（pm2 托管、固定端口，见文末「起本地服务」与 `references/本地服务.md`）；合并分支不起（要起由用户点名）。

**建完之后的开发规范**：本需求的开发提交**都推回这条分支**——提交后直接 `git push` 到该分支的远程同名分支（上游就是它自己）；不推主分支、不 `--force`、不开 PR（除非用户要求）。

**下一步（日报硬规则）**：开工前先写一次**需求理解**——日报 v3 要求需求首次进「开发中」前必须写过一次需求理解，写清功能点、边界 / 歧义 / 待确认点再动手。文档统一落在**工作区根目录**的 `Docs/需求拆解/`（**按当天建日期子目录归档**：`Docs/需求拆解/YYYY-MM-DD/`，不按月），**不随代码提交**。

**拆解即存档（2026-10-13 用户口径）**：拆解时必须把**需求原文与截图原图**一并落盘（后续 `代码审查` 做需求一致性比对的输入，审查侧按 `Docs/需求拆解/**/*<需求id>*` 检索）——与拆解文档同目录、同名：

- `<拆解文档同名>_需求原文.md`：原文全文，**一字不改**，开头注明来源（TAPD 链接 / 用户粘贴）与存档日期
- `<拆解文档同名>_截图/`：截图**原图**原文件名存放，不压缩、不裁剪、不转述成文字

**再往后**：开发（`开发中规范` → `代码审查` 影响面与回归）→ 每项完成即提交推送到本分支（`生成提交`）→ 随手把工作记进共享日报（`日报采集共写`，只更新自己会话的块）→ 上测试线/正式线后查 CNB 更新状态。全链路见工作区《日报周报生产流程_SOP.md》「零、日常主线」。

**本文档不绑定某个工具**：涉及"打开新目录"这类动作，按你实际用的工具照「跨工具怎么做」选一条；起服务统一按 `references/本地服务.md`（pm2）。

## 先分岔：建哪种分支（2026-10-06 用户口径）

| 用户要 | 分支类型 | 基地 | 分支名 = 目录名 |
|---|---|---|---|
| 开一个新需求（默认，本文主体） | **需求分支** | `origin/<生产主分支>` | `{U\|F\|D\|S}-{短id后4位}-{标题截取}` |
| 解决开发分支与测试分支的冲突、把需求改动带进测试线 | **合并分支** | `origin/<测试分支>` | `{U\|F\|D\|S}-{短id后4位}-To-test` |

- 需求分支那套（命名推导、速度优先、硬性规则、撞名复用、汇报）照旧；合并分支的差异见文末「合并分支（To-test）」一节。
- 触发词：「创建合并分支」「建 To-test 分支」「解决和测试分支的冲突」「把 xx 合进测试」。

## 速度优先（默认 · 2026-09-22 用户口径）

整个动作默认**一次脚本调用**（2026-10-13 用户口径：省掉 agent 逐步判断）：

1. **调一条龙脚本**：在目标业务仓内运行本技能的 `scripts/create-branch.sh <U|F|D|S> <需求id> "<标题>"`（合并分支末尾加 `--to-test`）——建分支、装依赖、起服务、打印汇报块一次跑完
2. **交付**：脚本输出的汇报块原样转述（含一行 `cd` 进入路径），结束

**报错即上报（2026-10-13 用户口径）**：脚本不存在或中途任何报错 → 把**原始报错原样汇报给用户**，不检索、不查找、不探究、不自行修复——脚本由用户来优化。

**不做的事（除非报错或用户点名）**：

- 不做任何完成检测：不校验上游、不用 `git status` / `git worktree list` 复核、不确认 node_modules
- `pnpm install` 不预检：不查 pnpm 版本、不看锁文件、不判断是不是 Node 项目、不共享 node_modules
- `pnpm install` 正常结束即算完成，装完不验证（不跑 `pnpm ls`、不 build、不追加装包）
- 不找启动命令、不读 `package.json`（起服务照 `references/本地服务.md` 模板抄，怎么启动不由 agent 判断，起不来报错问用户）
- 撞名不预查（既有口径：直接建，失败即复用）

**`pnpm install` 报错才介入**：读清报错，做最小修复并重试一次；仍失败就如实汇报，不循环重试、不自行换包管理器。

## 一条龙脚本（默认路径 · 2026-10-13 用户口径）

`scripts/create-branch.sh` 把「建分支 → 装依赖 → 起服务 → 汇报」固化成一条命令，agent 只调用、不判断：

```bash
# 在目标业务仓内运行（脚本自动定位仓根）；合并分支末尾加 --to-test
bash "<本技能目录>/scripts/create-branch.sh" U 1002998 "店铺备注"
```

- **脚本内部固化的规则**（与正文一致，改口径两处同改）：id 剥前缀取后 4 位、标题截取 ≤24 字、分支名=目录名、worktree 建在**原仓旁边同级**、端口=仓库位+id后4位、pm2 托管、启动方式按端位查脚本内配置表（U=`VITE_PORT`、F/D/S=`--port`；新仓库首次报错就补表）
- **脚本自动处理**：主分支探测（origin/HEAD → main2/main/master；`--to-test` 探测 main-test/main_test，判不了报错问用户）、被 gitignore 的 `.env*` 复制（不存在静默跳过）、撞名复用（目录已存在直接用，不覆盖不追加序号）、同名 pm2 在跑只报地址不重启
- **必须沙箱外运行**：写 `~/.pm2`、git 推送要走钥匙串
- **合并分支（`--to-test`）**：只建分支+装依赖，**不起服务**；合入开发分支与解冲突按正文「合并分支」节手走
- 输出即汇报块，agent 原样转述；**退出码非 0 → 原始报错原样上报用户，检索/排查/修复一概不做**（脚本由用户优化）

## 命名规范

**分支名 = worktree 目录名，同名**（2026-10-06 用户口径：分支名也带端前缀）：

```
{U|F|D|S}-{短id后4位}-{标题截取}
```

- 端前缀 = 需求所属端映射的单字母：**U=用户端、F=工厂端、D=设计器、S=ShopAgent**。从需求所在 TAPD 项目 / 目标仓库判断；用户点名了端就用点名的；判断不了**问一句，不猜**。

例题（真实输入 → 结果）：

| 输入 | 分支名 = worktree 目录名 |
|---|---|
| id `1140677205001002792`（TAPD 链接 `…/story/detail/1140677205001002792`）+ 标题「效果图与转平台能力流程重构（F1~F9 共 9 个功能，均可独立开发上线）」+ 端：用户端 | `U-2792-效果图与转平台能力流程重构` |
| id `1002816` + 标题「WB 颜色接口按色系分组展示」+ 端：工厂端 | `F-2816-WB-颜色接口按色系分组展示` |
| id `PROJ-88` + 标题「导出报表」+ 端：设计器 | `D-PROJ-88-导出报表`（非数字 id：前缀用完整 id） |
| id `1002830` + 标题「商品批量导入去重」+ 端：ShopAgent | `S-2830-商品批量导入去重` |

**三步推导（得 `{短id后4位}-{标题截取}` 段）：**

1. **取 id**
   - 给的是**短 id**（`1002792`）→ 直接用。
   - 给的是**长 id / TAPD 链接**（`1140677205001002792`）→ **去掉前 10 位前缀、再去掉前导 0**，得 `1002792`。
   - 非纯数字 id（`PROJ-88`）→ 原样使用，且**前缀用完整 id**。
2. **前缀** = 短 id 的**后 4 位**（`1002792` → `2792`）。
3. **标题截取** = 取标题里**第一个 `（` 或 `(` 之前**的部分 → 去首尾空白 → **空白转 `-`** → 剔除 git 非法字符（`~ ^ : ? * [ ] \` 与控制字符）→ **保留中文**。
   - 建议 ≤ **24 个字符**；太长时保留语义最前的部分截断，并在汇报里写明"标题已截断"。
   - 用户直接给了短标题 → 以用户的为准，不再截取。

**端前缀拼在最前面，得到的那一串同时用作分支名与 worktree 目录名。**

**合并分支命名**（无标题段）：

```
{U|F|D|S}-{短id后4位}-To-test
```

例：工厂端需求 `2816` → 合并分支与目录同名 `F-2816-To-test`。

## worktree 建在哪

**一律建在原仓目录旁边（同级）**：`<原仓父目录>/<worktree目录名>`（2026-10-13 用户口径：不用 `Apps/frontend/`，不用 `-wt-` 兜底；脚本按此固化）。

⚠️ 若原仓父目录本身是个 git 仓，`git status` 会把 worktree 显示成未跟踪 → 提醒用户把该目录加进 `.gitignore`。

## 模式选择（先判再做）

| 条件 | 模式 | 行为 |
|---|---|---|
| 用户说「worktree」「并行」「另开一线」「当前分支还在做 A」 | **Worktree（默认并行）** | 在**新目录**挂新分支；**不切换、不 stash、不碰**当前工作区 |
| 当前分支不是主分支，或工作区有未提交改动，又要开新需求 | **Worktree** | 同上 |
| 用户明确说「就在当前仓库切分支 / 不用 worktree」，且工作区允许检出 | **In-place** | 在本仓 `switch -c --no-track` |
| 信息不足 | **先问一句** | 默认倾向 Worktree |

**禁止**：在正开发 A 的脏分支上直接 `checkout -b` 开 B。

## 硬性规则（两种模式都要满足）

1. 新分支**只能**从 `origin/<主分支>`（fetch 后）创建。
2. 分支名与 worktree 目录名按上面的**命名规范**。
3. `@{upstream}` **必须是** `origin/<同名分支>`（自己）。
4. **绝对禁止**上游是主分支；禁止向主分支 push。
5. 建分支必须 `--no-track`。
6. **需求分支建完随即起本地服务**（快捷模式不加检测，见文末「起本地服务」与 `references/本地服务.md`）；合并分支不起，要起由用户点名。
7. 不改业务代码、不 `commit`。
8. 建完分支即在工作目录跑 `pnpm install`（速度优先：无报错不做任何检测，见「速度优先」）。

## 公共前置

### 输入可能是截图（日常多数情况）

🐱 常直接丢一张需求截图。按这个顺序处理：

1. **从截图读出**：需求标题、TAPD 编号（有就最省事）、关键口径（尺码/字段/状态这类）。
2. **只有标题、没有编号** → 用 `TAPD待办查询`（装了就用，没装就人工核）在对应项目按标题搜，拿到 id 与当前状态。
3. **搜不到对应需求单** → 不要硬编 ID：告诉用户"没有单"，请他决定是**建单**还是按「无单工作」走（无单工作每人每日 ≤1 条，需组长当日确认）。
4. 截图里的口径**原样记下来**（后续做需求拆解时当输入），别自己润色。

**缺 需求 id 或 需求标题 → 先问，不编造，不跑 git。**

### 判定远程主分支 `<主分支>`

1. 读**当前 Git 仓根**的 `AGENT.md` / `CLAUDE.md` / `AGENTS.md`
2. `git symbolic-ref refs/remotes/origin/HEAD`
3. 远程 `main`，否则 `master`
4. 仍不确定 → 问用户

### 确认 Git 仓根

命令必须在**真正的 git 仓库根**执行。多仓工作区根不是 git 根时，先进入对应子仓。

### 撞名处理：**直接建，撞了就用已有的**（2026-09-21 用户口径）

**不要事先查**"是否已有同名分支 / 目录"，也**不要事先查文档约定**——**直接创建**：

| 情况 | 怎么做 |
|---|---|
| 创建成功 | 正常走完流程 |
| 创建失败（分支或目录已存在） | 说明**已有这条需求的分支**，**直接使用它**（`cd` 进已有 worktree，或切到已有分支），不覆盖、不追加序号 |
| 用户明确说"查一下是否已有该需求分支" | 才去查（`git branch -a` / `git worktree list`），然后按查到的结果汇报 |

理由：查重在正常情况下是多余的往返；`git worktree add` / `git branch` 撞名本来就会失败，**失败即信息**。
**永远不覆盖、不删已有分支 / 目录**（这是硬底线，失败后只做"复用"或"回报给用户决定"）。

## 模式 A：Worktree 并行（推荐）

```
fetch → worktree add -b --no-track → push -u → pnpm install → 起本地服务 → 给出进入路径
```

在**原仓根** `git fetch origin`（可选 `git fetch origin <主分支>:<主分支>`，失败只警告）。**不要** switch/stash 当前分支。

```bash
git worktree add "<worktree路径>" -b "<分支名>" "origin/<主分支>" --no-track
cd "<worktree路径>"
git push -u origin HEAD
pnpm install   # 不预检、装完不验证
```

**复用优先**：创建失败或发现同一需求已有 worktree（目录名含同一个 id）→ **直接复用该目录**，不要重复新建、不要改名。

### 汇报（Worktree）

```
已用 worktree 并行创建需求分支：

  branch:    <分支名>
  from:      origin/<主分支> @ <short-sha>
  upstream:  origin/<分支名>   （自己，不是主分支）
  worktree:  <工作目录相对路径，如 ./Apps/frontend/F-2792-效果图与转平台能力流程重构>
  进入:      cd ./Apps/frontend/F-2792-效果图与转平台能力流程重构
  （绝对路径：<绝对路径>）
  install:   pnpm install 已在工作目录执行（无报错则不再说明）
  server:    本地服务已启动（pm2 name=<U|F|D|S>-<id后4位>，地址见服务汇报）
  原工作区:  未改动；原窗口可继续跑 A
```

**进入路径怎么给**：
- 优先给**相对当前工作目录**的路径（能算出相对就给相对，短、好粘）；同时附一行绝对路径兜底。
- **分支名里的空白已被转成 `-`，所以 `cd` 那行没有空格、可以直接粘**。想更保险就加引号：`cd "./Apps/frontend/…"`。

### 收尾（仅告知）

```bash
git worktree remove "<worktree路径>"
```

## 模式 B：In-place（仅本仓切换）

仅当用户明确不用 worktree，且工作区允许时。

```
fetch → switch -c --no-track → push -u → pnpm install → 起本地服务 → 汇报
```

有未提交且检出会冲突 → **改走模式 A**，禁止 stash 强切。

```bash
git switch -c "<分支名>" --no-track "origin/<主分支>"
git push -u origin HEAD
pnpm install
```

汇报中注明：`工作目录: <仓根>`（没换目录）、`pnpm install: 已执行`、`server: 已启动`。

## 合并分支（To-test · 2026-10-06 建法 / 2026-10-09 一致性口径）

**目的**：测试分支禁直推，开发分支直接合入测试常撞冲突——先建一条**以测试分支为基地**的合并分支，把开发分支的改动合进来，冲突在这条分支上解决，再经合并请求进测试分支。

**全链路与核心不变量（最重要 · 2026-10-09 用户口径）**：

```
开发分支开发完成 → 合入测试分支发现冲突 → 合并分支合入、解冲突、进测试线
→ 测试通过验收 → 开发分支直接合入生产分支
```

生产分支收到的始终是**开发分支**（合并分支止步于测试线，不进生产）。所以核心不变量是：

> **测试线上验收到的本需求行为 = 开发分支后续进生产的行为。** 合并分支验收通过后，开发分支必须能不加改动直接合入生产；这条不成立，测试就白测了。

- **基地**：`origin/<测试分支>`（工厂端 `main-test`、灵创 `main_test`；按仓库实际判定，判断不了问一句）。
- **合入**：把需求（开发）分支 `merge` 进合并分支；冲突在合并分支上手工解决（手改纪律照 `解决合并冲突`；此处合并开发分支是本分支的既定目的，不算"为解冲突主动 merge 对方"的违规）。
- **行为一致性（硬规则）**：合并分支与开发分支对**当前需求**不得有行为差异——合并分支只是把开发分支改动带进测试分支的载体，不是二次开发的地方。解冲突只做"保留哪边 / 两边融合"的取舍，**不顺手改逻辑、不加需求外的改动**。取舍铁律：
  - **优先保留开发分支的行为**，适配只落在测试分支侧的代码上（不触及本需求代码，开发分支不用动）。
  - 解冲突一旦**动了本需求的行为**（落在哪边代码都算）→ 必须把这部分改动**同步回开发分支**提交推送，再回合并分支重新对齐，做到"测过的 = 要发布的"。
- **合入会破坏原行为 → 停下来，先与用户讨论（禁止自行裁决）**：若解冲突或适配测试分支代码时，无论怎么取舍都会破坏开发分支上的原行为，不要硬改。带着下面四个问题与用户讨论，达成一致后再动手：

  1. 是否需要修改**开发分支**的代码？
  2. 要怎么改动（具体方案）？
  3. 会对原需求造成什么影响？
  4. 是否会造成**需求行为漂移**（测试线上的行为与需求原意 / 开发分支不一致）？

  讨论结论若改了开发分支代码 → 改完提交推送（走 `生成提交`），再回合并分支重新合并对齐。
- **解完冲突的自检**：`git diff origin/<开发分支> HEAD`——这个 diff 里只应出现**测试分支侧的适配**；凡本需求自己的代码 / 行为有出入，都按上面两条处理（同步回开发分支）。
- **验收后进生产**：合并分支测试验收通过、且本需求改动已与开发分支一致（或已同步回开发分支）→ 开发分支**直接**合入生产分支，不再绕合并分支；合并分支本身不进生产。
- **命名**：`{U|F|D|S}-{短id后4位}-To-test`（端前缀判定同需求分支）；worktree 目录同名，落点照「worktree 建在哪」。
- **上游**：同需求分支——`push -u` 后上游是自己；**测试分支禁直推不变**，进测试走合并请求。
- **撞名**：同需求已有 To-test 分支/目录 → 直接复用，不加序号。

```bash
git fetch origin <测试分支>
git worktree add "<worktree路径>" -b "<合并分支名>" "origin/<测试分支>" --no-track
cd "<worktree路径>"
git merge --no-ff "origin/<需求分支>"   # 冲突在此手工解决
git push -u origin HEAD
pnpm install   # 不预检、装完不验证
```

汇报照 Worktree 模板，加一行 `based on: origin/<测试分支>` 与 `merged: origin/<需求分支>`（有冲突解了几个也写上）；解冲突动了本需求行为并已同步回开发分支的，汇报里写明同步了什么。

## 跨工具怎么做（打开新目录 / 并行开发）

| 工具 | 打开 worktree 目录 |
|---|---|
| **Cursor** | File → New Window → Open Folder，选 worktree 路径（或 `cursor <路径>`） |
| **VS Code** | File → Open Folder…，或终端 `code <路径>` |
| **JetBrains 系** | File → Open…，选 worktree 目录 |
| **命令行型 Agent（Claude Code / WorkBuddy 等）** | 不用"打开"——直接在对话里把工作目录指到 worktree 路径，或 `cd <路径>` 后继续 |
| **纯终端** | `cd <路径>` 即可 |

> 关键不是用哪个工具，而是：**A 在原目录继续，B 在新 worktree 目录里做**。

## 起本地服务（需求分支默认动作 · 细则见 `references/本地服务.md`）

需求分支走一条龙脚本时本步已由脚本完成；手走时在 `pnpm install` 后**随即起服务**：pm2 托管，进程名 `{U|F|D|S}-{id后4位}`，**端口 = 仓库位 + 需求 id 后 4 位**（U=1 / F=2 / D=3 / S=4，如 F-2962 → 22962）——从端口一眼看出哪个仓库的哪个需求，且对每个需求固定。快捷两步（算端口 → cd 到 worktree 根照模板一条命令起服务+取 IP，pm2/pnpm 写绝对路径 `~/Library/pnpm/…`；启动命令照模板抄、不由 agent 判断；不预先验占用，报错才处理），不做多余检查；端口规则、汇报格式、三个口令、node_modules 共享与坑**全部见本技能内附模块 `references/本地服务.md`**。

**合并分支不起服务**（To-test 用于合入解冲突，不本地调试；要起由用户点名，名字带 `-To-test` 后缀，端口规则同）。
