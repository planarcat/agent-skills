# 写 PRD（产品需求文档）

将口述/草稿/讨论整理为可评审、可开发的 **PRD**。本 skill **只写文档，不改代码**。

## 触发时机

- 「写 PRD」「补 PRD」「出需求说明」「写产品需求文档」
- 「把这个需求整理成文档」「按模板写一份需求」
- 用户给出功能描述并明确要 **需求文档 / PRD**（不是「讨论技术方案」）

## 与相邻 skill 的边界

| Skill | 何时用 |
|---|---|
| **本 skill** | 产出正式/半正式 PRD |
| `requirement-clarification` | 需求模糊、先澄清；澄清完成后再写 PRD |
| `user-story-acceptance` | 只要用户故事 + AC / 测试提纲，不要完整 PRD |
| `plan-discussion` | 技术方案多轮讨论，落 `Plans/` 主题与 execution-plan |
| `competitive-or-feature-brief` | 做不做、方案取舍简报，不是完整 PRD |

需求仍含大量「待确认」时：先走 `requirement-clarification`，或在 PRD 顶部保留「待确认」清单再写正文。

## 落盘位置

默认写入**当前工作区/项目根**：

| 场景 | 路径 |
|---|---|
| 独立产品文档、长期保留 | `Docs/PRD/YYYY-MM-DD-{中文主题简称}.md` |
| 已与某方案主题绑定 | `Plans/{主题文件夹}/PRD.md` 或 `Plans/{主题文件夹}/附件/PRD.md` |
| 用户指定路径 | 按用户路径 |

- 目录不存在则创建。
- 同名已存在：追加 `-2`、`-3`，或经用户同意覆盖。
- 对人可见标题与章节名 **默认中文**。
- ❌ 禁止写入 `Apps/` 下业务源码目录；❌ 禁止改 `.ts` / `.vue` / `.java` 等源码。

## 工作流程

1. **收集输入**：对话、截图说明、链接、既有 Docs/Plans；缺关键信息先短问（目标用户、成功标准、范围边界、依赖端）。
2. **判定依赖仓**（有多仓工作区时必填，未知标「待确认」）：
   - 来图 / 设计器 / 工厂端 / 后端
   - 或项目内等价产品边界
3. **起草 PRD**：按下方模板；未知项写「待确认」或「假设：…」，禁止编造已确认事实。
4. **落盘**并回复：文件路径 + 待确认摘要（若有）。
5. 用户未要求落盘时，可先在对话给出全文，并询问是否写入 `Docs/` 或 `Plans/`。

## PRD 模板（必须覆盖下列章节）

```markdown
# {需求标题}

| 项 | 内容 |
|---|---|
| 状态 | 草稿 / 评审中 / 已定稿 |
| 作者 | |
| 日期 | YYYY-MM-DD |
| 关联 | Issues / 设计稿 / 方案主题（可选） |

## 1. 背景

- 现状与痛点（谁、在什么场景、什么问题）
- 为何现在做（业务/合规/技术契机，可选）

## 2. 目标

- 可验证的产品目标（1～5 条）
- 成功指标（若有：指标名、口径、基线/目标）

## 3. 非目标

- 本次明确不做的事项（防止范围蔓延）

## 4. 用户与场景

- 角色
- 主路径 / 关键异常路径（简述）

## 5. 用户故事

- 作为 {角色}，我想要 {能力}，以便 {价值}
- 可附优先级 P0/P1/P2

## 6. 验收标准

- 每条故事对应可测 AC；推荐 Given/When/Then
- 禁止空话（如「体验好」「性能高」须量化或可观察）

## 7. 功能说明（可选展开）

- 页面/流程/规则/权限/文案要点
- 与现网差异（若有）

## 8. 埋点与数据

| 事件名 | 触发时机 | 属性 | 用途 |
|---|---|---|---|
| | | | |

无埋点需求时写：「本次不新增埋点」及原因。

## 9. 风险与开放问题

| 风险/问题 | 影响 | 缓解/负责人 | 状态 |
|---|---|---|---|
| | | | |

## 10. 依赖仓与协作

| 仓/端 | 是否涉及 | 改动摘要 | 依赖方 |
|---|---|---|---|
| 来图 | 是/否/待确认 | | |
| 设计器 | | | |
| 工厂端 | | | |
| 后端 | | | |
| 其他 | | | |

## 11. 里程碑（可选）

- 评审 / 开发 / 联调 / 上线
```

## 质量要求

- **目标 vs 非目标** 必须同时存在。
- **验收标准** 必须可演示或可自动化验证。
- **依赖仓** 表必填；单仓项目可合并为一行并注明仓名。
- 埋点：有数据诉求必填表；否则显式写不做。
- 不写实现细节代替需求（除非影响验收）；技术方案指向 `plan-discussion`。
- 引用代码/接口时注明路径或 API，避免臆造字段。

## 对话交付摘要（落盘后）

用简短列表回复：

1. 文档路径  
2. 范围一句话  
3. P0 故事数 / 主要依赖仓  
4. 仍待确认的事项（若有）
