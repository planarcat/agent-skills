# Record Development Blog

## 触发时机

当用户在开发过程中遇到相对复杂的问题或需求，并说出以下或相近表达时，使用本 skill：

- “记录这个问题”
- “记录这个需求”
- “把这个问题记录下来”
- “把这个需求记录下来”
- “将这个问题编成博客”
- “将这个需求编成博客”
- “将这个问题编成 blog”
- “将这个需求编成 blog”
- “整理成博客”
- “写成博客”

## 核心目标

把本次问题或需求相关的开发上下文保存到项目根目录的 `Blogs/` 文件夹下，形成一篇自然、可回顾、第一人称视角的 Markdown 记录。

## 保存位置

- 固定保存到当前项目根目录下的 `Blogs/` 文件夹。
- 如果 `Blogs/` 不存在，需要先创建。
- 文件名使用日期和简短 slug：

```text
Blogs/YYYY-MM-DD-short-topic.md
```

示例：

```text
Blogs/2026-05-30-product-work-api-debug.md
Blogs/2026-05-30-editor-save-requirement.md
```

## 写作要求

1. **第一人称记录**
   - 使用“我”来记录背景、思考、排查、取舍和结论。
   - 不要写成冷冰冰的第三方报告。

2. **语言自然**
   - 像开发日志或技术博客草稿，而不是机械的任务清单。
   - 可以保留真实开发过程中的不确定、尝试、判断和结论。

3. **上下文完整**
   - 记录问题/需求产生的背景。
   - 记录我当时看到的现象、涉及的文件、相关代码位置、接口、配置、报错、约束等。
   - 如果已经做了排查或实现，也记录过程和结果。
   - 如果还有未完成事项，明确写出后续计划。

4. **不改动业务代码**
   - 触发本 skill 时，除非用户同时明确要求开发或修复，否则只创建或编辑 `Blogs/` 下的 Markdown 文档。
   - 不要借记录博客的机会修改源代码。

5. **保留关键细节，但避免泄密**
   - 可以记录文件路径、函数名、接口名、错误信息和技术判断。
   - 不要写入明文密钥、token、密码、私有凭据等敏感信息。
   - 如果上下文包含敏感值，用 `<redacted>` 或“已脱敏”替代。

## 建议文档结构

每篇博客建议使用以下结构，可根据实际情况自然调整：

```markdown
# {问题或需求标题}

> 记录时间: YYYY-MM-DD HH:mm
> 项目: {项目名或路径}

## 背景

我是在什么场景下遇到这个问题/需求的，为什么需要记录它。

## 当时的现象或目标

如果是问题：我看到了什么异常、报错或不符合预期的行为。
如果是需求：我想达到什么目标，用户体验或业务上希望变成什么样。

## 相关上下文

- 相关文件：`path/to/file`
- 相关函数/接口：`functionName`
- 相关配置：`ENV_NAME`（敏感值需脱敏）
- 相关命令或日志：必要时摘录

## 我的分析过程

我如何理解这个问题/需求，排查了哪些方向，哪些判断被证明有效或无效。

## 当前结论

我目前得到的结论、决定采用的方案，或者已经完成的处理结果。

## 后续计划

- [ ] 还需要确认的点
- [ ] 还需要实现或验证的内容
```

## 操作流程

1. 判断用户是在要求“记录问题/需求”还是“写成博客”。
2. 收集当前对话、最近查看文件、相关代码、配置、报错和执行结果中的有效上下文。
3. 如果关键信息不足，先用简短问题向用户确认；如果上下文已经足够，则直接记录。
4. 在项目根目录创建 `Blogs/` 文件夹（如不存在）。
5. 创建一篇新的 Markdown 文件，使用自然第一人称写作。
6. 完成后告诉用户文件路径，并简要说明已记录哪些内容。

## 文件命名规则

- 日期使用当前日期：`YYYY-MM-DD`。
- slug 使用英文小写、数字和连字符。
- slug 应反映主题，避免过长。
- 如果同名文件已存在，在文件名后追加序号：`-2`、`-3`。

## 质量检查

写入前后检查：

- 是否保存在项目根目录 `Blogs/` 下。
- 是否使用第一人称。
- 是否语言自然，不像模板填空。
- 是否包含足够上下文，未来回看能理解当时发生了什么。
- 是否没有泄露敏感信息。
- 是否没有修改 `Blogs/` 以外的代码或文档，除非用户另有明确要求。
