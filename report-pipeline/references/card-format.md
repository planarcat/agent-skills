# 素材卡格式细则与样例

> 配合 `report-pipeline` 技能使用。本文件管"每张卡怎么填"。
> **最高原则同 SKILL.md：规范 > 用户口径 > 本文建议。** 任何字段设计与规范冲突，以 `report-writer/references/spec.md` 为准。
> **适用范围：本技能只写日报。**

## 一、当日文档骨架

路径（**跟着工作区走，技能目录只读**）：`<当前工作区>/.workbuddy/reports/cards/YYYY-MM-DD.md`

工作区里若有自己的规范指定了位置（`AGENTS.md` / `CLAUDE.md` / `README`），或已有 `.workbuddy/reports/`、`docs/reports/` 这类目录，按那个来；都没有才用上面的默认落点。目录不存在就创建。

```markdown
# 素材 · 2026-09-15（周二）

> 采集规则见 report-pipeline 技能。素材区只追加不重写；成稿区由汇总者生成。
> 规范提交时限：日报每日 21:00 前。

## 素材区

### [1] ...
（卡片正文）

### [2·卡点] ...
### [3·失误] ...

## 成稿区

> 由素材区归并生成。状态：草稿 / 待用户确认 / 已定稿。
（归并后的七模块日报，或留空）
```

**成稿定稿后归档**：把成稿区内容另存为 `<工作区>/.workbuddy/reports/daily/日报_YYYY-MM-DD.md`（该工作区若有自己的落点则按它的），**不迟于当日 21:00**。素材文档留在 `cards/` 不动，供事后回查。

## 二、字段填写细则

### 产出卡

| 字段 | 必填 | 规范依据 | 写法 | 常见错误 |
|---|---|---|---|---|
| `[N] 标题` | ✅ | 颗粒度红线（单日单元） | 一句话说清"做了什么"，白话 | 写术语（"重构 effectPicRecord"）→ 改"效果图记录模块调整" |
| `项目` | ✅ | 权责红线 | 用素材里已出现的项目称呼，不造新总名、不预设清单 | 自创总名（"XX 自动化铺货项目"） |
| `责任人` | ✅ | 责任内联铁律 | 真名；多人 `A+B`；本人默认在内 | 写"后端""平台端"角色归因 |
| `做了什么` | ✅ | 交付红线·执行内容 | 1~2 句白话，动作 + 关键判断 | 罗列字段名/文件路径 |
| `交付物` | ✅ | 交付红线·当日交付物 | 当日产出物 + 部署去向 | 写"推进中"（那不是交付物） |
| `交互结果` | ✅ | 交付红线·交互结果 | 交付给谁 / 谁可用 | 只写"改动已完成"，不写谁用得上 |
| `标准` | ✅ | 交付红线·量化质量标准 | 数字或可复现对比 | 写"测试通过"不给数 → 等于没标准 |
| `结果` | ✅ | 交付红线 | 成功 / 未完成(进度%) / 失败 | 只写"完成了"不给状态 |
| `交付状态` | ✅ | 进度可信度 | 已部署测试环境 / 已部署生产环境 / 未部署（**09-17 起**：只有「已部署生产环境」算完成） | 混用"已上线"（规范口径：已上线=生产环境） |
| `交付时间` | ✅ | 责任内联·交付:月-日 时:分 | 真实发生；拿不到时分只写月-日 | 编造时刻（踩真实红线） |
| `TAPD id` | ✅（开发性工作） | 追溯（09-17 口径：所有开发性工作、含沟通交流与检查类都要挂） | 数字 id；成稿放标题尾部括注 | 拿不到就编 id（宁可留空、问一句） |
| `偏差` | 有滞后必填 | §3.4 延期天数 | 【计划｜实际｜偏差 N 天｜原因｜影响】 | 写"略有滞后"不给天数 |
| `涉及` | ✅ | 权责红线 | 真名 | 角色归因 |
| `待确认` | 视情况 | 真实红线 | "等谁 + 确认什么"，一条一问 | 含混（"等确认"） |
| `原文` | ✅ | 事后追溯 TAPD 编号/分支动作 | 用户口述原样抄，**不去噪** | 提前去噪删掉编号/术语，事后要回查就没了 |

### 卡点卡

| 字段 | 必填 | 规范依据 |
|---|---|---|
| `分类` | ✅ | §5 卡点栏（技术/对接/需求/资源） |
| `需协助` | ✅ | 同上 |
| `对接人` | ✅ | 权责红线（真名） |
| `期望解决` | ✅ | 同上（月-日 时:分 / 暂无确定日期） |
| `影响` | ✅ | 同上（影响天数或范围） |

### 失误卡

| 字段 | 必填 | 规范依据 |
|---|---|---|
| `描述` | ✅ | §3.6 四要素 |
| `影响等级` | ✅ | §3.3 P0~P3 |
| `责任人` | ✅ | §3.6 |
| `根因` | ✅ | §3.6 |
| `已修复` / `回归` | ✅ | §3.3 五要素 |
| `时间浪费` | 有则必填 | §3.5（N 人时｜来源｜归属） |

## 三、正例（照着这个填）

> ⚠️ 示例里的项目名（订单中心）是**虚构占位**。实际填写一律取当天素材里的称呼，不要照抄这里的名字。

```markdown
### [1] 上架客户端打包工具统一换成 Bun，代码检查首次全部通过

- 项目: 订单中心
- 责任人: 何成标
- 做了什么: 打包工具从两套包管理方式统一换成 Bun，流程里加了一道"检查不过就不打包"的门禁，顺带清掉攒了九天的 7 处代码检查报错。
- 交付物: 重新打包的上架客户端程序
- 交互结果: 客户端可直接安装使用（未走部署流程，本机实测通过）
- 标准: 代码检查全部通过；完整打包链路一次走通并能自动替换旧程序
- 结果: 成功
- 交付状态: 未部署
- 交付时间: 09-14 19:00
- 涉及: 何成标
- 待确认: —
- 原文: 打包工具统一 bun，lint 首次全绿，加 gate，清了九天积压的 7 个 lint error；整条打包链路跑通，能自动替换旧 exe。没走部署流程。
```

**为什么合格**：字段齐、状态明确（未部署 → 归并时标"（未完成，未部署）"）、标准是数字、交互结果写了"谁可用"、原文保留了 `lint`/`exe` 供事后回查。

## 四、反例（两头顶）

### 反例 A：太细（把过程日志搬进来）

```markdown
- 做了什么: 修改 tauri.conf.json 第 42 行，把 beforeBuildCommand 从 pnpm 改成 bun，
  新增 scripts/gate.mjs，调用 eslint --max-warnings 0，清理了 7 个错误分别在
  src/views/a.vue:13、src/views/b.vue:88…，提交记录 3f2a1b9，已 push 到 feature/lint-gate 分支。
```

✗ 三宗罪：① 文件路径、行号、commit hash、分支名——汇报全禁，成稿还得删；② 没有结果与交付状态，不知道算不算完成；③ 没有可验收结论（"7 个错误"是过程，结论是"检查全绿"）。

### 反例 B：太糙（等于没记）

```markdown
- 做了什么: 优化了打包
- 结果: 完成
- 证据: —
```

✗ 三宗罪：① 无数字无对比，违反交付红线（无量化标准），成稿时写不出"标准:"；② "完成"不给交付状态，归不了模块，也定不了标题占比；③ 原文缺失，隔天想不起改了什么，只能回头翻聊天记录。

### 反例 C：字段漏（成稿时只能编）

```markdown
- 做了什么: 工厂账号预充值一期做完
- 结果: 成功
```

✗ 漏 `交付状态`/`责任人`/`交付物`/`标准` → 成稿时"算产出还是进行中"说不清、"标准"写不出 → 只能猜 → 猜就踩真实红线。**字段漏比文字糙更危险。**

## 五、多 agent 场景示例

> ⚠️ 同上：项目名是虚构占位（订单中心 / 会员中心），实际以当天素材为准。

三个 agent 并行作业，各自往同一个当日文档 append：

```markdown
## 素材区

### [1] 工厂账号预充值一期：列表加余额列与充值入口
- 项目: 订单中心
- 责任人: 何成标+张昆
- 做了什么: 工厂列表加"账号余额"列和"充值金额"入口，按授权字段控制显隐。
- 交付物: 一期改动
- 交互结果: 复核通过后供工厂账号使用
- 标准: 有权限无值显示 0、无权限显示"-"；负数场景两处显示均正确
- 结果: 未完成(60%)
- 交付状态: 未部署
- 偏差: —
- 涉及: 何成标、张昆
- 待确认: 两个后端接口路径待张昆确认
- 原文: （agent-A 原始记录）

### [2] 后台列表页弹窗第三轮迭代
- 项目: 会员中心
- 责任人: 何成标
- 做了什么: 文案错字全部修正、输入框改默认单行 + 自动增高、修掉内容过长撑破容器。
- 交付物: 弹窗改动
- 交互结果: 客服与运营可直接使用
- 标准: 文案无错字；输入框默认单行、长内容自动增高且不撑破容器；全选替换粘贴结果正确、不回退成追加
- 结果: 成功
- 交付状态: 已部署测试环境
- 交付时间: 09-14 19:00
- 涉及: 何成标
- 待确认: —
- 原文: （agent-B 原始记录）

### [3] [状态更新] 引用 #1 —— 充值一期并入二期一起提测
- 项目: 订单中心
- 做了什么: 与张昆确认后，一二期合批，减少一次提测。
- 结果: 未完成(80%)
- 交付状态: 未部署
- 证据/标准: 两期改动合并后本机自测通过
- 涉及: 何成标、张昆
- 待确认: 后端接口路径仍未给
- 原文: （agent-A 补充记录）
```

归并时：`#1` 与 `#3` 是同一事项 → 取 `#3` 的最新状态（80%），内容累加；`#2` 独立成条；`#1/#3` 的 `待确认` 合并后升格为"三、卡点"一条（分类:对接 + 需协助:是 + 对接人:张昆 + 期望 + 影响）。

**关键点**：agent-A 没有回去改 `#1`，而是追加 `#3`。这样 `#1` 当时的状态永远可查——事后复盘"什么时候判断失误"时有据可依（对齐真实红线：进度变化要如实留痕）。

## 六、归并成稿的动作序列

```
1. 读当日素材文档全部卡片
2. 按「事项关键词重合」分组去重 → 同组取最新状态、内容累加
3. 每张卡按「结果 + 交付状态 + 卡型」查表落模块（见 SKILL.md 第四节映射表）
4. 卡点项补齐：分类 + 需协助 + 对接人 + 期望时间 + 影响
5. 产出项补齐：责任内联 + 交付物 + 交互结果 + 标准
6. 跑 report-pipeline 第六节机械自检（10 条，对齐五大红线）
7. 交 report-draft-filter 去噪 → report-writer 套模板
8. 写入成稿区 → 用户确认 → 另存为 `<工作区>/.workbuddy/reports/daily/日报_YYYY-MM-DD.md`（不迟于 21:00）
```

第 2 步是唯一需要判断的一步，其余都是机械映射。**判断只在"这两张卡是不是同一件事"上发生**，不在"该不该写"上发生——该不该写由 `report-draft-filter` 决定。
