# Report Pipeline（报告编写流水线 · 采集与归并）

## 最高原则：规范 > 一切

**《日_周_月报统一内容标准与管理规范（v2 · 错误强化·考核联动版）》是本技能、以及所有报告动作的最高标准。** 三级效力：

1. **规范**（最高）——`report-writer/references/spec.md`。五大红线、责任内联铁律、错误量化口径（3.1~3.6）、提交时限，不可因为"方便采集"而打折。
2. **用户口径**——何成标的历次裁定（术语白化、POD 压缩、失误栏口径等），仅在规范未覆盖处生效。
3. **本技能的设计建议**（节奏、字段、提问时机）——**只是实现规范的手段**。与规范冲突时一律作废，以规范为准。

**判据**：本技能任何一条规则被质疑，先回查规范原文；查不到依据的，退位让行。

## 适用范围（用户口径，2026-09-15 确认）

本技能只覆盖两类产出：

| 产出 | 载体 | 提交时限（spec §4） |
|---|---|---|
| **日报** | 工作区 `日报_YYYY-MM-DD.md` | 每日 21:00 前 |
| **周评** | 《周评绩效考核表》第一部分（**替代本周周报**） | 每周六 21:00 前 |

- **不写月报**。规范 §7 的月报条款作为存档依据保留，本技能不触发；若后续需要，回 `report-writer/references/spec.md` §7 补齐。
- 周评 ≠ 换个名字的周报：它同时是考核表的第一部分，**§2 项目进度排期跟进（含偏差天数）、§4 失误与影响汇总**是主管打分直接用的块，采集时不能漏。周评中「二~五部分」由主管/HR 填，**AI 一律不碰**。

## Overview

一句话：**规范要求填报的东西，必须在它发生时就被记下来——因为大部分是事后无法重建的。**

三层分工，本技能只管第一层：

| 层 | 技能 | 管什么 |
|---|---|---|
| 采集 | **report-pipeline（本技能）** | 什么时候记、记什么、谁提供、记多细 |
| 分拣 | `report-draft-filter` | 哪些写进汇报、哪些剔除、怎么归类合并 |
| 成型 | `report-writer` | 汇报长什么样、责任内联、红线自查 |

## 一、三个设计问题的结论

### 结论 1：节奏由规范的提交时限倒推——三拍

节奏**不是自选的**。规范 §4 定了提交时限与颗粒度要求，采集节奏必须与之一一对应：

| 规范要求（spec §4） | 倒推出的采集动作 |
|---|---|
| 日报：**每日 21:00 前**提交，颗粒度=纯单日任务 | 单日内**边做边落卡**，21:00 前归并成稿 |
| 周报：**每周六 21:00 前**提交，颗粒度=100% 拆解到每日 | 周六从本周已定稿日报 + 素材卡抽汇总，写成周评第一部分 |

落成三拍：

| 拍 | 触发 | 动作 | 产物 |
|---|---|---|---|
| ① 落卡 | 每完成一个阶段性工作（一段改动跑通、一次排查收口、一次会议出结论） | 往当日素材文档 append 一张素材卡 | 当日素材文档 |
| ② 归并 | 当日结束 / 用户说"出日报" | 素材卡 → 七模块草稿 → 用户确认 → **不迟于当日 21:00 交付** | 当日日报 |
| ③ 汇总 | 周六 | 本周已定稿日报 + 素材卡 → 周评第一部分（**周六 21:00 前交付**） | 周评 |

**为什么否掉"每份工作一份总结"**：规范红线=颗粒度最小单元为 1 天、禁止跨天模糊。碎片化的多份单事项总结既不是"单日任务"，也不构成单日视图，归并时极易产生"已部署"与"待提测"并存的矛盾（违反真实红线，`report-writer` 不得不专设"联动清理规则"来兜）。

**为什么否掉"末尾一次性回忆"**：规范要求"所有任务必须四要素齐全：执行内容 + 当日交付物 + 交互结果 + 量化质量标准"（交付红线），又要求周评必填偏差天数、返工率、时间浪费（spec §3.2~3.5）。**这些数字事后无法重建**——"146 项测试通过""14.7 秒""145→144""计划 09-10 / 实际 09-11"当天不记、隔天必忘。末尾一次性回忆等于注定写不出合规汇报。

### 结论 2：直接更新综合文档可以，但必须双区分离 + 只追加不重写

```
当日文档
├── 【素材区】append-only      ← 所有 agent 只往这里追加，不改已写的
└── 【成稿区】可整段重生成      ← 只有汇总者能写，每次由素材区重新生成
```

护栏原因，两条都指向规范红线：

- **只 append 不 rewrite** → 保"真实红线"（进度、问题、卡点、错误全部真实且可追溯）。反复改写会丢上下文、口径漂移；用户会直接手改日报文件（09-14 实证），重写会吃掉用户修改。
- **双区分离** → 保"交付红线"。素材区保留原始信息（含需求编号、分支动作），成稿区才是去噪成品。需求编号这类"日报不写但周评要填"的信息，只能靠素材区留底——与周评"下周计划 100% 拆解至单日并填写 TAPD"的做法一致。

### 结论 3：格式——字段齐（规范硬要求）＋ 文字薄（不写实现细节）

不是"越丰富越好"，也不是"一步到位写最终格式"：

- **字段一个不少**：素材卡必须携带规范要求的所有数据点（四要素 + 责任内联 + 错误量化字段）。因为成稿是机械映射，卡里没有的字段成稿时只能编——编就踩红线。
- **文字尽量薄**：只留 1~2 句白话和可验证数字，不搬实现细节。日报明令禁字段名 / 文件数 / 毫秒数 / 轮次 / git 动作；素材阶段写了，成稿还得删，白费工还污染归并。
- **一步到位写最终格式 ✗**：阶段完成时还不知道它会归到哪个模块（很可能从"进行中"变"产出"）；多 agent 并行时也没法拼装、排序、去重。

**一句话**："薄"指文字量，不指字段量。

## 二、素材卡格式

完整样例、正反例、多 agent 示例见 `references/card-format.md`。

### 2.1 产出卡（默认卡型）

字段按规范四要素 + 责任内联 + 周评量化口径设计：

```
### [N] 一句话标题
- 项目:
- 责任人:（默认含本人；多人写 A+B）
- 做了什么:          ← 执行内容
- 交付物:            ← 当日交付物
- 交互结果:          ← 交付给谁 / 谁可用
- 标准:              ← 量化质量标准（可验收）
- 结果: 成功 / 未完成(进度%) / 失败
- 交付状态: 已部署测试环境 / 已部署生产环境 / 未部署 / 未进入主版本
- 交付时间: 月-日 时:分（拿不到时分只写月-日，绝不编造）
- 偏差:【计划:月-日｜实际:月-日｜偏差:N天｜原因:｜影响:】  ← 有滞后才填，周评 §2 必填项
- 涉及: 人名
- 待确认: 等谁 + 确认什么；没有就留 —
- 原文: 用户口述原样抄，不去噪、不改写
```

**三条硬要求**：

1. `结果` + `交付状态` 必须给——决定成稿进"产出"还是"进行中"，也决定标题占比标注（`（100%）/（100%，未部署）`）。漏了就违反交付红线。
2. `标准` 必须有数字或可复现对比——它是规范"量化质量标准"的落地；写不出来的，说明这件事还不足以上报（补证据，或降级为"进行中"）。
3. `原文` **原样保留，不去噪**——术语、编号、分支动作都留着。去噪是 `report-draft-filter` 的活，不是采集的活。

### 2.2 卡点卡

规范要求卡点必带"分类 + 是否需协助 + 对接人 + 期望解决时间 + 影响"，采集时就按这个结构记：

```
### [N·卡点] 一句话
- 项目:
- 分类: 技术 / 对接 / 需求 / 资源
- 需协助: 是 / 否
- 对接人: 真名（不写"后端/平台端"）
- 期望解决: 月-日 时:分 / 暂无确定日期
- 影响: 对进度的影响天数或范围
- 待确认: —
- 原文:
```

### 2.3 失误卡（仅限"已交付后出现的问题"）

规范 §3.6 失误四要素 + §3.3 Bug 五要素，采集时一次记全，规避周评"重复回溯"：

```
### [N·失误] 一句话
- 描述:
- 影响等级: P0 / P1 / P2 / P3
- 责任人:
- 根因:
- 已修复: 是 / 否
- 回归: 有 / 无
- 时间浪费: N 人时｜来源:返工/卡点空等/方案反复｜归属:责任人
- 发生时间: 交付后 / 已上线
```

**准入门槛（不满足就建产出卡，不建失误卡）**：只有"交付后出现 / 影响使用"的问题才进失误卡。开发过程中复查发现并修复的问题属正常闭环，不进失误卡、也不进产出（09-01 口径）。反之，已交付功能的问题一旦载入"异常与协调"，失误栏必须同步补 Bug 行——否则触发规范 §9「填无但暴露问题＝虚报」。

### 2.4 状态更新卡

```
### [N] [状态更新] 引用 #X —— 一句话
（同样字段，只填变化的）
```

见第四节"状态跃迁规则"。

## 三、哪些必填、哪些尽量填、谁提供、何时问

### 3.1 信息分层（按规范归位）

| 层 | 内容 | 规范出处 | 谁填 | 时机 |
|---|---|---|---|---|
| **L1 硬事实**（必填） | 执行内容、交付物、交互结果、量化标准、责任人、项目 | 五大红线（交付/权责） | agent 自查直填 | 阶段完成即时 |
| **L2 归属判断**（必填，需确认） | 算不算"已完成/已上线"、算不算失误、落哪个模块 | 真实红线 + §3.6 | agent 给候选，用户点头 | 即时确认；批量项可留到出稿 |
| **L3 外部事实**（必填，agent 拿不到） | 真实部署状态、真实交付时刻、Bug 等级、偏差天数、返工原因、时间浪费、对接人期望时间 | §3.1~3.5 | 只能用户提供 | 出稿时批量问 |
| **L4 规范鼓励**（尽量填） | 技术/方案沉淀、亮点与不足、复盘、流程优化建议、风险预判 | 周评 §5/§6/§9 块 | agent 可写 | 出稿时 |

- **必填核心五件套**（缺任一不能成稿）：谁 · 做了什么 · 交付了什么 · 怎么验证 · 什么时候。
- **尽量填**：沉淀、亮点、复盘、风险。周评把它们列为独立块（§5 技术/方案沉淀、§6 亮点与不足、§9 个人复盘），属于"鼓励暴露"，填了得分。
- **可以缺省**：精确到分的时刻（拿不到就写到日期）、非关键过程细节。

### 3.2 什么时候找用户

| 时机 | 问什么 | 为什么是这个时机 |
|---|---|---|
| **即时问**（不能等） | ① 这件事算完成/上线了吗？② 这算失误吗？ | 这两条直接决定模块归属与失误栏写法（规范核心块）。错了要重排整篇，晚问等于白写 |
| **攒批问**（出稿时一次问完） | 时分精度、对接人姓名、Bug 等级、偏差天数、时间浪费、期望解决时间、给人看的口径 | 不影响结构，攒一批一次问，少打扰用户 |
| **不问** | 模块名、测试结果、耗时、失败项、代码事实；本地环境维护类操作（工作区改名、本机配置调整等） | agent 能从环境/上下文拿到，问就是偷懒；本地维护类按用户口径不进汇报 |
| **不问也不编** | 拿不到的真实时刻 | 降精度写（只写日期），**绝不编造**——规范真实红线优先于格式完整 |

**铁律：能自己查证的不问；只有"环境外事实"和"口径判断"才问用户。** 拿不到就说拿不到。

## 四、素材卡 → 七模块日报（机械映射）

| 素材卡状态 | 落到日报 |
|---|---|
| 结果=成功 且 交付状态=已部署测试/生产环境 | 一、产出 |
| 结果=未完成 / 成功但未部署 | 二、进行中 |
| 卡点卡 | 三、卡点（点名到人） |
| 失误卡 | 四、失误与影响 |
| 涉及多人 / 会议 / 方案变更 | 六、异常与协调 |
| 下一步动作 | 五、明日计划 |
| 复盘、沉淀 | 七、个人复盘 |

映射后仍须两道：先 `report-draft-filter` 去噪归类，再 `report-writer` 套模板 + 责任内联 + 红线自查。

**周评映射（周六汇总时用）**：本周全部日报 + 素材卡 →

| 周评块 | 素材来源 |
|---|---|
| §1 本周工作复盘（逐日核对完成率） | 本周各日报产出/进行中条目，按项目维度归组 |
| §2 进度排期跟进（含偏差天数） | 素材卡 `偏差` 字段（计划｜实际｜偏差 N 天｜原因｜影响） |
| §3 卡点汇总（区分已解/未解） | 卡点卡（含 `分类` 与状态） |
| §4 失误与影响汇总 | 失误卡 → 返工率 / Bug 清单 / 延期合计 / 时间浪费（§3.2~3.5） |
| §5 技术/方案沉淀、§6 亮点与不足 | 各日报第七节复盘中筛 |
| §7 下周计划（拆到单日 + TAPD） | 素材卡 `原文` 里的需求编号 + 各日报明日计划的未完成项 |
| §8 需协调与帮助 | 未解卡点卡的 `对接人 + 期望解决` |
| §9 个人复盘 | 各日报第七节复盘，做周度归并 |

**状态跃迁规则**：素材卡写出去后**不改**。同一事项有了新状态 → 追加一张 `[状态更新] 引用 #N` 卡。成稿时**同一事项取最新状态，其余内容全部累加**——不许"后发覆盖前发"，只有同一事项的状态冲突才以新为准（对齐规范的"如实暴露 + 持续闭环"：状态变化本身就是要留痕的事实）。

## 五、多 agent 并行规则

1. **只有汇总者能写成稿区**，其他 agent 只往素材区 append。
2. **只 append 自己的卡，不改别人的卡**（也不回头改自己已写好的卡——要更新就追加状态更新卡）。
3. 同一事项多个 agent 都记了 → 成稿时按「标题关键词重合」去重合并，不拆碎（对齐"同一事项合并成一条"）。
4. 冲突处理顺序：状态冲突取最新 → 事实冲突以有证据的一方为准 → 仍冲突则标 `待确认`，问用户。
5. 多 agent 并行作业时**各记各的，不要互相等**；归并是最后一步的事。
6. 上下文丢失的场景（额度限制降级、会话中断）优先保住素材区，它是最难重建的部分。

## 六、机械自检（归并前必跑）

逐条对齐规范五大红线与核心块：

| # | 自检项 | 对应规范 | 不通过怎么办 |
|---|---|---|---|
| 1 | 每张卡 `责任人` 非空，多人写 A+B | 权责红线 / 责任内联铁律 | 补责任人；补不出就问用户 |
| 2 | 每张产出卡 `交付物 + 交互结果 + 标准` 三行齐 | 交付红线（四要素） | 补；补不出把该卡降级为"进行中" |
| 3 | 每张卡 `结果` + `交付状态` 非空 | 交付红线 / 进度可信度 | 即时问用户 |
| 4 | 涉及部署/交付的卡，`待确认` 已被用户答复 | 真实红线 | **没答复的不许写成"已部署"** |
| 5 | `偏差` 字段：凡有滞后必带"计划/实际/偏差 N 天/原因/影响" | §3.4 延期天数 | 缺天数不许写"略有滞后" |
| 6 | 失误卡五要素齐（描述/等级/责任人/已修复/回归） | §3.3 + §3.6 | 缺等级不许写"有 bug 已修" |
| 7 | 每张卡 `证据` 是数字或前后对比 | 交付红线量化标准 | 补证据或降级 |
| 8 | `原文` 字段存在且未被去噪改写 | 周评 §7 需回溯 TAPD 编号等 | 从上下文恢复 |
| 9 | grep `待填\|待你\|拍板` 无命中 | 真实红线（禁占位） | 补问用户，不许留占位进成稿 |
| 10 | grep `正常推进\|一切正常\|暂无问题` 无命中 | §9 敷衍话术闸门 | 改写成具体状态 |

- `references/card-format.md` — 素材卡完整样例、正反例对照、字段填写细则、多 agent 场景示例、当日文档骨架、归并动作序列。
- `scripts/export-portable.py` — **移植导出脚本**。把三层技能打包成可移植版（单文件通用版 + 技能压缩包 + 移植说明），重新运行即重新生成，不手写副本。用法：`python3 scripts/export-portable.py [-o 输出目录] [--merge AGENTS.md] [--lite]`。技能源目录从脚本自身位置推导（换机器不用改路径），默认输出到当前目录 `./report-skill-portable/`。

## 整套技能的文件清单（移植时按此核对）

| 层 | 技能 | 文件 | 必需 |
|---|---|---|---|
| 规范（最高标准） | report-writer | `references/spec.md` | ✅ |
| 采集 | report-pipeline | `SKILL.md`、`references/card-format.md` | ✅ |
| 分拣 | report-draft-filter | `SKILL.md`、`references/gather-to-draft.md` | ✅ |
| 成型 | report-writer | `SKILL.md`、`references/templates.md` | ✅ |
| 工具 | report-pipeline | `scripts/export-portable.py` | ⭕ 仅移植时需要 |

共 8 个文件，全为纯 Markdown + 一个零依赖 Python 脚本；无外部服务、无网络、无第三方库。
唯一的外部约定是存放路径（素材卡 `.workbuddy/reports/cards/`、日报 `日报_YYYY-MM-DD.md`）与写死的人名/项目名——移植到别的机器或给别人用时必须替换。

## 与其他技能的关系

- `report-pipeline`（本技能）：采集层，管"什么时候记、记什么、谁提供"。
- `report-draft-filter`：分拣层，管"哪些写、哪些剔除"。
- `report-writer`：成型层 + **规范原文载体**（`references/spec.md`），管"汇报长什么样、命中哪条红线"。

三者不重叠：本技能不产出汇报正文，只产出素材卡；一切格式与口径冲突回 `report-writer/references/spec.md` 裁定。
