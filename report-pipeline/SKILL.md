# Report Pipeline（共享日报 · 采集与共写）

## 最高原则：规范 > 用户口径 > 本技能建议

1. **规范**（最高）——`report-writer/references/spec.md`（v3.1，飞书 rev 67）**（同仓库/同组内有效；单独搬走本技能时以自带 `references/` 为准，建议与 `report-writer` 整组移植）**。内容质量的全部硬要求——TAPD 对齐、四要素、虚报双向红线、敷衍话术禁令——出自它，不打折。
2. **用户口径**——何成标的历次裁定。其中 **2026-09-22 共享日报口径是落盘与协作方式的最新安排**（下一节），覆盖旧的两拍节奏、素材卡体系与成稿落盘；其余口径（零注入、白话表述、不写 AI 旁白等）继续生效。
3. **本技能的设计建议**——只是实现手段，与上两者冲突时一律作废。

**判据**：任何一条规则被质疑，先回查 v3 规范原文与本口径；查不到依据的，退位让行。

## 共享日报口径（2026-09-22 用户拍板，本技能的核心）

1. **落盘**：`<工作区根>/Reports/daily_work/YYYY-MM-DD.md`。目录不存在就创建，不用问。
2. **每日一份**：一个工作区一天只有这一份日报文件。**不建素材卡、不另存成稿**——所有更新都发生在这份文件上。
3. **所有 agent 共写**：在同一工作区干活的每个 agent 会话，都直接在这份文件上更新**自己会话**的工作内容。
4. **以工作分支为维度**：一个工作分支一个小节。同一分支的多个会话（如 A 开发登录模块、D 在 A 基础上继续）**共同维护该分支的「工作总结」**；不同分支的会话（B 修 bug、C 加强密码校验）**各自维护自己的小节**。
5. **边界**：只更新自己会话的记录与自己在总结里相关的句子；**不重排、不删改、不"顺手规范化"他人的内容**。
6. **时间要素（2026-09-22 补充）**：每条工作节点都带 `[HH:MM]`（取记录时刻）——工作总结的句子、会话记录里的工作节点、卡点 / 异常 / 明日 / 复盘条目，一个不漏。同分支 A、D 共写同一份总结时，靠时间戳排序与归属，谁在什么时候做了什么一目了然；不带时间的条目一律补齐。

> 旧机制（素材卡 append-only → 次日 09:30 归并素材 → 五栏成稿另存）自本口径起作废。v3 规范的**内容要求**（TAPD 对齐、四要素、差异、协同人、卡点、时限）全部保留，只是承载结构换成共享日报。

## 数据存放位置（跟着工作区走，技能目录只读）

- 共享日报落在**产生这份工作的工作区**根目录；哪份工作属于哪个工作区，数据就落在那个工作区。
- 工作区里已有更明确约定（`AGENTS.md` / `CLAUDE.md` / README 指定了汇报目录）→ 按它的来；用户点名了别的路径 → 按用户的来；都没有 → 用默认落点。
- 工作区在 git 仓库里 → 提醒用户自行决定是否把 `Reports/` 加进 `.gitignore`。
- 旧版数据（`.workbuddy/reports/`、工作区根 `日报_YYYY-MM-DD.md`）不迁移；发现历史文件当素材读，不擅自搬动。

### 跨工作区怎么收齐

① 当前工作区 → ② 本次会话里出现过代码 / 文件路径的工作区 → ③ 日报工作区的 `sources.md`（可选清单，没有就跳过） → ④ 仍缺就问一句"今天还在别的哪个目录干过活？"——问一次记进 `sources.md`，以后不必再问。**找不到就说找不到**，不得用别的日期或别的事项顶替。

## 文件骨架（当日文件不存在时，按此创建）

```markdown
# 日报 YYYY-MM-DD · <工作区或项目名>

> 共享日报（2026-09-22 口径）：本工作区当日唯一日报，所有 agent 会话直接在本文件更新自己会话的工作内容。
> 只更新自己的会话块与自己相关的总结句；不重排、不删改他人内容；写入前先重读最新文件；**每条工作节点带 `[HH:MM]` 时间**。

## 今日总览
（收口时由 report-writer 汇总各分支小结填写；平时留空）

## 分支：<分支名>（#<TAPD ID>）
### 工作总结
- [HH:MM · <agent 名>] <一句话；按时间先后排列；只增/改自己会话相关的句子>

### 会话记录
#### <agent 名·HH:MM>（会话标识）
- 任务: #<TAPD ID> <任务名>（拿不到 → 无单工作）
- 工作节点:
  - [HH:MM] <一条进展 / 动作>
- 交付物/标准:
- 执行差异: 待确认
- 协同人: —
- 原文:

## 卡点与阻碍
## 异常与需协调
## 明日计划
## 复盘
```

## 会话标识（首次写入前定好，全天不变）

- 格式：`<agent 名或工具名>·<当日首次写入时刻 HH:MM>`；同 agent 同分钟冲突 → 尾加 `-2`、`-3`。
- 同一会话后续所有更新**沿用同一标识**定位自己的会话块；换了会话就是新标识、新块。

## 更新动作（阶段完成即更新）

1. **读最新文件**：文件不存在 → 按骨架创建；存在 → 以文件现状为准（用户可能刚手改过），编辑锚点不凭记忆。
2. **定位分支小节**：以当前 git 分支为准；拿不到分支 / 非代码工作 → 用工作项名，取名拿不准问一句。小节不存在 → 在「卡点与阻碍」小节**之前**插入新分支小节，既有小节顺序不动。
3. **更新会话记录**：在自己的会话块里追加 / 修改本条记录（块不存在先建）；**每个工作节点带 `[HH:MM]`**；字段见下。
4. **更新工作总结**：把自己会话的工作补进本分支「工作总结」——句子格式 `- [HH:MM · <agent 名>] 内容`，**按时间先后插入**；只增 / 改与自己会话相关的句子；他人写的句子一字不动。
5. **工作区级小节**：卡点 / 异常 / 明日 / 复盘有内容就追加，条目格式 `- [HH:MM · <agent 名>] 内容`；无卡点不写（收口时统一判「无」）。
6. **收尾**：不做全文重排、不做格式"顺手统一"——那是收口层（report-writer）的事。

### 会话记录块（字段即 v3 必填数据点）

```markdown
#### <agent 名·HH:MM>（会话标识）
- 任务: #<TAPD ID> <任务名>（拿不到 → 写「无单工作」并说明；ID 不许编）
- 工作节点:
  - [14:05] <一条进展 / 动作，禁"继续开发/按计划推进">
  - [16:20] <下一条>
- 交付物/标准: <当日交付物 + 量化标准>
- 执行差异: 一致 / 提前N天 / 滞后N天 / 阻塞 / 与TAPD不符 / 待确认
- 协同人: <owner 非本人必填（姓名+角色）；无则 —>
- 原文: <口语原样抄，不去噪、不改写>
```

硬要求（沿 v3，一条不能少）：

1. TAPD ID 拿不到就问一句或标「无单工作」（无单工作每人每日 ≤1 条，需组长当日确认），**不许编**；
2. `执行差异` 必须有值，判不准写「待确认」；
3. `协同人`：owner 不是本人时必填，空置扣分（v3 §8.2 红线）；
4. 四要素（工作节点 / 交付物 / 交互结果 / 量化标准）写全，写不出交互结果就写清"谁下一步能用"；
5. `原文` 原样保留——去噪是 report-draft-filter 的活。
6. **每个工作节点带 `[HH:MM]` 时间要素**——共写的排序与归属靠它，不许省略；时间取记录时刻（24 小时制）。

## 时间要素（2026-09-22 补充 · A / D 共写防混乱）

每个工作节点都带 `[HH:MM]`（24 小时制，取记录时刻）。三个位置的格式：

| 位置 | 格式 |
|---|---|
| 工作总结的句子 | `- [HH:MM · <agent 名>] 内容`（agent 名同名多会话时加 -2 / -3 后缀） |
| 会话记录里的工作节点 | `- [HH:MM] 内容`（来源由所在块标明） |
| 卡点 / 异常 / 明日 / 复盘条目 | `- [HH:MM · <agent 名>] 内容` |

- **排序**：工作总结与各条目一律按时间先后排列；更新时插到正确的时间位置，不改他人句子的时间。
- **归属**：同分支 A、D 共写同一份总结——时间戳看「什么时候」，agent 名看「谁写的」，读的人不用猜新鲜度，写的人不用争先后。
- 会话记录块标题里的 `HH:MM` 是**会话首次写入时间**（会话标识的一部分，用于定位块），与逐条节点时间不是一回事，别混用。

## 多 agent 共写规则（并发安全）

1. **先读后写**：每次更新前重读文件最新内容；只做局部编辑，不整文件重写。
2. **各记各的，不互相等**，也不用协调先后。
3. **小节顺序不可重排**；新分支小节一律追加在既有分支小节之后。
4. **冲突处理**：状态冲突取最新 → 事实冲突以有证据的一方为准 → 仍冲突标「待确认」，收口时问用户。
5. 同分支多会话的「工作总结」出现重复表述 → 平时不互相删改，收口时由 report-writer 合并。
6. 会话中断 / 额度降级场景：优先保证自己会话块已落盘，收口时标注缺口。

## 零注入：采集是报表侧的事，不指挥开发过程（2026-09-21 口径，继续生效）

- 开发技能里不许写日报内容（不写"为了日报要怎样"、不写"落卡""标差异"这类要求）——开发按原节奏走，开发 agent 不需要知道日报的存在。
- 素材由报表侧自己取：TAPD（状态 / owner / due / 子需求）、CNB（落在哪条线 / sha / PR）、本地文件与共享日报既有内容；取不到才问，且只问用户本人。
- 问题只在收口时一次问完；不问开发 agent，也不要求它配合格式。
- 铁律：能自己查证的不问；只有"环境外事实"和"口径判断"才问用户。拿不到就说拿不到。

## 项目名（不预设）

本技能不含、也不得内置任何项目清单。项目名一律从当天素材与上下文里取：素材怎么称呼就怎么写；同一项目跨天沿用已经出现过的称呼；判断不了就问用户，不猜。

## 收口衔接（report-writer 的活）

- 用户说「出日报」或提交前 → `report-writer` 在共享日报上收口：补「今日总览」、逐分支核对必填、合并重复表述、跑机械自检、TAPD 状态前置动作。
- 提交时限仍按 v3：**次日 09:30 前**（周一至周五）。
- 若需要正式 v3 五栏提交文本（公司评分器按五栏解析），由 report-writer 从共享日报一次性生成并直接交付——**不在工作区另存第二份日报文件**。

## 周报（按需，09-19 口径）

- 落点：`<工作区根>/Reports/weekly/周报_<起>至<止>.md`；写周报的会话在采集时**额外记**：① 计划完成日（due）与实际完成日；② 方案链接与版本号。其余见 report-writer「附：周报」。
- 不写周评、不写月报。

## 与其他技能的关系

- `report-pipeline`（本技能）：采集与共写层，管"什么时候更新、更新哪块、怎么共写"。
- `report-draft-filter`：分拣层，管"口语小结哪些写、哪些剔除、怎么归类"。
- `report-writer`：收口层 + **规范原文载体**（`references/spec.md`，v3.1），管"今日总览、合规自检、五栏提交文本生成"。

三者不重叠：本技能不产生第二份文件；一切口径冲突回 `report-writer/references/spec.md` 裁定（落盘与协作方式以 2026-09-22 共享日报口径为准）。
