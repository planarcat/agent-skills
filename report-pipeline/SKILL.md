# Report Pipeline（报告编写流水线 · 采集与归并 · v3）

## 最高原则：规范 > 一切

**《日 / 周报填写规范与要求（v3 · TAPD 对齐版）》是本技能、以及所有报告动作的最高标准。** 三级效力：

1. **规范**（最高）——`report-writer/references/spec.md`（v3.1，飞书 rev 67）。三条铁律、五栏填法、虚报双向口径、提交时限，不可因为"方便采集"而打折。
2. **用户口径**——何成标的历次裁定，**仅在规范未覆盖处生效**；与 v3 冲突的旧口径（责任内联、进度百分比、失误栏等）一律作废。
3. **本技能的设计建议**（节奏、字段、提问时机）——**只是实现规范的手段**，与规范冲突时一律作废。

**v2 已作废**：v2 规范在飞书标「(过期)」，存档在 `report-writer/references/spec-v2-archive.md`。凡旧卡里出现的 v2 专用字段（责任内联、占比、Bug 五要素、失误卡、复盘），**都不再采集**。

**判据**：本技能任何一条规则被质疑，先回查 v3 规范原文；查不到依据的，退位让行。

## 适用范围（用户口径，2026-09-16；09-19 起周报按需）

**日报是主产出**（本技能完整覆盖）；**周报按需**（09-19 用户直接点过「编写本周周报」）——采集时**额外多记两类素材**，其余照日报走。

| 产出 | 载体 | 提交时限（v3） |
|---|---|---|
| **日报** | 见下方落点 | **次日 09:30 前**（不是当日 21:00） |
| **周报**（按需） | 同落点，`周报_<起>至<止>.md` | **周五下班前**（v2 的周六 21:00 作废） |

- 写周报时，素材卡**额外记**：① 这条任务的**计划完成日（due）**与**实际完成日**——周报①进度表要算偏差；② 方案的**链接与版本号**——周报⑤方案沉淀要用（缺链接/版本号该方案当月不计分）。
- **不写周评、不写月报**（周评是试用期每周 1v1 不填表；月报员工不填）。

## 数据存放位置（跟着工作区走，技能目录只读）

**技能目录永远只读，运行时数据一律不写进去。** 素材卡和日报定稿写在**工作区**里——哪份工作属于哪个工作区，数据就落在那个工作区。

落点按优先级取第一个命中的：

| 顺序 | 位置 | 说明 |
|---|---|---|
| 1 | 该工作区自己的规范 | 工作区里若已有明确约定（`AGENTS.md` / `CLAUDE.md` / `README` 指定了文档或汇报目录，或已有固定习惯），按它的来 |
| 2 | 工作区里已有的约定目录 | 已经存在 `.workbuddy/reports/`、`docs/reports/` 这类目录，直接用 |
| 3 | 默认落点 | 都没有 → 用 `<工作区>/.workbuddy/reports/` |

落点内部结构固定（落在哪一级都一样）：

```
<工作区>/.workbuddy/reports/
├── cards/2026-09-18.md            素材卡（素材区 append-only + 成稿区）
└── daily/日报_2026-09-18.md       日报定稿
```

> **本工作区（日报、周报、月报）的实际约定**：素材卡落在 `.workbuddy/reports/cards/YYYY-MM-DD.md`，**日报定稿直接放工作区根目录 `日报_YYYY-MM-DD.md`**（与已有几十份历史日报保持一致）。这属于优先级 1"工作区自己的约定"。

规则：

- **目录不存在就按需创建**，不用问用户放哪。
- **素材卡写在"产生这份工作的工作区"**；日报定稿写在**执行「出日报」时所在的工作区**。
- 工作区若在 git 仓库里，提醒用户把落点加进 `.gitignore`。
- 用户明确指定了别的路径，按用户说的来。
- 旧版曾把数据放在 `<技能目录>/report-pipeline/data/`。若发现该目录下有历史数据，**一并读取、不擅自搬动**。

### 跨工作区怎么收齐

1. 当前工作区；
2. 本次会话里出现过代码 / 文件路径的工作区；
3. 日报工作区下的 `sources.md`——一张可选的工作区清单（没有就跳过）；
4. 仍缺就去问用户一句"今天还在别的哪个目录干过活？"——**问一次，记进 `sources.md`，以后不必再问**。

**找不到就说找不到**，不得用别的日期或别的事项顶替。

## 项目名从哪里来（不预设）

**本技能不含、也不得内置任何项目清单。** 项目名一律从当天素材和上下文里取：

- 素材里怎么称呼，就怎么写；
- 同一项目跨天沿用**已经出现过的称呼**，不凭空造新总名、不擅自缩写；
- 素材没写清归属时按内容判断；判断不了就问用户，不猜。

## Overview

一句话：**v3 要人填的东西只剩四处，而这四处全是"事后无法重建"的判断——必须在它发生时就被记下来。**

| v3 手填项 | 为什么事后补不了 |
|---|---|
| **执行差异** | TAPD 只记结果，不记"晚了几天、为什么晚" |
| **协同人** | TAPD 只有 `owner`，没有实际配合关系 |
| **需求理解与方案输出** | 边界分歧当天不写下来，两周后就是一次返工 |
| **卡点 / 异常 / 明日计划** | 外部依赖与下一步判断 |

三层分工，本技能只管第一层：

| 层 | 技能 | 管什么 |
|---|---|---|
| 采集 | **report-pipeline（本技能）** | 什么时候记、记什么、谁提供、记多细 |
| 分拣 | `report-draft-filter` | 哪些写进日报、哪些剔除、怎么归类合并 |
| 成型 | `report-writer` | 日报长什么样、差异/协同人怎么标、红线自查 |

## 一、三个设计问题的结论（v3 版）

### 结论 1：节奏由规范的提交时限倒推——两拍

节奏**不是自选的**。v3 §3.5 定了提交时限，采集节奏必须与之对应：

| 规范要求（v3 §3.5） | 倒推出的采集动作 |
|---|---|
| 日报**次日 09:30 前**提交 | 单日内**边做边落卡**；当日结束归并成草稿，**次日 09:30 前定稿交付** |

落成两拍：

| 拍 | 触发 | 动作 | 产物 |
|---|---|---|---|
| ① 落卡 | 每完成一个阶段性工作（一段改动跑通、一次排查收口、一次会议出结论、一次需求理解对齐） | 往当日素材文档 append 一张素材卡 | `<工作区>/.workbuddy/reports/cards/YYYY-MM-DD.md` |
| ② 归并 | 当日结束 / 用户说"出日报" | 素材卡 → v3 五栏草稿 → 用户确认 → **不迟于次日 09:30 交付** | 见落点规则（本工作区＝工作区根目录 `日报_YYYY-MM-DD.md`） |

**v3 的提交窗口比 v2 宽了半天**（当日 21:00 → 次日 09:30），但**差异与协同人必须在当天记**——隔夜就记不清"今天和计划比偏没偏""谁跟我一起做的"。

**为什么否掉"末尾一次性回忆"**：v3 要的四要素（执行内容 + 交付物 + 交互结果 + 量化标准）和差异判断，当天不记、隔天必忘。

### 结论 2：直接更新综合文档可以，但必须双区分离 + 只追加不重写

```
当日文档
├── 【素材区】append-only      ← 所有 agent 只往这里追加，不改已写的
└── 【成稿区】可整段重生成      ← 只有汇总者能写，每次由素材区重新生成
```

- **只 append 不 rewrite** → 保真实（用户会直接手改日报文件，重写会吃掉他的修改）。
- **双区分离** → 素材区保留原始信息（含 TAPD ID、分支动作、术语），成稿区才是去噪成品。

### 结论 3：格式——v3 字段（只记四处手填 + 四要素）＋ 文字薄

- **字段一个不少**：素材卡必须携带 v3 要求的数据点（TAPD ID、差异、协同人、需求理解/方案、四要素、卡点 6 项）。成稿是机械映射，卡里没有的字段成稿时只能编——编就踩红线。
- **文字尽量薄**：只留 1~2 句白话和可验证数字，不搬实现细节（字段名 / 文件数 / 毫秒数 / 轮次 / git 动作）。
- **v3 明确不采的**：进度百分比、手写状态、责任内联、Bug/返工/延期天数、失误五要素、个人复盘。

## 二、素材卡格式（v3）

完整样例、正反例、多 agent 示例见 `references/card-format.md`。

### 2.1 任务卡（默认卡型）

```
### [N] 一句话标题
- 任务: #TAPD ID 任务名（拿不到 → 写「无单工作」并说明；ID 不许编）
- 项目:（取自素材的称呼，不预设）
- 执行差异: 一致 / 提前N天 / 滞后N天 / 阻塞 / 与TAPD不符 / 待确认
- 协同人:            ← owner 不是本人时必填（姓名+角色）
- 今日动作:          ← 执行内容，写具体动作
- 交付物:            ← 当日交付物
- 交互结果:          ← 交付给谁 / 谁可用
- 标准:              ← 量化质量标准（可验收）
- TAPD状态: 评审中 / 开发中 / 待测试 / 测试中待验收 / 已闭环（以 TAPD 为准，中文语义）
- 需求理解:          ← 边界、歧义、待确认点；首次进「开发中」前必须写过一次
- 方案输出:          ← 方案名 + 链接 + 版本 + 推进到第N段（无则留 —）
- 差异依据:【计划:月-日｜实际:月-日｜偏差:N天｜原因:｜影响:】 ← 滞后/提前才填
- 涉及: 人名
- 待确认: 等谁 + 确认什么；没有就留 —
- 原文: 用户口述原样抄，不去噪、不改写
```

**四条硬要求**：

1. `执行差异` **必须有值**（拿不到就写"待确认"并在出稿前问用户）——它是 v3 日报唯一不能被系统替代的判断。
2. `协同人`：`owner` 不是本人时**必须填**，空置扣分（v3 §8.2 红线）。
3. `需求理解`：需求**首次进入「开发中」之前必须写过一次**，一次没写就开工 = 不合格日报。
4. `原文` **原样保留、不去噪**——术语、编号、分支动作都留着；去噪是 `report-draft-filter` 的活。

### 2.2 卡点卡

v3 §3.2 要求卡点必带 6 项，采集时就按这个结构记：

```
### [N·卡点] 一句话
- 项目:
- 分类: 技术 / 对接 / 需求 / 资源
- 内容: 卡在哪，具体到接口名、人名、数据
- 需协助: 是 / 否
- 对接人: 真名（不写"后端/平台端"；涉及主管写「欧阳老师」）
- 期望解决: 月-日 / 暂无确定日期
- 影响: 对进度的影响天数或范围
- 待确认: —
- 原文:
```

**卡点是必填栏**：确无卡点，成稿时写"无"；不能因为"没记"就空着（空置即标黄，连续 2 日触发问询）。

### 2.3 异常卡

```
### [N·异常] 一句话
- 项目:
- 类型: 需求变更 / 临时会议 / 跨部门对接 / AI 查出的新异常分支
- 涉及: 人名（只按原文出现的人取，不凭"涉及主管就默认主管在场"补人）
- 待确认: —
- 原文:
```

> **一次发来的分段摘要 = 一张卡，不是多张**（09-17 两次被纠正：两段会议纪要＝同一场会）。

### 2.4 明日计划卡

```
### [N·明日] 一句话
- 任务: #TAPD ID 任务名 / 无单工作
- 交付物:
- 标准:
- 原文:
```

**无单工作上限：每人每日 ≤1 条**，需组长当日确认；技术债、重构、调研、热修、支撑答疑应开 `技术任务` 单。

### 2.5 状态更新卡

```
### [N] [状态更新] 引用 #X —— 一句话
（同样字段，只填变化的）
```

见第四节"状态跃迁规则"。

> **v2 的"失误卡"已取消**（v3 不再手填失误与影响，由 TAPD 派生），不再采集。

## 三、哪些必填、哪些尽量填、谁提供、何时问

### 3.1 信息分层（按 v3 归位）

| 层 | 内容 | 出处 | 谁填 | 时机 |
|---|---|---|---|---|
| **L1 硬事实**（必填） | 今日动作、交付物、交互结果、量化标准、TAPD ID、项目 | v3 §6 四要素 | agent 自查直填 | 阶段完成即时 |
| **L2 归属判断**（必填，需确认） | 执行差异（一致/提前/滞后/阻塞/**与 TAPD 不符**）、协同人、落哪一栏 | v3 §3.2 | agent 给候选，**用户点头** | 即时确认；批量项可留到出稿 |
| **L3 外部事实**（必填，agent 拿不到） | TAPD 最新状态、真实差异天数、协同人姓名、需求边界/歧义、卡点对接人与期望时间 | v3 §3.2/§7 | 只能用户提供 | 出稿时批量问 |
| **L4 v3 鼓励**（尽量填） | 方案链接与版本、异常分支清单、AI 查出的漏洞、风险预判 | v3 §9 / SOP | agent 可写 | 出稿时 |

- **必填核心**：**TAPD ID · 差异 · 协同人（owner 非本人时）· 四要素**。缺任一不能成稿。
- **v3 不再采**：进度百分比、手写状态、责任人内联、Bug/返工/延期天数、失误五要素、日报复盘。

### 3.2 什么时候找用户

| 时机 | 问什么 | 为什么是这个时机 |
|---|---|---|
| **即时问**（不能等） | ① 这条和计划比一致/提前/滞后？② 谁跟你一起做的？ | 这两条直接决定日报最核心的两栏，隔夜就记不清 |
| **攒批问**（出稿时一次问完） | 需求边界与待确认点、方案链接与版本、卡点对接人/期望时间、明日 TAPD ID | 不影响结构，攒一批一次问，少打扰用户 |
| **不问** | 模块名、测试结果、耗时、代码事实；本地环境维护类操作（工作区改名、本机配置调整等） | agent 能从环境/上下文拿到，问就是偷懒 |
| **不问也不编** | 拿不到的 TAPD ID、真实时刻、参会人 | 降精度写或标"待确认"，**绝不编造**——v3 里 ID 写错＝虚报 |

**铁律：能自己查证的不问；只有"环境外事实"和"口径判断"才问用户。** 拿不到就说拿不到。

## 四、素材卡 → v3 五栏日报（机械映射）

| 素材卡 | 落到日报 |
|---|---|
| 任务卡（有 TAPD ID / 无单工作） | **① 今日任务对齐**（任务行 + 差异 + 协同人 + 今日动作 + 交付物/标准） |
| 任务卡里的 `需求理解` / `方案输出` 字段 | **② 需求理解与方案输出**（有变化才写，无变化写"—"） |
| 卡点卡 | **③ 卡点与阻碍**（必填，无则"无"） |
| 异常卡 | **④ 异常与需协调事项**（无则"无"） |
| 明日计划卡 | **⑤ 明日计划**（1~3 项，带 TAPD ID） |

**v3 没有的落点**（v2 有、现在取消）：失误与影响、个人复盘与思考。素材里若有对应内容 → 不进日报（复盘移周报）。

映射后仍须两道：先 `report-draft-filter` 去噪归类，再 `report-writer` 套五栏模板 + 标差异/协同人 + 红线自查。

**状态跃迁规则**：素材卡写出去后**不改**。同一事项有了新状态 → 追加一张 `[状态更新] 引用 #N` 卡。成稿时**同一事项取最新状态，其余内容全部累加**——只有同一事项的状态冲突才以新为准。

**TAPD 状态即时更新**：v3 里"状态即时更新是交报表的前置动作"。归并时若发现日报要写的状态比 TAPD 靠前（或靠后），**先去 TAPD 改状态**，再定稿。

## 五、多 agent 并行规则

1. **只有汇总者能写成稿区**，其他 agent 只往素材区 append。
2. **只 append 自己的卡，不改别人的卡**（也不回头改自己已写好的卡——要更新就追加状态更新卡）。
3. 同一事项多个 agent 都记了 → 成稿时按「标题关键词重合」去重合并，不拆碎。
4. **合并后任务行仍须 ≤3 条**（v3 §3.4：超过 3 条组长当日必问）——多 agent 记录最容易堆条数，归并时要主动压。
5. 冲突处理顺序：状态冲突取最新 → 事实冲突以有证据的一方为准 → 仍冲突则标 `待确认`，问用户。
6. 多 agent 并行作业时**各记各的，不要互相等**；归并是最后一步的事。
7. 上下文丢失的场景（额度限制降级、会话中断）优先保住素材区，它是最难重建的部分。

## 六、机械自检（归并前必跑）

| # | 自检项 | 依据 | 不通过怎么办 |
|---|---|---|---|

全为纯 Markdown + 一个零依赖 Python 脚本；无外部服务、无网络、无第三方库。
**装完即可用，不需要改任何路径**：运行时数据落在**当前工作区**内，技能目录保持只读；项目名一律从当天素材里取，技能内不含项目清单。唯一写死的是报告作者本人姓名（何成标）。

## 与其他技能的关系

- `report-pipeline`（本技能）：采集层，管"什么时候记、记什么、谁提供"。
- `report-draft-filter`：分拣层，管"哪些写、哪些剔除"。
- `report-writer`：成型层 + **规范原文载体**（`references/spec.md`，v3.1），管"日报长什么样、命中哪条红线"。

三者不重叠：本技能不产出日报正文，只产出素材卡；一切格式与口径冲突回 `report-writer/references/spec.md` 裁定。
