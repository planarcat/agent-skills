# Report Pipeline（共享日报 · 采集与共写）

## 最高原则：规范 > 用户口径 > 本技能建议

1. **规范**（最高）——`report-writer/references/spec.md`（v3.1，飞书 rev 67）**（同仓库/同组内有效；单独搬走本技能时以自带 `references/` 为准，建议与 `日报撰写` 整组移植）**。内容质量的全部硬要求——TAPD 对齐、四要素、虚报双向红线、敷衍话术禁令——出自它，不打折。
2. **用户口径**——何成标的历次裁定。其中 **2026-09-29 日报落盘口径是落盘与协作方式的最新安排**（下一节），覆盖旧的两拍节奏、素材卡体系、成稿落盘与 2026-09-22 的单文件共写；其余口径（零注入、白话表述、不写 AI 旁白等）继续生效。
3. **本技能的设计建议**——只是实现手段，与上两者冲突时一律作废。

**判据**：任何一条规则被质疑，先回查 v3 规范原文与本口径；查不到依据的，退位让行。

## 日报落盘口径（2026-09-29 用户拍板，本技能的核心）

1. **按日期建文件夹**：`<工作区根>/Reports/daily_work/YYYY-MM-DD/`（文件夹名用当天日期，`date +%F` 可取）。目录不存在就创建，不用问。
2. **按需求一文档**：工作文档放**当天文件夹**里，命名 `【需求id_需求标题】.md`（如 `【1002792_效果图与转平台能力流程重构】.md`）。id 用短 id（长 id 去前 10 位前缀再去前导 0）；标题剔除文件系统非法字符（`/ \ :` 等），建议 ≤24 字符，太长截断并在汇报里说明；拿不到 TAPD 单 → `【无单_事项简述】.md`。
3. **同需求多 agent 共写同一份文档**：不同 agent 在同一需求上干活，写进**同名的当天文档**；**不需要考虑冲突的问题**（2026-09-29 用户口径，顾名思义：不加锁、不做任何并发处理），也不需要协商先后。
4. **只在当天文件夹里写**：每天文件夹里的文档只收**当天发生**的工作；同一需求分多日做 → 每天各有各的文档；**历史日期文件夹一律只读**，不回写、不补改。会话跨天怎么分拣见「会话跨天」一节。
5. **边界**：只更新自己会话的记录与自己在总结里相关的句子；**不重排、不删改、不"顺手规范化"他人的内容**。
6. **时间要素（2026-09-22 起，继续生效）**：每条工作节点都带 `[HH:MM]`（取记录时刻）——工作总结的句子、会话记录里的工作节点、卡点 / 异常 / 明日 / 复盘条目，一个不漏。多会话共写同一份总结时，靠时间戳排序与归属，谁在什么时候做了什么一目了然；不带时间的条目一律补齐。
7. **会话中断 / 额度降级**：优先保证自己会话块已落盘，收口时标注缺口。

> 2026-09-22 的「每工作区每日一份 `YYYY-MM-DD.md` 单文件」自本口径起作废；当天目录里若还留着旧单文件，当素材读，不搬不删。v3 规范的**内容要求**（TAPD 对齐、四要素、差异、协同人、卡点、时限）全部保留，只是承载结构换成日期文件夹 + 需求文档。

## 数据存放位置（跟着工作区走，技能目录只读）

- 共享日报落在**产生这份工作的工作区**根目录；哪份工作属于哪个工作区，数据就落在那个工作区。
- 工作区里已有更明确约定（`AGENTS.md` / `CLAUDE.md` / README 指定了汇报目录）→ 按它的来；用户点名了别的路径 → 按用户的来；都没有 → 用默认落点。
- 工作区在 git 仓库里 → 提醒用户自行决定是否把 `Reports/` 加进 `.gitignore`。
- 旧版数据（`.workbuddy/reports/`、工作区根 `日报_YYYY-MM-DD.md`）不迁移；发现历史文件当素材读，不擅自搬动。

### 跨工作区怎么收齐

① 当前工作区 → ② 本次会话里出现过代码 / 文件路径的工作区 → ③ 日报工作区的 `sources.md`（可选清单，没有就跳过） → ④ 仍缺就问一句"今天还在别的哪个目录干过活？"——问一次记进 `sources.md`，以后不必再问。**找不到就说找不到**，不得用别的日期或别的事项顶替。

## 需求文档骨架（当天文档不存在时，按此创建）

```markdown
# 【<需求id>_<需求标题>】· YYYY-MM-DD

> 本文档由当天在该需求上干活的 agent 会话共写（同需求多会话写同一份文档，不需要考虑冲突的问题）。
> 只更新自己的会话块与自己相关的总结句；不重排、不删改他人内容；**每条工作节点带 `[HH:MM]` 时间**。

## 工作总结
- [HH:MM · <agent 名>] <一句话；按时间先后排列；只增/改自己会话相关的句子>

## 会话记录
#### <agent 名·HH:MM>（会话标识）
- 任务: #<TAPD ID> <任务名>（拿不到 → 无单工作）
- 工作节点:
  - [HH:MM] <一条进展 / 动作>
- 交付物/标准:
- 执行差异: 待确认
- 协同人: —
- 原文:

## 卡点与阻碍
## 异常与需协调
## 明日计划
## 复盘
```

「今日总览」不再常驻文件：收口时由 日报撰写 读当天文件夹里**全部**需求文档汇总生成。

## 会话标识（首次写入前定好，全天不变）

- 格式：`<agent 名或工具名>·<当日首次写入时刻 HH:MM>`；同 agent 同分钟冲突 → 尾加 `-2`、`-3`。
- 同一会话后续所有更新**沿用同一标识**定位自己的会话块；换了会话就是新标识、新块。

## 总结即落盘（2026-09-29 用户口径）

用户说「总结工作 / 工作总结 / 总结一下 / 记一下」＝让你**把总结直接写进当天的需求文档**（照「更新动作」执行；总结的活跨几个需求，就分别写进各自文档）。不是让你在对话里输出一遍总结文字：

- **落盘即交付**：写完只回一行落点（写进了哪个文档、记了几条、有无卡点），**不在对话里重复总结正文**。
- **不许再问一遍**：禁止问"要不要写入文档 / 需要我落盘吗 / 跟我确认一下"——用户口径：那叫脱裤子放屁。
- 文档里已有的节点不重复写，只补本次新增内容。
- 整理 / 总结时**先做合入检查**（见下节），把需求阶段随总结一起写进文档。

## 知识沉淀链（连续沉淀 · 2026-10-09 用户口径）

总结写完、告知用户落点之后，**不停顿、不询问**，接着按 `知识沉淀` 执行连续沉淀：

1. 扫描当天总结内容 → 识别：需求增量（业务语义）/ 坑（实现教训）/ 口径拍板
2. 按 `知识沉淀` 分流规则起草增量（业务文档节 / 模块卡坑节），过八条文风自检
3. **直接落盘** + 刷新 `Knowledge/_map.md` 对应行；工作区还没有 `Knowledge/` → 按其自举规则创建
4. 汇报在日报落点之后追加一行「沉淀清单」（沉淀了什么、落在哪）；用户事后可打回，打回即改

## 合入检查（整理 / 总结时必做 · 2026-09-29 用户口径）

整理工作内容时，查一下该需求工作分支的合入情况，用合入状态判定需求阶段，随总结写进该需求文档：

| 合入情况 | 需求阶段 |
|---|---|
| 已合入**生产分支 `main2`**（灵创用户端/平台端 `lingchuang-front`、工厂端 `factory-front` 的生产分支都是 `main2`） | **已发版**：已发布生产环境、已验收、需求闭环 |
| 已合入 **`main-test` 或 `main_test`**（部署测试环境的分支） | **测试中**：已进测试环境，正在测试 |
| 都没合入 | **开发中 / 本地自测** |

查法（在对应子仓执行；工作分支已被删就用最近一次的分支 tip sha，或按需求 id 搜合入日志）：

```bash
cd <lingchuang-front 或 factory-front>
git fetch origin main2                             # 先拉生产分支最新
git fetch origin main-test main_test 2>/dev/null   # 测试分支名以仓库实际为准
git merge-base --is-ancestor <工作分支或sha> origin/main2 && echo "已合入 main2（已发版闭环）"
git merge-base --is-ancestor <工作分支或sha> origin/main-test && echo "已合入 main-test（测试中）"
```

- 远程拉不动（权限 / 网络）时：改走**部署测试环境的 worktree**，在那边更新 `main-test` 最新代码后再比。
- 结论写进该需求文档「工作总结」的最新一条，如 `- [16:20 · ZCode] 分支已合入 main2，已发版生产，需求闭环`；测试中 / 开发中同理，并据此看「明日计划」还要不要排它。
- 查不出来就写「合入情况待确认」，**不猜**。

## 会话跨天：先分拣再落盘（2026-10-06 用户口径）

一个会话连着干几天很常见。**落盘前先 `date +%F` 定住今天日期，再按顺序分拣：**

1. **定起点：上一次工作总结之后**。先看这个需求最近记到哪（当天文档已有条目 → 此前日期文档的最后一条），已总结过的不重复。**默认记录范围 = 上一次工作总结之后 → 今天**。
2. **归属看发生日**：候选里发生在今天的 → 正常写进今天的「工作总结」；发生在昨天等近期的漏记 → 只在自己会话块里加**带完整日期的补记行**：`- [MM-DD HH:MM] <内容>（补记）`——补记行**也算今天的产出**（收口统计时计入）。
3. **长间隔先确认**：候选与今天隔了多天（上次总结之后一直没记）→ **先向用户确认一句**（并入今天 / 按补记 / 不记），确认后再动笔；不许默默整批回填。
4. **无实质工作不确认**：候选里没有实际代码开发（只是创建了需求分支、做了需求拆解这类）→ **不问**，默认直接当做今天的工作内容写入。
5. **时间规则**：当场记的节点用 `[HH:MM]`（记录时刻＝发生时刻）；补记**必须带完整日期**；不造「约」式的假精确。
6. **分不清发生在哪天 → 一律按补记处理**（宁可少记、不错记），仍拿不准就问用户一句。
7. 会话标识跨天沿用；每天在新文档里照常新建自己的会话块。

## 更新动作（阶段完成即更新）

1. **定位当天文件夹**：`<工作区根>/Reports/daily_work/YYYY-MM-DD/`，不存在就建。
2. **定位需求文档**：`【需求id_需求标题】.md`（取名见口径第 2 条）；不存在 → 按骨架创建。
3. **更新**：读文档最新内容（锚点不凭记忆，用户可能刚手改过）→ 定位 / 新建自己的会话块 → 更新工作总结与相关条目（句子格式 `- [HH:MM · <agent 名>] 内容`，**按时间先后插入**；只增 / 改与自己会话相关的句子；他人写的句子一字不动）；卡点 / 异常 / 明日 / 复盘有内容就追加，无卡点不写（收口时统一判「无」）。
4. **收尾**：不做全文重排、不做格式"顺手统一"——那是收口层（日报撰写）的事。

### 会话记录块（字段即 v3 必填数据点）

```markdown
#### <agent 名·HH:MM>（会话标识）
- 任务: #<TAPD ID> <任务名>（拿不到 → 写「无单工作」并说明；ID 不许编）
- 工作节点:
  - [14:05] <一条进展 / 动作，禁"继续开发/按计划推进">
  - [16:20] <下一条>
- 交付物/标准: <当日交付物 + 量化标准>
- 执行差异: 一致 / 提前N天 / 滞后N天 / 阻塞 / 与TAPD不符 / 待确认
- 协同人: <owner 非本人必填（姓名+角色）；无则 —>
- 原文: <口语原样抄，不去噪、不改写>
```

硬要求（沿 v3，一条不能少）：

1. TAPD ID 拿不到就问一句或标「无单工作」（无单工作每人每日 ≤1 条，需组长当日确认），**不许编**；
2. `执行差异` 必须有值，判不准写「待确认」；
3. `协同人`：owner 不是本人时必填，空置扣分（v3 §8.2 红线）；
4. 四要素（工作节点 / 交付物 / 交互结果 / 量化标准）写全，写不出交互结果就写清"谁下一步能用"；
5. `原文` 原样保留——去噪是 日报草稿过滤 的活。
6. **每个工作节点带 `[HH:MM]` 时间要素**——共写的排序与归属靠它，不许省略；时间取记录时刻（24 小时制）。

## 时间要素（2026-09-22 补充 · A / D 共写防混乱）

每个工作节点都带 `[HH:MM]`（24 小时制，取记录时刻）。三个位置的格式：

| 位置 | 格式 |
|---|---|
| 工作总结的句子 | `- [HH:MM · <agent 名>] 内容`（agent 名同名多会话时加 -2 / -3 后缀） |
| 会话记录里的工作节点 | `- [HH:MM] 内容`（来源由所在块标明） |
| 卡点 / 异常 / 明日 / 复盘条目 | `- [HH:MM · <agent 名>] 内容` |

- **排序**：工作总结与各条目一律按时间先后排列；更新时插到正确的时间位置，不改他人句子的时间。
- **归属**：多会话共写同一份总结——时间戳看「什么时候」，agent 名看「谁写的」，读的人不用猜新鲜度，写的人不用争先后。
- 会话记录块标题里的 `HH:MM` 是**会话首次写入时间**（会话标识的一部分，用于定位块），与逐条节点时间不是一回事，别混用。

## 零注入：采集是报表侧的事，不指挥开发过程（2026-09-21 口径，继续生效）

- 开发技能里不许写日报内容（不写"为了日报要怎样"、不写"落卡""标差异"这类要求）——开发按原节奏走，开发 agent 不需要知道日报的存在。
- 素材由报表侧自己取：TAPD（状态 / owner / due / 子需求）、CNB（落在哪条线 / sha / PR）、本地文件与共享日报既有内容；取不到才问，且只问用户本人。
- 问题只在收口时一次问完；不问开发 agent，也不要求它配合格式。
- 铁律：能自己查证的不问；只有"环境外事实"和"口径判断"才问用户。拿不到就说拿不到。

## 项目名（不预设）

本技能不含、也不得内置任何项目清单。项目名一律从当天素材与上下文里取：素材怎么称呼就怎么写；同一项目跨天沿用已经出现过的称呼；判断不了就问用户，不猜。

## 收口衔接（日报撰写 的活）

- 用户说「出日报」或提交前 → `日报撰写` 读**当天文件夹里全部需求文档**收口：汇总「今日总览」、逐任务核对必填、合并重复表述、跑机械自检、TAPD 状态前置动作。
- 提交时限仍按 v3：**次日 09:30 前**（周一至周五）。
- 若需要正式 v3 五栏提交文本（公司评分器按五栏解析），由 日报撰写 从共享日报一次性生成并直接交付——**不在工作区另存第二份日报文件**。

## 周报（按需，09-19 口径）

- 落点：`<工作区根>/Reports/weekly/周报_<起>至<止>.md`；写周报的会话在采集时**额外记**：① 计划完成日（due）与实际完成日；② 方案链接与版本号。其余见 日报撰写「附：周报」。
- 不写周评、不写月报。

## 与其他技能的关系

- `日报采集共写`（本技能）：采集与共写层，管"什么时候更新、更新哪块、怎么共写"。
- `日报草稿过滤`：分拣层，管"口语小结哪些写、哪些剔除、怎么归类"。
- `日报撰写`：收口层 + **规范原文载体**（`references/spec.md`，v3.1），管"今日总览、合规自检、五栏提交文本生成"。

三者不重叠：本技能不产生第二份文件；一切口径冲突回 `report-writer/references/spec.md` 裁定（落盘与协作方式以 2026-09-22 共享日报口径为准）。
