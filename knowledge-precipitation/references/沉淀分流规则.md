# 沉淀分流规则：需求沉淀 vs 缺陷修复沉淀

> 核心区别一句话：**需求沉淀记「业务应该是什么」，缺陷沉淀记「实现哪里容易错」。**
> 拿不准本次是否动了业务语义 → 问用户，不自行裁决。

## 一、对照表

| 维度 | 需求沉淀 | 缺陷修复沉淀 |
|---|---|---|
| **沉淀对象** | 业务**应该是什么**（业务语义） | 实现**哪里容易错**（实现陷阱） |
| **落点** | `business/<仓>/<业务>.md`（正文节 + 变更史一行） | `modules/<仓>/<模块>.md` 的「坑」节 + `Logs/` 短记 |
| **写什么** | 流程 / 规则 / 边界 / 状态流转（新增或修改） | 根因 / 症状 / 一句修法 / 防范与回归点 |
| **读者** | 新人、领导、所有 agent | 开发者、开发 agent |
| **文风** | 人话层（八条红线，零代码命名） | 技术层（允许代码命名、路径） |
| **触发** | `需求拆解` 收尾 / 需求收口 / 日报链路 | 缺陷修复完成 / `改动记录`（长记） |
| **变更史** | **记一行**（业务演进的显式记录） | **不进**业务文档变更史（不影响业务语义） |
| **示例** | U-2792 新增批量转平台 → 业务文档加流程与规则 R5/R6 | 批量转平台偶发丢图 → 坑节记「并发写覆盖，需加锁，回归点 XX」 |

## 二、判定流程

```
本次知识事件是什么？
  ├─ 新需求 / 需求变更（业务多了能力、改了规则）
  │    → 需求沉淀：定位业务域 → 改被影响节 → 变更史一行
  ├─ 缺陷修复（实现违背业务意图，业务意图本身没变）
  │    → 缺陷沉淀：坑节落「症状+根因+修法+防范」→ Logs/ 短记
  └─ 缺陷修复中暴露业务口径本身错了（需求理解错，不是实现错）
       → 口径部分升级走需求沉淀路径（改业务文档正文，先与用户确认）
       → 实现部分照常进坑节，两不混
```

## 三、交叉情况

| 情况 | 处理 |
|---|---|
| 缺陷修复暴露口径错误 | 口径升级为需求沉淀（先问用户）；实现教训进坑节 |
| 需求开发顺带修了老坑 | 坑照常沉淀（坑节），与需求增量分开落，互不混写 |
| 同一坑反复修 | 坑节合并为一条并升级防范级别；考虑是否应成为「硬约束与不变量」节内容 |
| 缺陷导致硬约束变化 | 更新模块卡「硬约束与不变量」节（仍不进业务文档变更史） |

## 四、变更史记录规则

- 只记**业务语义级**变更：新增能力、规则改动、口径调整、状态流转变化
- 一行格式：`<需求id>（YYYY-MM-DD）：一句话`
- 不记：bug 修复、代码重构、文档自身排版调整（这些不是业务演进）
- 超 15~20 条压缩老条目为季度摘要（回链 `snapshots/`）

## 五、共用红线（两类沉淀都遵守）

1. 无来源不落盘（需求 id / commit / 讨论主题）
2. 体量守恒：改写优于追加；坑节合并同类项；只留当前仍需防范的坑
3. 宁缺毋滥：修正、删除优先于新增；过时的知识比没有更危险
