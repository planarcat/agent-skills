# 业务文档模板与文风红线（business/ 层）

> 读者：新人、领导、非本业务开发者、所有 agent。**人话层**——中文优先、零代码命名。
> 验收一句话：没参与过该业务的人，不读代码、不问人、不读其他文档，读完这一篇能用自己的话复述「做什么、谁用、主流程、硬规则、不做什么」，且复述里用不上任何代码词汇。

## 一、九节模板（节数固定，稳定期不加节）

文件位置：`Knowledge/business/<仓>/<业务名>.md`；标题 = 业务名；一篇只讲一个业务，自包含。

```markdown
---
status: 线上 | 开发中 | 已下线
requirements: [U-2792]            # 关联 TAPD 需求，可回溯需求单原文
updated: 2026-10-09               # 最后验证时间；超 60 天由审计标「陈旧」
---
# 效果图转平台（标题 = 业务名）

## 一句话                          # 这个业务是做什么的，20 字内（领导 3 分钟测试的第一段）
## 给谁用、解决什么问题             # 用户与动机；写"商家要批量上架"不写"接口并发限制"
## 业务流程                        # 用户视角主流程，编号步骤；例：商家勾选 50 张 → 逐张转换 → 失败的标红可重试
## 业务规则与口径                   # 逐条编号（R1、R2…），每条可测；口径变更有记录
## 状态流转                        # 如有：状态机 / 订单流转，用表格
## 边界与不做什么                   # 明确排除项——防止 agent 自行扩大范围的关键节
## 涉及的端与页面入口               # 用户端/工厂端/ShopAgent 各自哪里触达（用户语言描述）
## 代码落点                        # 入口文件一段带过，细节进 modules/ 卡；唯一允许代码命名的一节
## 关联                           # TAPD 需求单、ADR、相邻业务文档互链

## 变更史                          # 倒序，一行一需求；唯一允许单调增长的节
- U-2792（2026-10-09）：新增批量转平台；R2 口径改为按色系分组
- U-2611（2026-09-12）：初版，单张转平台
```

**自包含规则**：只读这一篇就能回答五问；需要术语时跳术语表、需要代码细节时跳 modules/ 卡——但**不跳也能读懂主线**。

## 二、八条文风红线（起草后逐条自检，不过不出稿）

| # | 红线 | 自检问句 |
|---|---|---|
| 1 | **中文优先**：正文全中文；英文/缩写首现给中文解释（≤1 句）并登记进术语表 | 每个 API/POD/PSD 都解释过吗？ |
| 2 | **零代码命名**：流程、规则、边界、状态各节不出现函数名/变量名/组件名/文件路径/接口名 | 删掉「代码落点」节后全文还有代码词吗？ |
| 3 | **业务角色与动作**：用用户动作讲流程，不用系统实现语言 | 写的是"商家上传"还是"前端调用上传接口"？ |
| 4 | **例子优先**：一个具体例子胜过一段抽象规则 | 每条难懂的规则配例子了吗？ |
| 5 | **结构化表达**：流程用编号步骤/表格/图，不写大段文字 | 有超过 5 行的纯段落吗？ |
| 6 | **领导 3 分钟测试**：只读「一句话 + 给谁用 + 现状（status）」能明白这业务做什么、值不值得关注 | 摘掉正文只留三段，通顺吗？ |
| 7 | **新人 0 前置测试**：不了解项目历史、不读其他文档，能顺着主流程读完不卡壳 | 有"如前所述""就是之前那个 xx"吗？ |
| 8 | **术语有出口**：确需技术概念时，正文用中文词 + 链接术语表，不展开技术细节 | 技术概念都出口到术语表了吗？ |

被打回的文档必须**用人话重写**，不得原样再交。用户裁决是终审——用户说"看不懂"即红线未过。

## 三、体量守恒写法（所有文档类型共用）

文档 = 业务**当前态**的完整描述，**不是历史日志**。文本量与业务生命周期同步：新业务 0 → 开发上线到峰值 → 大动作台阶式变动 → 稳定期微增量平稳。

| 事件 | 正确写法 | 错误写法 |
|---|---|---|
| 稳定期小需求 | **改写**现有规则条目/流程步骤，变更史一行 | 新增小节、追加段落 |
| 小缺陷修复 | 坑节改一两行，或并入既有同类坑 | 每修一个 bug 加一条，坑节无限变长 |
| 大版本/重构 | **台阶式重写**受影响章节（体量允许大变动） | 旧描述上打补丁，新旧并存 |
| 坑已过时（重构后不存在） | 删除或压缩成一句防范规则 | 一直留着 |

- 九节模板**节数固定**：稳定期只改节内内容，不加节
- 坑节**合并同类项**：同根因合并为一条；坑 = 当前仍需防范的，不是修过的 bug 流水
- **变更史是唯一允许单调增长的部分**：超 15~20 条，老条目压缩成一句季度摘要（如「2026 Q3：初版至批量能力（详见 snapshots/xxx）」）
- 体量反常 = 写法异常，处置见 `_map.md` 使用说明：稳定期持续增长 → 精简合并一轮；上线后体量过小 → 沉淀欠债补课；无大动作暴涨 → 过程内容清去 Logs/snapshots

> 健康阈值：稳定业务的业务文档，连续两个月行数变化应 ≤ ±10%。

## 四、增量合并规则（多人/多 agent 沉淀不打架）

| 情况 | 规则 |
|---|---|
| 一个需求跨多个业务域 | 按域拆增量，分别归位各自文档 |
| 新需求与文档现状冲突 | 以新需求为准更新正文，旧口径压入变更史 |
| 冲突大到疑似原业务逻辑要翻 | 停下来与用户确认，不自行裁决 |
| 增量无来源（需求 id / commit / 讨论主题） | 不落盘 |
