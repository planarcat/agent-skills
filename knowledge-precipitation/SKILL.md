# 知识沉淀（Knowledge/ 开发知识库）

**定位**：把「读代码读不出来的知识」以**需求为单位增量沉淀**进工作区根 `Knowledge/`。**业务逻辑文档是第一公民**——任何一个业务，看一篇文档就知道它是做什么的；读者不止 AI，新人、领导不看代码也能看懂。

**沉淀 = 归位 + 摘要，不是重新创作**：影响面、方案文档、坑记录本来就会生成，本 skill 只做归位与压缩，不做创造性写作。

**两条铁律**：

1. **无来源不落盘**——每篇沉淀必须带来源（需求 id / commit / 讨论主题）
2. **宁缺毋滥**——过时的知识比没有更危险；修正、删除优先于新增

## 知识库在哪（工作区根）

```
<工作区根>/Knowledge/          # 与 Docs/、Logs/、Blogs/、Reports/ 同级，不进业务仓
├── _map.md                    # 入口：业务一览表 + 使用说明（唯一必维护的索引）
├── 00-入门/                    # 系统总览 + 术语表（业务词↔技术词翻译枢纽）
├── business/<仓>/              # ★ 业务逻辑文档（第一公民，人话层）
├── modules/<仓>/               # 代码模块卡（辅助：入口文件/硬约束/坑，技术层）
├── adr/                        # 架构决策记录（≤50 行）
└── snapshots/                  # 带日期演进快照（事件驱动才产生）
```

**读法（消费优先级）**：开工先读 `_map.md` → 命中的业务文档 / 模块卡 → 信息不够再 GitNexus 图谱 → 现读代码。读到文档与代码不符，**顺手修正文档**（消费即校准——每次被使用都是验证机会）。

### 首次使用自举（工作区还没有 Knowledge/ 时）

本 skill 所在仓库只承载规范；`Knowledge/` 是运行时数据，跟着**开发工作区**走。**首次沉淀时**若工作区根没有 `Knowledge/`：

1. 按 `references/模块卡与ADR模板.md` 的 `_map.md` 结构，在工作区根创建骨架：`_map.md`（含使用说明）+ `00-入门/术语表.md` 起步；`business/ modules/ adr/ snapshots/` 目录随首篇内容一并创建，不建空目录
2. 创建后**直接落第一篇增量**，不为建骨架单独跑一趟
3. **不预写种子业务文档、不做历史补录**——冷启动口径：知识库从下一个需求开始增量生长，老业务碰到才补

## 增量三步（每次沉淀都走）

1. **定位**：本次知识属于哪个业务域？`business/<仓>/` 已有该业务文档 → 归入；没有 → 按模板新建（新业务只填本次涉及的节，其余留待后续需求补）
2. **增量起草**：只改被本次事件影响的节，不重写全文（模板与文风红线见 `references/业务文档模板与文风红线.md`）
3. **记变更史一行**：`<需求id>（YYYY-MM-DD）：一句话改了什么`——这是「在原需求基础上更新了什么」的显式记录

## 分流：需求沉淀 vs 缺陷修复沉淀

一句话：**改业务语义（应该是什么）走需求沉淀 → `business/`；改实现认知（哪里容易错）走缺陷沉淀 → `modules/` 坑节 + `Logs/`**。对照表与升级路径见 `references/沉淀分流规则.md`；拿不准是否动了业务语义 → 问用户。

## 交互模式（按链路分两种）

| 链路 | 模式 |
|---|---|
| **日报 / 改动记录链路**（`日报采集共写`、`日报撰写`、`改动记录` 收尾） | **连续沉淀**：工作总结写完、告知用户后**不停顿、不询问**，直接起草 → 自检 → 落盘 → 刷 `_map.md`，汇报带「沉淀清单」，用户**事后可打回**（说「沉淀错了/改掉某条」即修正） |
| **其余链路**（`需求拆解` 收尾、`方案锁定`、用户点名「沉淀一下」） | 起草 → 用户一字裁决（**落** / 跳过 / 改后再落）→ 落盘 |

质量底线两种模式一致：起草后必须过八条文风自检，不过不出稿；被打回的文档必须用人话重写，不得原样再交。

## 体量守恒（写法铁律）

文档 = 业务**当前态**的描述，不是历史日志；文本量与业务生命周期同步（新业务 0 → 上线时到峰值 → 大动作台阶式变动 → 稳定期微增量平稳）。

- **稳定期改写优于追加**：小需求只改现有条目 + 变更史一行，**不加节**（九节模板节数固定）
- **坑节合并同类项**：坑 = 当前仍需防范的，不是修过的 bug 流水；过时的坑删除或压缩成一句防范规则
- **变更史是唯一允许单调增长的部分**，超 15~20 条把老条目压缩成季度摘要（细节回链 `snapshots/`）
- **大动作台阶式重写**：大版本/重构允许大量改写或大量新增，**禁止新旧描述并存**
- 体量反常即写法异常（稳定期持续增长 / 上线后体量过小 / 无大动作暴涨）→ 精简或补课，处置规则固化在 `_map.md` 使用说明

## 沉淀什么、不沉淀什么

只沉淀**读代码读不出来的**。取舍自测：**「下次有 agent 再开发到这里，还要不要花同样的理解成本？」要 → 沉淀；不要 → 不沉淀。** 量化近似：`价值 = 获取成本 × 复用频率 × 稳定性`，三项都高才动笔。

- ✅ 沉淀：业务口径（glossary）/ 模块知识卡 / 硬约束与不变量 / ADR / 坑与教训 / 工程口径与演进快照
- ❌ 不沉淀：代码结构本身（GitNexus 管）、日报流水账（`Reports/` 管）、调试过程（只留根因 + 一句修法）、30 秒能从代码看出来的、未验证的猜测（要么验证后落，要么标 `confidence: 低` 且不进地图推荐位）

## 与其他 skill 的关系

| skill | 关系 |
|---|---|
| `需求拆解` | **第一写入锚点**：拆解完成 → 起草业务文档增量（拆解产出本就是业务理解，归位即可）；开场消费侧：先读 `_map.md` 与命中卡再拆 |
| `日报采集共写` / `日报撰写` | 连续沉淀链路：总结写完告知后接着沉淀，不断不问，事后可打回 |
| `改动影响面与回归` | 影响面结论归位模块卡更新；发现文档与实现不符 → 顺手修正 |
| `改动记录` | 长记完成 → 坑上翻对应模块卡「坑」节（并按体量守恒合并同类项） |
| `方案锁定` | 归档时从主题提炼 ADR 落 `Knowledge/adr/`（决策摘要 + 回链 Plans 主题） |
| `生成提交` | 防腐烂检查：diff 文件命中模块卡 `module` 路径 → 汇报加一行提醒（只提醒不强制） |
| `方案讨论` | 消费侧：讨论前读相关 `adr/` 与业务文档，防重复决策、防推翻已定口径 |
| `开发中规范` | 只做**轻标记**：发现新坑/新口径/与卡不符，记一行「待沉淀」，不打断开发 |
