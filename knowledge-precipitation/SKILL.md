# 知识沉淀（Knowledge/ 开发知识库）

**定位**：把「读代码读不出来的知识」以**需求为单位增量沉淀**进工作区根 `Knowledge/`。**业务逻辑文档是第一公民**——任何一个业务，看一篇文档就知道它是做什么的；读者不止 AI，新人、领导不看代码也能看懂。

**沉淀 = 归位 + 摘要，不是重新创作**：影响面、方案文档、坑记录本来就会生成，本 skill 只做归位与压缩，不做创造性写作。

**沉淀是逐渐揭示项目业务的过程（2026-10-15 用户口径）**：没有知识库时，弄清某个业务在代码里怎么实现，要深挖代码与上下文摸脉络；知识库把项目完全收纳后，用户问「XXX 怎么实现的 / 显示条件是什么 / 要做什么、为什么」可直接从库里得到答案——所以**每次查阅代码弄懂的业务，答案本身就是待沉淀内容**。

**两条铁律**：

1. **无来源不落盘**——每篇沉淀必须带来源（需求 id / commit / 讨论主题）
2. **宁缺毋滥**——过时的知识比没有更危险；修正、删除优先于新增

## 知识库在哪（工作区根）

```
<工作区根>/Knowledge/          # 与 Docs/、Logs/、Blogs/、Reports/ 同级，不进业务仓
├── _map.md                    # 入口：业务一览表 + 使用说明（唯一必维护的索引）
├── 00-入门/                    # 系统总览 + 术语表（业务词↔技术词翻译枢纽）
├── business/<仓>/              # ★ 业务逻辑文档（第一公民，人话层）
├── modules/<仓>/               # 代码模块卡（辅助：入口文件/硬约束/坑，技术层）
├── adr/                        # 架构决策记录（≤50 行）
└── snapshots/                  # 带日期演进快照（事件驱动才产生）
```

**读法（消费优先级）**：开工先读 `_map.md` → 命中的业务文档 / 模块卡 → 信息不够再 GitNexus 图谱 → 现读代码。读到文档与代码不符，**顺手修正文档**（消费即校准——每次被使用都是验证机会）。

### 首次使用自举（工作区还没有 Knowledge/ 时）

本 skill 所在仓库只承载规范；`Knowledge/` 是运行时数据，跟着**开发工作区**走。**首次沉淀时**若工作区根没有 `Knowledge/`：

1. 按 `references/模块卡与ADR模板.md` 的 `_map.md` 结构，在工作区根创建骨架：`_map.md`（含使用说明）+ `00-入门/术语表.md` 起步；`business/ modules/ adr/ snapshots/` 目录随首篇内容一并创建，不建空目录
2. 创建后**直接落第一篇增量**，不为建骨架单独跑一趟
3. **不预写种子业务文档、不做历史补录**——冷启动口径：知识库从下一个需求开始增量生长，老业务碰到才补

## 查阅即沉淀，节奏轻快（2026-10-15 用户口径）

- **查阅代码回答业务问题后**（XXX 怎么实现 / 显示条件是什么 / 要做什么、为了什么、原因是什么）：答案即待沉淀内容——当场只记一行「待沉淀：<一句话>」（与开发中规范轻标记同款），**不立即展开写**，收尾/总结时随锚点归位
- **广义开发全程（需求理解 / 开发实现 / 审查修改）沉淀要轻、快、甚至推后**，不对开发节奏造成拖慢；**总结记录环节才做完整的沉淀**（日报 / 改动记录收尾的连续沉淀即此口径）

## 增量两步（每次沉淀都走）

1. **定位**：本次知识属于哪个业务域？`business/<仓>/` 已有该业务文档 → 归入；没有 → 按模板新建（新业务只填本次涉及的节，其余留待后续需求补）
2. **增量起草**：只改被本次事件影响的节，不重写全文（模板与文风红线见 `references/业务文档模板与文风红线.md`）

**变动不进知识库，落独立记录（2026-10-15 用户口径）**：业务更改、bug 修复等变动**不在知识库追加历史条目**（否则容量极速增大），知识库正文只把受影响内容**更新为最新现状**；变动本身**照记**，但落在知识库外的**独立改动记录体系**——`改动记录` 技能的短记 `Logs/` 与长记 `Blogs/`，仓库提交记录承载明细。

## 分流：需求沉淀 vs 缺陷修复沉淀

一句话：**改业务语义（应该是什么）走需求沉淀 → `business/`；改实现认知（哪里容易错）走缺陷沉淀 → `modules/` 坑节 + `Logs/`**。对照表与升级路径见 `references/沉淀分流规则.md`；拿不准是否动了业务语义 → 问用户。

## 交互模式（按链路分两种）

| 链路 | 模式 |
|---|---|
| **日报 / 改动记录链路**（**公司库** `日报采集共写`、`日报撰写`；`改动记录` 收尾） | **连续沉淀**：工作总结写完、告知用户后**不停顿、不询问**，直接起草 → 自检 → 落盘 → 刷 `_map.md`，汇报带「沉淀清单」，用户**事后可打回**（说「沉淀错了/改掉某条」即修正） |
| **其余链路**（`方案` 锁定阶段、用户点名「沉淀一下」） | 起草 → 用户一字裁决（**落** / 跳过 / 改后再落）→ 落盘 |

质量底线两种模式一致：起草后必须过八条文风自检，不过不出稿；被打回的文档必须用人话重写，不得原样再交。

## 体量守恒（写法铁律）

文档 = 业务**当前态**的描述，不是历史日志；文本量与业务生命周期同步（新业务 0 → 上线时到峰值 → 大动作台阶式变动 → 稳定期微增量平稳）。

- **稳定期改写优于追加**：小需求只改写现有条目，**不加节**（八节模板节数固定）
- **坑节合并同类项**：坑 = 当前仍需防范的，不是修过的 bug 流水；过时的坑删除或压缩成一句防范规则
- **变动不进知识库**（2026-10-15 用户口径）：业务更改、bug 修复的变动**照记**，但落独立改动记录体系（`改动记录`：`Logs/` / `Blogs/`）；知识库只写当前实现，不追加历史
- **大动作台阶式重写**：大版本/重构允许大量改写或大量新增，**禁止新旧描述并存**
- 体量反常即写法异常（稳定期持续增长 / 上线后体量过小 / 无大动作暴涨）→ 精简或补课，处置规则固化在 `_map.md` 使用说明

## 沉淀什么、不沉淀什么

只沉淀**读代码读不出来的**。取舍自测：**「下次有 agent 再开发到这里，还要不要花同样的理解成本？」要 → 沉淀；不要 → 不沉淀。** 量化近似：`价值 = 获取成本 × 复用频率 × 稳定性`，三项都高才动笔。

- ✅ 沉淀：业务口径（glossary）/ 模块知识卡 / 硬约束与不变量 / ADR / 坑与教训 / 工程口径与演进快照
- **以当前代码实现为基准（2026-10-15 用户口径）**：代码实现的现状**照实记录**——实现就是现状；代码未实现的不记录，或作为「待实现目标」单独记录；业务预期与实现冲突 → 照实现状记录之外，**再记为可能的缺陷（bug）待纠正/修复**；业务更改、bug 修复等**变动不进知识库**（照记，落独立改动记录体系——`改动记录` 的 `Logs/` 与 `Blogs/`）
- ❌ 不沉淀：代码结构本身（GitNexus 管）、日报流水账（`Reports/` 管）、调试过程（只留根因 + 一句修法）、30 秒能从代码看出来的、未验证的猜测（要么验证后落，要么标 `confidence: 低` 且不进地图推荐位）

## 与其他 skill 的关系

**落笔人铁律（2026-10-17 用户口径）**：下表每一处"挂载"的沉淀动作，**落笔人 = 触发它的那个 agent** —— 它刚改完代码、刚弄懂口径，正是沉淀时机。**"提醒 / 建议"不是终点，不许把落笔甩给用户或别的会话**（实录：agent 只输出"建议按知识沉淀归位更新"，被用户当场质问「你只建议？那你让谁来更新？」）。允许只记一行「待沉淀」推到当日总结补齐，但**不能只报告不入库**。

**标「公司库」的挂载点在另一个仓库** `lingchuang-skills`（TAPD / CNB / 日报 / 需求拆解 / 分支流水线）；**没装就跳过该行**——跨库引用一律条件引用，不许写成硬依赖。

| skill | 关系 |
|---|---|
| **公司库** `日报采集共写` / `日报撰写`（`lingchuang-skills`，没装则跳过本行） | 连续沉淀链路：总结写完告知后接着沉淀，不断不问，事后可打回 |
| `代码审查`（影响面与回归） | 影响面结论归位模块卡更新；发现文档与实现不符 → 顺手修正 |
| `改动记录` | 长记完成 → 坑上翻对应模块卡「坑」节（并按体量守恒合并同类项） |
| `方案`（锁定阶段） | 归档时从主题提炼 ADR 落 `Knowledge/adr/`（决策摘要 + 回链 Plans 主题） |
| `生成提交` | 防腐烂检查：diff 命中模块卡 `module` 路径 → **本 agent 当场归位该卡**（改写对应节 + `updated` 改当天）；无命中且属需求 / 功能改动 → 当场建最轻一份（知识空白信号，2026-10-16——无命中静默会让新知识永远进不来）；可记「待沉淀」当日补齐，**但不许只报告不入库**（2026-10-17 口径：提醒即落笔） |
| `方案`（讨论阶段） | 消费侧：讨论前读相关 `adr/` 与业务文档，防重复决策、防推翻已定口径 |
| `开发中规范` | 只做**轻标记**：发现新坑/新口径/与卡不符，记一行「待沉淀」，不打断开发——**这行标记由本会话在收尾 / 总结时补齐，不许只标不落笔**（同「落笔人铁律」） |
