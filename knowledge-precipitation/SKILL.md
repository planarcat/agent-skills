# 知识沉淀（总入口 · 底层 kb-skills 体系）

**为什么换**：旧体系（工作区 `Knowledge/` + 手工维护 `_map.md`）跑了几个月，agent 开发了很多需求，沉淀量却很小——问题出在「结构靠自觉、无查重、无 lint、无主动提议」。新体系（`@optima-chat/kb-skills`，MIT，v0.9）用**结构化 wiki + 查重 + lint + 对话结论主动捞取**解决这几点。

## 底层体系一览

**所有知识库都在全局 `~/kb/` 下**（不在工作区里），每个库一个子目录、独立 .git：

```
~/kb/
├── REGISTRY.md          # 所有库的登记表（库 → local_dir → 路径）
├── PROGRESS.md          # 工作日志
└── <slug>/              # 一个知识库（如 lingchuang-engine）
    ├── AGENTS.md        # 本库的 agent 维护规则（运行契约）
    ├── index.md         # 稳定导航
    ├── log.md           # 演化日志
    ├── raw/             # 原始资料（文章 / PDF / 摘录）
    └── wiki/
        ├── overview/    # 综述页（一个主题一篇）
        ├── entities/    # 实体页（一个业务对象/模块一篇）
        ├── sources/     # 来源页（一份材料一篇）
        └── analyses/    # 分析页
```

**CLI**：全局已装 `kb` 命令（`bun add -g @optima-chat/kb-skills`）。常用：`kb lint`（坏链 / orphan / 缺索引）、`kb list`、`kb sync`（配了 `KB_BACKEND_URL` 才用）、`kb migrate`。**升级**：`bun add -g @optima-chat/kb-skills@latest`。

## 路由（按意图分流到 6 个子 skill）

| 用户意图 / 场景 | 走哪 | 一句话 |
|---|---|---|
| 「建个知识库 / 把这个项目管起来」 | `initializing-kb` | 建 `~/kb/<slug>/` + AGENTS.md 契约 + wiki 骨架 |
| 「把这份资料 / 文章 / 链接沉淀进去」 | `ingesting-sources` | 外部素材首次落库：来源页 + 待更新清单 |
| 「沉淀一下 / 记住这个 / 这个结论存一下」 | `capturing-takeaways` | **对话结论捞取**：agent 主动提议（至多 3 条）→ 查重 → 用户点头才落盘 |
| 「更新受影响的页面」 | `updating-related-pages` | ingest 后同步实体页 / 综述页 / 交叉链接 |
| 「基于知识库回答 XXX」 | `querying-the-wiki` | 先查 wiki 再答，答完高价值结论回写 |
| 「检查一下知识库」 | `linting-the-wiki` | 结构 / 债务 / 缺口体检 |

**子 skill 正文是执行标准**：路由命中后 Read 对应 `SKILL.md` 全文再动手，不要凭本页概述执行。

## 挂载点（收尾自动触发 · 落笔人铁律不变）

**落笔人 = 触发它的那个 agent**——它刚改完代码、刚弄懂口径，正是沉淀时机。**「提醒 / 建议」不是终点，不许把落笔甩给用户或别的会话**；允许记「待沉淀」一行推到收尾补齐，但不能只报告不入库。

| 挂载自 | 收尾动作（都走 `capturing-takeaways` 语义：提议 → 查重 → 点头落盘） |
|---|---|
| **公司库** `日报采集共写` / `日报撰写`（没装则跳过） | 日报收口后，把当天「值得长期记住」的结论（至多 3 条）提议沉淀 |
| `代码审查`（影响面与回归） | 影响面结论里「下次还要花理解成本」的点提议沉淀；发现 wiki 与实现不符 → 顺手修正 |
| `改动记录` | 长记完成后，把坑与教训提议沉淀（查重后更新既有实体页，不无脑新增） |
| `方案`（锁定阶段） | 归档时把关键决策提议沉淀为 analyses 页（带回链 Plans 主题） |
| `生成提交` | 防腐烂：diff 命中已有实体页的模块 → 提议更新该页；无命中且属功能改动 → 提议新建最轻一篇（知识空白信号） |
| `开发中规范` | 轻标记「待沉淀」的接收方，收尾时转成 capturing-takeaways 提议 |

**标「公司库」的挂载点在另一个仓库** `lingchuang-skills`；没装就跳过该行——跨库引用一律条件引用。

## 沉淀判定（沿用旧口径，与新体系对接）

- ✅ 值得：数字红线与阈值、拍板过的打法、踩坑教训、反复用得上的事实、业务口径、硬约束、关键决策
- ❌ 不值得：一次性细节（单号 / 某次报价）、闲聊、随手可查的公开事实、未验证的推测
- **先查重再提议**（capturing-takeaways 内置）：库里已有同主题 → 提议「更新既有页面」而非新增
- **无来源不落盘**：每篇带来源（需求 id / commit / 讨论主题）——对应 wiki 的 `sources/` 页
- **宁缺毋滥**：过时的知识比没有更危险；lint 与更新优先于新增

## 与其他 skill 的关系

| skill | 关系 |
|---|---|
| `改动记录` | 分工：它记**过程**（Logs/ / Blogs/），本体系记**结论**（wiki 当前态）；变动明细不进知识库 |
| `日报采集共写` / `日报撰写`（公司库） | 日报记当天干了什么；收口后触发本体系的提议沉淀 |
| `querying-the-wiki` | 开发中查业务问题：先查 wiki → 不够再 GitNexus → 再现读代码；查到的答案即待沉淀内容 |
| `linting-the-wiki` | 定期体检（建议每周或每需求收尾跑一次），产出补课清单 |

## 存量迁移（未做，待用户拍板）

各工作区旧的 `Knowledge/`（灵创引擎等）**没有自动迁移**：内容量小，建议在 `~/kb` 建对应 slug 的库后，把存量业务文档按 `ingesting-sources` 逐篇 ingest 成 sources/entities 页，而不是整目录硬拷。迁移期间旧 `Knowledge/` 只读保留，两边不双写。
