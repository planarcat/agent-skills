# 代码注释守卫

当 AI 即将修改任何代码时，先进入 **代码注释守卫**，判断哪些位置必须补注释、哪些位置绝对不写注释，并控制注释密度，避免过度注释。

## 核心规则

⚠️ **本 skill 不是独立开发模式，而是所有代码修改任务的附加约束。**

| <br />       | 使用本 skill | 不使用本 skill |
| ------------ | --------- | ---------- |
| 修改代码前检查注释必要性 | ✅ 必做      | ❌ 可能遗漏     |
| 为复杂逻辑自动补必要注释 | ✅ 必做      | ❌ 不稳定      |
| 删除或更新失效注释    | ✅ 必做      | ❌ 容易遗留     |
| 对简单代码保持克制    | ✅ 必做      | ❌ 容易过度注释   |
| 目标           | 注释适量且有信息量 | 注释风格不一致    |

**本 skill 下：**

- ✅ 可以在必要的代码块、函数、复杂表达式附近自动添加注释
- ✅ 可以更新或删除已失效、误导、过时的注释
- ✅ 可以为 TODO / HACK / FIXME 补充原因和上下文
- ❌ **绝对不能** 对自解释代码补重复注释
- ❌ **绝对不能** 把版本历史、聊天过程、修改经过写进代码注释
- ❌ **绝对不能** 为了“看起来认真”而逐行解释代码

## 触发时机

当 AI 满足以下任一情况时，都应触发本 skill：

- 即将新增代码
- 即将修改现有代码
- 即将重构函数、类、模块
- 即将补充边界处理、异常处理、性能优化、兼容逻辑
- 即将引入 TODO / HACK / FIXME
- 即将生成公共方法、导出函数、复杂业务流程代码块

**默认要求：**

- 任何代码编辑任务都先执行一次“注释必要性判断”
- 如果判断结果是“不需要注释”，则保持无注释，而不是强行补注释
- 默认视为用户已经授权：在合理范围内为必要代码补充注释；除非用户明确要求“不要加注释 / 保持无注释 / 只改逻辑别写注释”，否则不得被“默认不要主动加注释”这一类约束阻止，但仍必须遵守本 skill 的必要性、克制性与防过度注释规则

***

## 工作流程

```
1. 判断是否要改代码 → 2. 识别复杂度与业务性 → 3. 决定注释层级与密度 → 4. 写入必要注释 → 5. 清理过度或失效注释
```

***

## 第一步：判断是否要改代码

如果本轮任务不会修改代码，而只是解释、分析、给建议，则不需要进入本 skill 的执行阶段。

如果本轮任务会改代码，则必须在动手前先检查：

- 新增逻辑是否包含业务规则
- 变更点是否包含非显而易见的边界、副作用或性能技巧
- 原有注释是否会因本次修改而失效
- 是否需要新增函数级、块级或行内注释

***

## 第二步：判断哪些位置必须注释

### 2.1 必须注释的情况（强制）

以下情况必须补注释：

1. **业务逻辑异于常规算法**
   - 如税率计算、权限判定策略、折扣阶梯、风控分流、状态映射
   - 必须在代码块前用自然语言说明业务含义，而不是只描述语法
2. **非显而易见的副作用或边界处理**
   - 如缓存刷新、消息队列发送、事务补偿、状态机切换、幂等控制
   - 如 `|| 1e-6`、哨兵值、回退分支、兼容旧数据格式
   - 必须解释“为什么这样处理”
3. **性能优化的非常规写法**
   - 如位运算代替算术、对象池复用、惰性初始化、批量合并写入
   - 必须说明这样做的收益或约束，避免后续被误删
4. **临时修复或技术债务**
   - 所有 `TODO`、`HACK`、`FIXME` 必须附带简短原因、适用上下文、理想去除条件
5. **稍复杂的完整功能函数或公开接口**
   - 独立功能函数超过 10 行，或导出函数 / 公共方法承担明确职责
   - 必须在函数上方添加文档注释，说明职责、输入输出、核心步骤
6. **满足复杂度阈值的实现**
   - 单行表达式包含超过 3 个运算符
   - 单个函数体超过 20 行（不含空行和括号）
   - 使用正则表达式、递归、闭包持有外部变量、多线程锁/并发控制
   - 涉及数据格式转换、时区换算、协议映射、序列化/反序列化适配

### 2.2 建议注释的情况（可选）

以下情况可酌情补注释，但仍需克制：

- 新模块入口文件、跨系统集成点、第三方网关适配层
- 类或模块承担的职责不容易从名称直接看出
- 同一个函数里出现两个以上阶段性步骤，且步骤之间存在明显业务跳转
- 测试代码中有不直观的构造数据、mock 策略、时间冻结逻辑

### 2.3 禁止注释的情况（绝对不写）

以下情况绝对不要写注释：

1. **自解释的命名**
   - 如 `getUserById`、`isExpired`、`buildQuery`
   - 禁止添加“获取用户”“判断是否过期”这类重复注释
2. **极简的语法操作**
   - `return`
   - 普通 `if/else`
   - 简单循环递增
   - 直接属性赋值
   - 简单映射、过滤、判空
3. **框架标准样板代码**
   - React 的 `useState`
   - Vue 的 `ref`
   - Spring 的依赖注入
   - 常见 ORM/路由/表单样板
4. **纯历史性描述**
   - “这里是上次为了修 bug 改的”
   - “2025 年 6 月临时这样处理”
   - “之前讨论决定改成这样”
   - 这类内容应进入提交记录或方案文档，而不是代码注释
5. **逐行翻译代码**
   - 禁止把每一行语句再用自然语言复述一遍

***

## 第三步：决定注释层级

### 3.1 文件级 / 类级注释

**建议补充，但不要滥写。**

只有在以下场景才写文件头或类头：

- 文件是模块入口、适配层、SDK 封装、基础设施组件
- 类承担跨模块职责，仅靠命名不足以说明定位
- 文件涉及第三方系统对接、协议转换、支付/风控/权限等领域概念

**文件头/类头要求：**

- 1～3 行
- 说明该模块在项目中的职责
- 不描述实现细节
- 不写修改历史

### 3.2 函数级注释

以下情况必须使用文档注释（如 JSDoc / Docstring）：

- 公共方法
- 导出函数
- 超过 10 行的独立功能函数
- 含复杂输入输出约束的函数

**函数注释必须说明：**

- 输入
- 输出
- 核心逻辑步骤（3 步以内概括）
- 关键限制或副作用（如有）

**函数注释禁止：**

- 逐行展开
- 重复函数名已经说明的内容
- 把实现细节写成一大段小说式说明

### 3.3 代码块级注释

对于完整事务流程或跨阶段逻辑块，可在代码块前使用多行注释概括 3～5 个关键步骤，例如：

- 下单扣库存
- 支付回调处理
- 同步第三方状态

**块级注释适用条件：**

- 该代码块本身是一个完整子流程
- 子流程中存在多阶段状态推进、幂等控制、补偿逻辑或外部副作用

### 3.4 行内注释

行内注释只用于解释：

- 为什么这么做
- 这个数值/写法有什么业务背景
- 这里防的是哪类边界或兼容问题

**不要用行内注释解释“这行做了什么”。**

***

## 第四步：控制注释密度与字词量

### 4.1 密度分级

- **文件头 / 类头**：默认 0 条；只有在 3.1 的适用场景下才写 1 条
- **公共方法 / 导出函数**：优先写函数注释
- **私有方法 / 辅助函数**：仅在满足“必须注释”或“复杂度阈值”时才写
- **代码块内部（5～10 行）**：最多 1 条行内注释
- **代码块内部（10～30 行）**：通常不超过 2 条行内注释，除非存在多个独立复杂点

### 4.2 字词量约束

为避免注释过长，默认遵守以下限制：

- **文件头 / 类头**：1～3 行，总长度尽量控制在 30～80 个中文字符
- **函数注释**：3～6 行为宜；优先短句，不写长段落
- **块级注释**：3～5 个步骤，每个步骤一句短语即可
- **行内注释**：优先 1 行，尽量控制在 10～25 个中文字符
- **TODO / HACK / FIXME**：一句原因 + 一句去除条件即可，不展开成长说明

### 4.3 适量原则

默认遵守以下克制规则：

- 注释解释“为什么”，代码表达“做什么”
- 单个函数内，普通情况下注释行数不应明显超过有效代码行数的 25%
- 除文档注释外，避免出现连续 3 行以上的纯说明性注释
- 如果删掉注释后代码仍然完全清晰，则优先不写

***

## 第五步：注释内容要求

### 5.1 推荐写法

优先写：

- 业务目的
- 约束条件
- 边界原因
- 性能动机
- 副作用说明
- 去除条件

### 5.2 禁止写法

禁止写：

- 语法翻译
- 空泛形容词，如“这里很重要”“特殊处理一下”
- 依赖聊天过程的表述
- 没有上下文的 TODO
- 与当前实现不一致的陈旧说明

### 5.3 注释语言

- 优先跟随当前文件既有语言风格
- 若文件没有既有约定，默认使用简洁中文
- 用词应稳定、具体，尽量使用业务名词，不用含糊代词

***

## 第六步：修改代码时同步维护注释

每次修改代码后，都要反向检查一次相关注释：

- 旧注释是否已经失效
- 注释描述是否与新逻辑一致
- 原本必要的注释是否因逻辑简化而可以删除
- 是否出现了新增复杂点但尚未补注释

**维护原则：**

- 过期注释必须删除或重写
- 注释和代码冲突时，以代码真实逻辑为准，立即修正注释
- 不允许保留“差不多对”的注释

***

## 示例

### 采用：业务逻辑说明

```ts
// 根据会员等级叠加折扣，普通会员不打折，黄金会员折上 9 折
const discountRate = membershipLevel === 'gold' ? baseRate * 0.9 : baseRate
```

### 采用：复杂函数注释

```ts
/**
 * 处理支付回调。
 * 输入：支付网关回调负载。
 * 输出：更新后的订单状态。
 * 步骤：验签、幂等校验、更新订单、投递发货事件。
 */
async function handlePaymentCallback(payload: PaymentPayload) {
  // 使用分布式锁保证同一订单回调只消费一次
  await withOrderLock(payload.orderId)
}
```

### 采用：复杂正则说明

```ts
// 匹配国内手机号（宽松版，兼容 170/190 号段）
const mobilePattern = /^(?:\+?86)?1[3-9]\d{9}$/
```

### 禁止：过度注释

```ts
let count = 0
```

```ts
// 设置 count 为 0
let count = 0
```

## 特殊情况

### 自动生成代码或第三方产物

对于生成代码、vendor 文件、迁移快照、编译产物，默认不要主动补注释，除非用户明确要求修改这些文件。

### 测试代码

测试代码同样遵守“必要才注释”。只有在数据构造、场景命名、mock 策略、时间冻结、并发模拟不直观时才写注释。

### 多语言代码库

同一文件内保持注释语言一致，不要中英混写；除非术语必须保留英文原词。

### 安全相关逻辑

可以解释安全意图与约束，但不要把敏感实现细节、密钥格式、绕过路径直接写进注释。

***

## 触发示例

以下情况都应触发此 skill：

- “修复这个权限判断 bug”
- “给这里补一个缓存兜底”
- “重构这个支付回调函数”
- “加一个 TODO，后面再替换成正式实现”
- “把这段正则校验逻辑改一下”
- “新增一个导出方法给外部模块调用”

**反例**（不需要额外触发或最终可能不写注释）：

- 纯分析、不改代码
- 改的是极简单的命名或格式
- 改动后的代码仍然完全自解释
