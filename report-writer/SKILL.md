# Report Writer（日报编写 · v3 TAPD 对齐版）

## 最高原则：规范 > 用户口径 > 技能建议

1. **规范**（最高）——`references/spec.md`（v3.1，飞书 rev 67）。三条铁律、四条栏位硬规则、虚报双向口径，不得因"方便"打折。
2. **用户口径**——何成标的历次裁定，**仅在规范未覆盖处生效**；与 v3 冲突的旧口径一律作废（见下方「v2 口径作废清单」）。
3. **本技能的设计建议**（流程、字段、提问时机）——只是实现规范的手段，被质疑就先回查规范原文，查不到依据的退位让行。

**v2 已作废**：原《日_周_月报统一内容标准与管理规范（v2 · 错误强化·考核联动版）》在飞书标「(过期)」，存档在 `references/spec-v2-archive.md`，仅供对照，**不再作为填报依据**。判断某条旧习惯还算不算数，先回 v3 spec 查。

## 适用范围（用户口径 · 2026-09-16 起，09-19 扩到周报）

**日报为主**（本技能的主流程）；**周报按需写**（用户 09-19 直接点了「编写本周周报」，走 v3 spec §4 的八栏，见下面「附：周报」节）。

- 月报在 v3 里**员工不填写**（管理者产出）；周评是试用期每周 1v1，不填表，本技能都不碰。
- **周报的坑**：它比日报依赖更多"只有系统才知道的数字"（绑定一致率、停滞任务数、无单工作条数）。本地作业时**能算的算、算不了的说清楚**（如"本栏需要系统口径"），绝不编一个百分数出来。

## Overview：v3 到底是干什么的

> **v3 把"填报表"改成"对数据"。你能从 TAPD 查到的，一个字都不用写；TAPD 查不到的，才是你真正要写的东西。**

日报从 8 个模块压到 **5 栏**，手填内容只剩 **4 处**，填报时间从约 20 分钟降到约 3 分钟。日报**唯一不可被系统替代的价值**就是两项新增 + 两项手写：

| 手写项 | 为什么只有你能写 |
|---|---|
| **执行差异** ★ | TAPD 只记结果，不知道任务**晚了几天、为什么晚** |
| **协同人** ★ | TAPD 只有 `owner`，**没有实际配合关系**；你配合了别人但你不是 owner 的活，不写就在数据里不存在 |
| **需求理解与方案输出** ★ | 返工和事故几乎都起源于**没被写下来的边界分歧** |
| **卡点 / 异常 / 明日计划** | 外部依赖与下一步判断，系统算不出来 |

**三条禁则（违反直接打回）**：日报不许复述 TAPD；周报不许是日报拼接；月报不许让员工填。

**分层**：采集与共写归 `report-pipeline`（共享日报协议），分拣去噪归 `report-draft-filter`，收口与规范裁定归本技能。三者冲突时一律以 `references/spec.md` 为准（落盘与协作方式以 2026-09-22 共享日报口径为准）。

## 共享日报收口（2026-09-22 用户口径）

日报的日常维护已改为**共享日报**：`<工作区根>/Reports/daily_work/YYYY-MM-DD.md`，每工作区每日一份，所有 agent 会话按 `report-pipeline` 的共写协议直接更新自己会话的内容（分支维度小节 + 会话记录）。本技能的「成型」在共享日报上执行，**不再另立成稿文件**：

1. **读最新共享日报**（用户可能手改过，以文件现状为准；跨工作区按 pipeline 规则收齐）。
2. **补「今日总览」**：汇总各分支「工作总结」，2~4 句。
3. **逐分支核对必填**：TAPD ID（拿不到问用户，不许编）、四要素、执行差异、协同人（owner 非本人必填）、**每个工作节点的时间要素 `[HH:MM]`（缺的补上）**——差异与协同人**只有本人知道**，缺口一次问齐。
4. **合并重复表述**：同分支多会话的工作总结去重；任务行全日合计 ≤3 条（压不下去向用户说明）。
5. **卡点 / 异常 / 明日**：卡点 6 项齐、确无写「无」；明日 1~3 项带 TAPD ID；无单工作 ≤1 条。
6. **TAPD 状态前置动作**：日报状态比 TAPD 靠前 → 先改 TAPD 再收口（见下「数据源」）。
7. **跑机械自检**（下一节），命中先改。
8. **交付**：共享日报即最终日报；需要正式 v3 五栏提交文本（评分器按五栏解析）时，从收口后的共享日报一次性生成并直接交付，**不在工作区另存第二份日报文件**。

## 日报模板（v3 · 五栏 + 复盘）

```
【日报】何成标 / YYYY-MM-DD

① 今日任务对齐（TAPD 已带出，你只标差异 + 记动作）
   #<任务ID> <任务名>｜类型:技术开发/文案内容｜状态:〔同步·中文语义〕
     owner:〔同步〕｜协同人:＿＿＿
     差异:一致 / 提前 N 天 / 滞后 N 天 / 阻塞 / 与 TAPD 不符
     今日动作(动工细节):＿＿＿
     交付物/标准:＿＿＿
② 需求理解与方案输出（有变化才写，无变化写"—"）
   需求理解:＿（边界、歧义、待确认点）
   方案输出:方案名 + 链接 + 版本 ／ 方案推进至:第 N 段
③ 卡点与阻碍（必填，无则写"无"）
   分类(技术/对接/需求/资源)｜内容｜是否需协助｜对接人｜期望解决时间｜影响:
④ 异常与需协调事项（无则写"无"）
⑤ 明日计划（1~3 项，必须带 TAPD ID 或标注"无单工作"）
⑥ 复盘（1~2 句，第一人称白话）
```

**任务行 ≤3 条**。超过 3 条 = 任务切太碎或多线并行，组长当日必问（§3.4 不合格判定）。

> **与共享日报的关系（2026-09-22 口径）**：五栏是**内容要求**；日常承载在共享日报的分支小节与工作区级小节里（结构见 report-pipeline），其中「今日动作」在共享日报里就是带 `[HH:MM]` 时间的「工作节点」列表。需要正式五栏提交文本时，由本技能从收口后的共享日报一次性生成并直接交付，不另存文件。

**⑥ 复盘（2026-09-19 用户拍板新增，与 v3 原口径的临时处理）**：
- 背景：日报评分器**仍考「复盘深度」**——2026-09-18 实测，日报没有复盘块被扣到 **35 分**（虽与"v3 复盘移周报"的规范冲突，但先按评分器口径执行，冲突待与主管确认）。
- 写法：**1~2 句**，第一人称白话，写当天**具体的一件事**（踩坑 + 结果 / 一个教训）；禁格言式开头、禁"要…要…"排比说教、不写成长篇；完整复盘仍归**周报⑥**（AI 只提纯不代下结论的规则不变）。
- 自检：日报末尾必须有这 1~2 句；没有 = 复盘深度直接掉到 35 分。

## 逐栏硬规则

### ① 今日任务对齐 —— 日报的第一动作

打开日报第一件事不是回忆今天干了什么，而是**逐条标出执行差异**。

| 要素 | 怎么写 | 判断标准 |
|---|---|---|
| **差异** ★ | 一致 / 提前 N 天 / 滞后 N 天 / 阻塞 / 与 TAPD 不符 | **日报唯一不能被系统替代的判断**；不标 = 不合格 |
| **协同人** ★ | 手写姓名 + 角色 | **`owner` 不是你时必须填**，空置扣分 |
| **今日动作** | 今天具体动了什么工 | 禁止"继续开发""按计划推进""进展顺利" |
| **交付物/标准** | 交付了什么 + 达到什么量化标准 | 四要素见 v3 §6 |

**差异栏会被机器逐条比对，不是自由文本。** 系统拿 TAPD 的计划完成时间/实际完成时间比：

- 标「提前 N 天」/「滞后 N 天」→ 与 TAPD 时序对不上就标黄，**拒不改正按虚报**；
- 标「与 TAPD 不符」→ **当日必须把 TAPD 改对，标它不免责**；
- 标「阻塞」→ 无机器基准，进卡点栏人工核对。

> **配套动作（每天多 30 秒）：状态即时更新是交日报的前置动作。** 发现 TAPD 状态没跟上 → 先去 TAPD 改状态，再交日报。不要用日报去追认一个 TAPD 里还不存在的状态。

**状态列与 `owner` 标 `〔同步〕`，不能改、不要手填。** 状态一律写**中文语义**，不写 raw key：

| TAPD raw key | 写出来 | 含义 |
|---|---|---|
| `planning` | **评审中** | ⚠ **正在等人评审方案，不是"还没开始"**；卡住时追责对象是评审人/排期 |
| `developing` | 开发中 | 正在写代码 |
| `status_3` | 待测试 | 已提交测试，等测试接收 |
| `status_4` | 测试中/待验收 | 测试进行中或等验收 |
| `resolved` / `closed` | 已闭环 | 走完终态 |

> **「开发完成」不是闭环。** 考核的闭环率只统计走到 `resolved`/`closed` 的任务。

### ② 需求理解与方案输出 —— 有变化才写，但进了开发中之前必须写过一次

| 写什么 | 要求 | 反例 |
|---|---|---|
| **需求理解** | **边界、歧义、待确认点**，不是复述需求 | ✗「理解了退款拦截需求」<br/>✓「"自动修复"只覆盖格式类异常，内容类仍需人工复核——已与产品确认边界」 |
| **方案输出** | 方案名 + 链接 + 版本 + 推进到第几段 | ✗「方案在写了」<br/>✓「【高清图检测方案】<链接> v1，推进至第④段异常分支」 |

**硬规则**：需求在**首次进入「开发中」之前必须至少写过一次「需求理解」**，一次都没写就开工 = 不合格日报。

这一栏与方案评审 SOP 咬合：开工校验（卡片 1）→ 8 段式方案（卡片 3）→ 异常穷举（卡片 2）→ 组长 6 维打分 ≥70 → 闸门① 才能进开发。详见 `references/sop-v3.md`。

### ③ 卡点与阻碍 —— 必填栏

必带 6 项：**分类（技术/对接/需求/资源）｜内容（具体到接口名、人名、数据）｜是否需协助｜对接人｜期望解决时间（月-日）｜影响（天数或范围）**。

- **空置即标黄；连续 2 日空置触发问询。** 确无卡点写「无」，不能留空。
- 对接人写**具体姓名**，不写"后端/平台端"角色归因；涉及主管写「欧阳老师」。
- 同一事实可同时出现在「③卡点」和「④异常」两处（09-17 用户确认），两处都留。

### ④ 异常与需协调事项

需求变更、临时会议、跨部门对接、AI 查出的新异常分支。**无则写"无"。** 这一栏是周评捞证据的地方。

### ⑤ 明日计划（1~3 项）

每一项必须带 **TAPD ID**，或显式标注 **"无单工作"**。

- **无单工作上限：每人每日 ≤1 条**，需组长当日确认；技术债、重构、调研、线上热修、支撑答疑应开 `技术任务` 单。
- 连续 3 日出现无单工作 → 视为流程缺口，组长补建任务类型，**不追责个人**。

## 交付标准四要素（v3 §6，所有任务适用）

每条任务必须能回答这四个问题，**缺一个即不合格**：

| 要素 | 说明 | 反例 |
|---|---|---|
| **执行内容** | 具体做了什么 | 「继续开发 xxx」 |
| **当日交付物** | 交付了什么可验证的东西 | 「（100%）」 |
| **交互结果** | 别人/别的系统能拿到什么 | 「已完成」 |
| **量化质量标准** | 达到什么标准算合格 | 「没问题」 |

合规示例：`完成退款弹窗页面结构开发，交付可交互页面，UI 1:1 还原、无报错、异常分支覆盖 4 条`

## 红线与虚报（v3 §8，最重要）

### 虚报的客观定义：**报表与 TAPD 不一致 = 虚报，双向、不分方向。**

| 情形 | 判定 |
|---|---|
| 报表状态比 TAPD 更靠后（往好里报） | **虚报**，进红线闸门 |
| 报表比 TAPD 保守（TAPD 已闭环但没写） | **虚报**，进红线闸门 |
| 日报写了 TAPD 不存在的任务 ID | 虚报（等于编造任务） |
| 状态变更时序晚于日报提交时间 | 虚报（当前靠人工抽查） |
| 差异栏标「与 TAPD 不符」 | **不免责**——是说明原因的入口，不是免责入口 |

> **罚的是"对不上"，不是"坏消息"。** 按 TAPD 如实写滞后、阻塞、返工，两者始终一致，**永远不会触发虚报**——"如实暴露不亏"在新口径下依然成立。

**核对方式是「按任务逐条查询」**：系统把日报里每个 `#<任务ID>` 单独拿去 TAPD 查当前状态。**ID 是这条链路的唯一入口，别手抄错。**

**宽限期**：第 1 周清存量（僵尸单/状态/处理人），**前 2~4 周不一致只标黄、不扣分**。

### 红线闸门（命中即重罚，先于加权）

| 命中 | 处理 |
|---|---|
| "正常推进 / 暂无问题 / 一切正常"等敷衍话术 | 风险与影响分 ≤40 并标红 |
| **虚报（报表与 TAPD 不一致，双向）** | 犯错影响分 ≤30 + 标记虚报，主管必看 |
| 颗粒度违规（任务未挂 TAPD、无单工作超限） | 完整性扣 10~20 分 |
| 交付红线缺失（无交付物/标准） | 进度可信度扣 10~20 分 |
| 协同人缺失（`owner` 非本人却未标） | 责任可追溯扣 10~20 分 |

### 不合格判定（组长直接打回，无需解释）

- 事项行无 TAPD ID（且未标"无单工作"）
- 状态或 owner 手填而非同步
- **任务行未标「执行差异」**
- **协作类任务「协同人」空置**（`owner` 非本人时必填）
- **需求在首次进入「开发中」之前从未写过「需求理解」**
- 卡点栏空置（连续 2 日空置 → 触发问询）
- 出现"正常推进/暂无问题/一切正常/进展顺利/按计划执行中"等敷衍话术
- 写了 TAPD 中不存在的任务 ID
- **报表状态比 TAPD 状态更靠后**
- 任务超过 3 条

### 提交与校验

| 项 | 规则 |
|---|---|
| 提交时间 | **次日 09:30 前** |
| 提交日 | 周一至周五（周六日不要求，不计缺交） |
| 自动校验 | TAPD ID 存在性 / owner 是否本人 / 状态是否一致 / 是否属当前迭代 / 时序校验 |
| 校验失败 | **以 TAPD 为准，报表标黄并要求当日修正** |

## 何成标专属口径（v3 适配后仍有效）

以下是**不与 v3 冲突、继续生效**的用户偏好：

- **只写本人/前端工作**：非本人、非前端内容（Java 后端事项、服务费需求评审、裁片库限制等）不写进日报。
- **不写 AI 旁白与元信息**：提交件不出现"给内部核对用"的括号说明、整节"昨日计划完成度核对"、顶部"已按你的要求…"、文末"待补充信息/合规自检"。
- **白话表述，禁专业术语**：让非技术读者看懂。**禁词**：「合入」→「验证通过后部署测试」；git 动作词（已提交/已推送远程/分支名）不写；**不写分期与内部编号**（不写「一期/二期」「阶段一/二」「Phase」「方案一/二」），需求名从头到尾一个称呼。
- **项目名从素材取**：不凭空造新总名、不擅自缩写；本技能**不含项目清单**。归属说不清就问用户，不猜。
- **同一件事只写一条（v3 更严：任务行 ≤3 条）**：同一件工作的不同侧面（画流程图 + 出方案 + 更新文档 + 核代码差异）合一条，用「交付物/标准:A + B + C」并列表达。判据：交付物同属一批、交付时间相同、责任主体相同 → 一条。
- **一次发来的分段摘要 ≠ 多个事件**（09-17 两次被纠正）：两段会议纪要 = **同一场会**，写一条；**参会人只按原文字面取**，不凭"涉及主管就默认主管在场"补人。
- **点名到人，不写角色归因**：协同人、对接人写具体姓名；涉及主管写「欧阳老师」，正文与字段一起改。
- **同日多份素材一律累加**：用户常分多次发来同一天不同线的小结，新素材视为**追加**，不得"后发覆盖前发"；只有同一事项的状态冲突才以新为准。
- **本地环境维护类不写**：工作区改名、本地文件整理、本机配置调整等与岗位产出无关的操作，任何栏位都不写。
- **「已上线」= 已部署生产环境，「已上测试」= 已部署测试环境**；部署去向写在任务行的「交付物/标准」里，不单独占栏。
- **用户会直接手改日报文件**（09-14 实证）→ **每次改日报前先重读文件最新内容**，编辑锚点不用记忆里的旧文本；改完再复查，别把用户的删改覆盖回来。
- **找不到就说找不到**：不得拿别的日期、别的事项顶替；拿不到的真实信息（TAPD ID、参会人、时刻）问一句，**绝不编造**。

## 数据源：日报的「TAPD 已带出」怎么来

v3 假定任务行由 TAPD 自动带出。**在本地作业时，这一步由 AI 用 TAPD 连接器代替系统完成**：

1. 用 `mcp__tapd__get_stories_or_tasks` 按负责人 + 当天日期拉当日任务（三个项目：灵创_用户端 40677205 / 来图 39230945 / 灵创_工厂端 44355585）。
2. 逐条取：`#ID`、任务名、类型、状态（转中文语义）、`owner`。
3. **状态以 TAPD 为准；对不上先改 TAPD，再写日报。**
4. `owner` 不是本人的任务 → 必须让用户手填「协同人」。

> **同步字段改哪一头（09-18 实证）**：`状态` 和 `owner` 只能改 TAPD。用户说"日报里 owner 去掉某某"时，**改日报不改 TAPD 只会造出反向不一致**（报表少一个人、TAPD 多一个人），照样算虚报。动作顺序永远是 **先改 TAPD → 再让报表同步**。
> **改父子结构的 owner 必须级联**：TAPD 子需求各自独立挂 owner，改父不会带着子变。先 `ancestor_id=<父id>` 实查完整子列表（别用记忆里的"父 + N 子"数字，会过时），再逐条 `update_story_or_task`，改完复核；子需求里 owner 只有后端单人、本人不参与的不动。细节见 `tapd-todo-query` 技能的「改 TAPD 同步字段时」节（**没装那个技能时，按本节这套流程走就行**）。
> **状态词认准 §7.1 表反推的 raw key，别认 TAPD 界面名**（09-18 22:57 更正上一条）：机器比对用的就是 §7.1（`planning`=评审中 / `status_3`=**待测试**）。而 TAPD 用户端旧枚举的流转顺序是 `planning`(初稿) → `status_3`(**评审中**) → `developing`(实现中) → `status_4`(测试中) —— **"评审中"在界面挂在 `status_3`、在规范挂在 `planning`，两个不是一回事**。
> 所以：想让日报写「评审中」并合规 → **TAPD 要设 `planning`**（不是 status_3）。09-18 就是设成 status_3 后，日报的「评审中」按表被判成 planning ≠ status_3 → 报表与 TAPD 不一致。
> **改状态前先查工作流**：用户端 `实现中 → 评审中` 不被允许（只能到「测试中」）；`planning → status_3` 才行。查 `get_workflows_all_transitions`；装了 `tapd-todo-query` 的话，流转细则与各项目状态 key 见它的「改状态」节（**没装也不影响，本节流程自足**）。

**跨工作区收素材**（同日报流水线）：① 当前工作区 → ② 会话里出现过路径的工作区 → ③ 日报工作区的 `sources.md` → ④ 仍缺就问一句"今天还在别的哪个目录干过活？"，问一次记进 `sources.md`。

## 生成后机械自检（逐条 grep 级检查，不靠"记得"）

1. **结构齐 + 复盘**：今日总览已填；每个分支小节有「工作总结 + 会话记录」，会话记录字段齐（任务 #ID / 工作节点 / 交付物标准 / 执行差异 / 协同人 / 原文）；**所有工作节点带 `[HH:MM]` 时间要素**；卡点、异常、明日计划、复盘各节齐全（无则「无」）。多出的节（失误与影响、v2 式长篇复盘）**删**。
2. **任务行**：每条以 `#<TAPD ID>` 开头；带 `｜类型:…｜状态:…〔同步〕`；**任务行 ≤3 条**。
2.1 **全文每个 `#1` 开头的编号后面必须紧跟需求标题**：grep 一遍所有 ID，逐个确认后面就是标题（卡点、计划项、需求理解里也不许只写编号）——2026-09-21 定规则、09-23 被再次纠正，属高频违规。
3. **差异栏**：每条任务行都有「差异:」；无差异 = 违规。
3.1 **核心产出每项带一句影响面或量化结果**（覆盖的单量/入口、影响的操作次数等），让「已闭环」有可衡量落脚点——不只写功能名（2026-09-23 评审）。
4. **协同人**：`owner` 非本人的任务行，「协同人:」非空。
5. **卡点**：非空（无则写"无"），6 项齐全，对接人是真名；**待确认口径要带对接人 + 期望回复日期**（不许悬空）
5.1 **排查类卡点写"四件套"**（2026-09-22 评审「异常与协调 90 分」的可复制模式）：① **验证过程**（做了几组对照、分别什么结果）② **结论**（谁有效、谁无效、哪侧无缺陷）③ **待确认口径**（要对方明确哪几个问题、对接人 + 期望日期）④ **同形态扫描**（同一问题别处是否也有，主动点出）。只写"卡在某接口"拿不到高分；**缺陷单提交后把单号回填到日报与任务备注**；滞后项补「剩余步骤 + 目标日期」并说明是否影响下游排期（2026-09-22 评审）。
6. **明日计划**：1~3 项，每项带 TAPD ID 或标"无单工作"，并带**完成判据**——执行多少用例 / 通过判定线 / 缺陷收敛目标；**「进测试线」「上线」这类验收动作要直接写成计划项**；**每项标注时间点与预计投入，冲突时写明取舍顺序**（2026-09-23 评审）。**计划项四件**：动作 + 交付物 + **完成判据**（用例条数/判定线/缺陷收敛目标）+ 日期——只有 ID 和动作 = 计划质量会被扣（09-20 周报 57、09-22 日报 80，两次都是最低分项）。
7. **复盘**：末尾有 1~2 句、第一人称、写了具体的事；没有 = 复盘深度评分掉到 35 分（2026-09-18 实测）。
8. **全文 grep**：`返工:|Bug:|违约责任|责任人:|交付:0|（100%）|（95%）|未完成，未部署|正常推进|一切正常|暂无问题|进展顺利|按计划推进|继续开发|待填|待补充|已按你的要求` → 命中即违规，逐条改。
9. **术语 grep**：`合入|一期|二期|阶段一|Phase|已推送|已提交|分支` → 命中改白话。
10. **排版字符 grep**：**半角波浪号 `~` 一律不写**（09-18 实证）——Markdown 把 `~` 当删除线/格式标记，同一段里出现两个就会**配对吃掉波浪号并画一条删除线**：`（F1~F9 共 9 个功能…）` 在预览里显示成 `（F1F9 共 9 个功能…）` 且被划掉。范围一律写 `F1-F9`、`2-3 秒`、`10-20 分`。同理避开 `*` `_` `#` 开头的裸用法。
10. **元信息**：顶部说明行、文末合规自检 → 删，只留五栏。

- 用户要求"写日报""按规范出日报""日报模板"。
- 用户提到执行差异、协同人、需求理解、方案输出、TAPD 对齐、日报绑定一致率、虚报等 v3 字段。

## 工作流程

1. **确认要写的是日报还是周报**（周报走上面「附：周报」节；周评/月报本技能不覆盖）。
2. **日常更新**由 `report-pipeline` 的共享日报协议负责（阶段完成即更新自己会话的块）；本技能在「出日报」时对共享日报做**收口**。
3. **读共享日报最新内容**（`<工作区根>/Reports/daily_work/YYYY-MM-DD.md`；跨工作区按 pipeline 规则收齐）。
4. **拉 TAPD 任务行核对**（见上「数据源」）：状态转中文语义；日报状态比 TAPD 靠前 → **先改 TAPD 再收口**。
5. **逐分支核对必填**：TAPD ID、四要素、执行差异、协同人——差异和协同人**只有本人知道**，缺口一次问齐，不能猜。
6. **补「今日总览」**：汇总各分支工作总结，2~4 句。
7. **写③卡点 / ④异常 / ⑤明日计划 / ⑥复盘**：卡点必填（无则「无」），明日带 TAPD ID；复盘每会话 1~2 句，AI 可起草，**用户改完才算数**。
8. **合并去重**：同分支多会话的工作总结去重；任务行全日合计 ≤3 条。
9. **跑机械自检**（上一节），命中先改再交付。
10. **交付**：共享日报即最终日报；需要正式 v3 五栏提交文本时一次性生成并直接交付（附合规结论与虚报风险点，若有），**不另存第二份文件**。

## 附：周报（九栏印证版 · 2026-09-19 起以此为准）

**规范源**：飞书《周报填写示例（v3 · 含周末单周样例）》
https://ocnun8rb7n63.feishu.cn/wiki/IihZwInlIihd70kogwWcpfjTnJh
（旧 spec §4 八栏口径作废；本节为执行摘要，冲突以该文档为准。）

**关键口径（与旧版差异）**：
- **周区间 = 周一 00:00 ~ 周日 23:59**；提交 = **次周一 09:30 前**（不是周五下班前）
- 抬头三件：`【周报】姓名 / 第 N 周（YYYY-MM-DD ~ YYYY-MM-DD）` + **周报文档链接** + **提交时间**
- **九栏**：①计划vs实际（计划｜实际｜偏差天数｜归因四选一，**单列 WIP**；「实际」取**日报口径的完成日**，TAPD 状态流转时间只作参照——状态晚改不计进度偏差，2026-09-19 #1002815 实证）②日报印证（**五个数字**：日报提交 X/5、绑定一致率、状态不符、无单工作、需求理解覆盖率 + 不一致项）③方案沉淀（链接+版本+评审分+打回次数；**无版本号当月不计分**）④卡点汇总与升级（卡在谁+期望时间+**我已做的动作**+升级判断）⑤**失误与影响**（失误+Bug 分级 P0-P3+影响量化+本人认领；**本周有卡点/告警却填"无"=虚报，本维度不及格**。**什么算失误（2026-09-19 用户口径）**：只算**造成持续影响**的问题——拖住他人、返工、延期，或方案/判断层面的漏项；**当场发现当场修复、没留下持续影响的一律不算失误**（含开发/测试中暴露的缺陷，也含线上暴露但当场修掉的）。**⑤⑥ 一律写“具体漏了什么”**（如“开工前没和后端对接口字段契约”），不写“缺 XX 一节/一章”这种抽象句式）⑥复盘（亮点/不足写到根因/**下周要改的一条**）⑦风险预警（停滞数+超期清单+最可能出事+我的应对）⑧下周计划（**≤3 项，每项带交付物+完成日期**）⑨需协调（具体对象+不解决的后果；上周提的本周要给进展）
- **① 大偏差必须归到环节（2026-09-20 周报反馈）**：归因不能只写「估时错/被阻塞」，要在括号里写清偏差发生在 **需求 / 方案 / 编码 / 等待** 哪一环，例：`估时错（编码超期）`、`被阻塞（等测试，对接测试·X，期望 09-17 回，超期升级组长）`。**大偏差（≥10 天）另在⑥写 ≤3 行根因**，并给下次估时修正系数或把任务拆成 ≤3 天子项。
- **① 计划列不许留「—」（2026-09-20 反馈）**：没设预计完成时间的工单，**先回 TAPD 补「计划完成时间 + 优先级」再写周报**（前置动作）；只有临时触发的事（线上告警）才允许「—」。
- **产出要带业务侧量化影响 + 上线后验证结果（2026-09-20 反馈）**：不能只有工单号和日期——写清谁受影响、范围多大、上线后谁在何时验证、结论如何。
- **「需求变」要写清释放工时与去向（2026-09-20 反馈）**：释放了 N 人日、挪到了哪个工单。
- **周末口径**：周末处理的问题计入本周①、归因多为需求变/方案返工，并在⑤说明是否暴露自身疏漏；**日报只算工作日 5 天**（② 恒为 X/5），周末的事在**下周一日报**补一条状态变更；周末没做事不凑内容
- ⑤ 最容易踩的坑：周末处理了线上问题却在⑤填「无」→ 与②的状态核对互相印证，判虚报
- **口径/判定标准不写进周报正文**（09-19 用户口径）：像「当场发现当场修不算失误」「实际以日报完成日为准」这类是给写报告的人看的口径，放本节/技能里；交付件只留结论与事实，不写解释性旁白、不写「改进见⑥」这类交叉引用
