# Report Writer（日报/周报/月报编写）

## Overview

本技能依据技术部《日_周_月报统一内容标准与管理规范（v2 · 错误强化·考核联动版）》，
帮助用户快速、合规地编写日报、周报、月报。核心目标：把"责任到人、错误量化、延期天数、
返工次数、时间浪费"从散文变成强制结构与数字，直接喂给《周报四维评分引擎 v2》。

**核心导向**：如实暴露错误与延期不扣分反而给满分；隐瞒、虚报、敷衍倒扣并标红。

**上游采集层**：日常开发中的"什么时候记、记什么、谁提供"由 `report-pipeline` 技能负责（素材卡 → 七模块的机械映射）。本技能是成型层与规范原文载体（`references/spec.md`）；采集层与本技能冲突时，一律以规范为准。

## 用户专属偏好（何成标 · 技术部前端）

在遵守上述 v2 规范的基础上，针对何成标的汇报额外遵循以下硬约束（经 2026-08-18 多轮日报修订确认，已与两份日报格式对齐）：

- **适用范围（2026-09-15 用户口径）：只写日报 + 周评，不写月报。** 周报以《周评绩效考核表》第一部分形式提交（该部分替代本周周报），提交时限仍按规范=每周六 21:00 前；周评的第二~五部分由主管/HR 填写，AI 一律不碰。规范 §7 的月报条款仅作存档依据，当前不触发。
- **只写本人/前端工作**：非本人、非前端内容（如 Java 后端事项、服务费需求评审、裁片库限制等）不写进日报。
- **不要 AI 旁白注释**：日报是给领导看的，不出现"给 AI/内部核对用"的旁白——如括号内说明"属同一个任务"、整节"昨日计划完成度核对"等只用于内部核对的内容，不写入提交件。
- **项目名从素材取，不预设**：项目名称一律用素材/前文已出现的称呼，不凭空造新总名、不擅自缩写；**本技能不含项目清单**（项目随业务变，写死就只对一个项目有效）。同一批工作涉及多个项目时，按素材里的归属分别归位；归属说不清的问用户，不猜。
- **状态表述**："已上线测试"统一表述为"已部署测试环境"。
- **责任内联（9-02 晚「按规范来」定稿，替代早期「交付=部署状态词」写法）**：交付字段按 spec 字面写**完成日期/时刻**：`【责任人:姓名｜交付:月-日 时:分】`。当日完成产出写当天日期：用户给过真实时分就写时分（如 09-02 19:00），只给了日期就写到「09-02」，**没有真实时刻的时:分一律不编造**（真实红线优先于格式字面）。多人协作 `【责任人:甲+乙｜交付:月-日 时:分】`。**部署状态/交付物实情不再占用交付字段**，改写入条目内「交付物:…」描述行，如：交付物:改动并入主版本并已部署测试环境｜交付物:11MB 安装包，已交付雷彤实际使用（未走部署流程）｜交付物:引擎与界面改动，本机实测通过（未部署）。**语义铁律不变**：只有真部署/真交付/真发生才算数——排期（尚未发生的「08-20 上生产」）不得写成已完成交付；上测试/上生产=交付的判断仍有效、只是改在交付物行体现；进度（30%/80%/本地跑通）标标题不占交付字段；状态不重复写两遍。
- **提交件去元信息**：顶部"已按你的要求…"说明行、文末"待补充信息""合规自检"不写入提交件。
- **失误无也显式写**：用 v2 格式 `返工:X｜Bug:无`。
- **规范四要素默认带齐（2026-09-14 对照 spec.md 审计后固化，生成时直接写全、不要等用户审计才发现）**：① 产出标题必须标占比——已部署写「（100%）」，开发完成未部署写「（100%，未部署）」，未进主版本写「（100%，未进入主版本）」；② 进行中每条必须含「进度:…」＋「剩余:…」＋【责任人｜预计:月-日】（纯外部依赖可写条件，如"验收通过后"）；③ 明日计划每条必须含「内容 ＋ 交付物:… ＋ 标准:…」三行（交付物写部署目标或可交付物，如"三处改动部署测试环境"）；④ 每条产出的「交付物:」行要带**交互结果**——写明交付给谁/谁可用（如"客户端可直接安装使用""已交模板录入客户端使用""供三个仓库选用"），不能只写"改动已完成"。
- **失误栏 Bug 行（2026-09-14 用户裁定，覆盖此前"失误栏只写一行"的绝对化写法）**：当已上线功能的问题载入了六、异常与协调（即"别处暴露问题"），失误栏必须同步按 spec 3.3/3.6 补 Bug 五要素行，否则触发规范 §9「填无但暴露问题＝虚报」红线。格式：`返工:无｜Bug:P3 x1【责任人:姓名｜描述:…｜根因:排查中｜已修复:否｜回归:无】`；确无问题才写「返工:无｜Bug:无」，仍不写辩解说明行。
- **单项目区块文字量上限（2026-09-14 立为铁律，用户原话「那个项目文字量太多了，每次总结都要提这点」）**：**体量大的项目区块**（跨端、条目多的）要**少而短**——① 同类合并：同一个客户端/同一批改动并成一条（如「打包工具换 Bun + 对接状态标准 + 界面反馈调整」合成 1~2 条），10 条并到 5 条以内；② 每条正文只留 1~2 句白话，交代"做了什么 + 结果"，随后只跟「交付物:…｜标准:…」一行，禁止罗列字段名、文件数、毫秒数、测试用例数、轮次等实现细节数字堆栈；③ 异常与协调、复盘里的该类条目同样只留结论句，不复述排查过程（可留一句因果）；④ 目标：**任一项目区块篇幅不超过全篇三分之一**。**注意与「四要素默认带齐」不冲突**：压缩的是正文过程描述，占比标注、交付物（含交互结果）、标准三样照旧齐备。
- **白话表述**：不出现专业术语，用通俗白话表达（如"创建分支"→"把功能单独复制到一个新版本里保留下来"），让非技术读者能看懂。**禁词补充（8-31 用户质疑「合入」后沉淀）**：「合入」=合并进主版本，领导看不懂，一律改「验证通过后部署测试」；同理「提交分支」等 git 动作词不写，直接写部署目标。
- **阻塞/协作点名到人**：卡点、协调、依赖一律写具体责任人姓名（如曹银峰、邓志豪），不写"后端/平台端"等角色归因；卡点必须带 对接人+期望时间+影响+协调动作。
- **日报模块顺序**：一产出 → 二进行中 → 三卡点 → 四失误与影响（核心块连续在前）→ 五明日工作计划 → 六异常与协调 → 七个人复盘与思考（独立模块在后）。**注意：8-24 起用户已把「五异常/六明日」互换为「五明日/六异常」，以最新顺序为准。**
- **明日计划必带「标准:」**：明日计划每条格式为 `内容 + 标准:量化标准 + 【责任人:姓名｜承诺交付:月-日 时:分】`——标准是强制项，不是可选项。生成日报时**先写好标准再交付**，不得留到用户提醒（8-24、8-25 连续两天因漏标准被用户批评，已立为铁律）。标准写法：完成后的可验收结果，如「标准:各平台上传/回显正常」「标准:绑定保存回显不丢」。**承诺交付时间（9-02 晚「按规范来」起）**：写目标日期/时刻（如 09-03 18:00，目标时刻可给，属承诺性质非编造事实）；部署目标（部署测试/生产环境）写入该条「交付物:」行，如「交付物:部署测试环境」。
- **产出区只写已完成**：产出里只放已完成/已交付的内容；"还没做"的事项、实现边界说明（如"只改某端、设计器不动"）、本地方案术语（Phase/方案等）都不写进产出——未做事项放进行中，实现细节不放日报。
- **不写需求 id 和 git 细节**：标题不带需求编号（1002665 等）；不写"已提交/已推送远程"等提交过程。
- **同一事项合并表述**：同一个事项的多个子项合并成一条写（如手工单事项含配对弹窗、数量金额修改、会议遗留等），不拆碎。**同项目新旧版本合并（8-31 沉淀）**：旧版本被舍弃、整体重构为新版本时，旧版本的所有修改内容并入新版本一条，不单列「旧客户端/旧框架」条目（如某客户端旧版重构并入「新客户端重构」一条）。**同一主线的配套条目必须并入主体（09-15 沉淀）**：一条主工作 + 它的配套（代码审查 / 验证 / 清理 / 改名 / 回归）默认合成一条，审查验证只在主体句尾一笔带过（例：「登录链路改造：强口令校验 + 验证码开关 + 4 处缺陷」一条，句尾写「改动经两轮代码审查与验证后部署测试环境」），**不单列「本批改动两轮审查与验证」这类条目**；进行中同理，同一件事的「等复核部署」与「遗留待办」不并列两条。只有交付物、交付时间、责任主体不同的才算独立条目。用户原话：「这种不要写了，要么写到主体工作里，一笔带过」「这种明显一回事的为什么要分开写？」。写前自问一句：这几条是不是一回事？
- **承诺交付写日期目标（9-02 晚按规范来）**：明日计划承诺交付写目标日期/时刻（如 09-03 18:00），不写部署目标、不写 git 过程；部署目标进交付物行。
- **失误栏口径**：开发中代码复查发现并修复的问题，属开发过程的正常闭环、不是交付后出现的问题，不算失误——不写进产出、也不写进失误栏（产出里不要出现"修了 XX 小问题"这类表述）；失误栏只记录交付后出现/影响使用的问题。**失误栏永远只写「返工:X｜Bug:X」一行，不加任何说明行（9-03 用户两次纠正后定稿，推翻 9-02 晚「补说明行防考核引擎判虚报」的做法）**——开发中的事连「说明:…不属交付后失误」的辩解都不写，写说明本身就是把开发中的事往失误栏里塞。
- **周报/月报「失误与影响汇总」同样禁辩解（2026-09-06 用户纠正，原话「不记返工这种话你也写出来？」）**：周报失误区的量化行（返工率/Bug 清单/延期合计/时间浪费/交付影响）**只写事实与数字，不夹任何口径/辩解说明**——「按开发/自测期口径不记返工」「已在卡点区如实暴露」这类话是给自己看的口径，写进提交件等于主动递「虚报」把柄。返工率行只写「0%（0/N 项交付）」；口径与防虚报的说明只留本地分析文件，绝不进提交件。机械自检 grep：`不记返工|如实暴露|不属交付后失误|口径不` 命中即删。
- **口径区分**："已上线"=已部署生产环境；"已上测试"=已部署测试环境。
- **同日多份素材一律累加（2026-09-01 教训，用户明确不满过）**：用户常分多次发来同一天不同线的工作小结（不同项目/不同时段/语音转文字）。新素材一律视为**追加**，不得以"后发为准"整份覆盖前一份；只有**同一事项的状态冲突**时才以新素材为准，其余全部保留。已经被覆盖过的内容由 AI 主动补回，绝不回头追问用户"要不要并回来"——那是自找的返工。
- **失误栏判定顺序（2026-09-01 用户纠正）**：先看有没有交付上线（部署测试/生产）。未上线的内部工具、开发联调过程中暴露的事故与 bug——哪怕影响到了真实数据（如写到生产库、真实刊登用了错图）——一律不算失误，写「返工:无｜Bug:无」；事故根因修复写进产出条目时用**中性交付表述**（如「任务号与截图路径规范：任务号生成规则收紧避免重复产物」，不出现"修掉/事故/闪退根因"等字样），遗留项落卡点/进行中，教训落复盘。规范里「失误栏填无但别处暴露问题 = 标虚报」这条红线**只适用于已交付后的问题**，不要拿它硬套在开发中项目上。
- **对接人称呼用本人叫法（2026-09-01）**：涉及主管一律写「欧阳老师」，不写真名；**正文和「对接人:」字段要一起改**，只改正文会被批评。不给姓名的对接人写「待确认」，用户说「无」就整段去掉对接人字段。

## 月报结构铁律（2026-08-30 沉淀 · 当前不适用，仅存档）

> ⚠️ 2026-09-15 用户口径：**不需要写月报**。本节保留备用，除非用户明确要求写月报，否则不触发。

**月报严格按飞书模板固定 6 段**：一、本月关键产出（最多 5 项）→ 二、项目 / 需求推进情况 → 三、协作与对接 → 四、问题、风险、卡点（含缺陷汇总）→ 五、下月计划 → 六、自评与互评。**禁止给月报新增模板外的小节**（如「技术/能力沉淀」「个人复盘与思考」独立成段）——模板没有这部分内容就不写（2026-08-30 用户明确指示，此前 AI 曾加两节被要求整体撤销）。

- 规范七提到的「技术/能力沉淀」「个人复盘与思考」等模块，如确需体现，**并入产出区对应条目或风险区改进点**（如可复用工具写进产出5 工具行、复盘教训写进风险条目改进），不另开章节、不改变编号。
- 月报数据来源与缺漏核对见工作流程第 2 步；自评栏评分不代填（见周评/考核边界）。

## 交付状态短指令映射（2026-08-24 沉淀，何成标高频用法）

何成标会「引用日报条目 + 短指令」快速修正交付状态，AI 须映射到规范口径：

| 用户短指令 | 映射结果 |
|---|---|
| 已部署线上 / 部署线上 / 已发布 | 标题进度标注去掉或改（100%）；交付:09-02（当日，用户补时刻则带时:分）；交付物行写「已部署生产环境」 |
| 已部署测试 / 已上测试 | 标题改（100%）；交付:09-02（当日）；交付物行写「已部署测试环境」；**联动移入产出区**：删进行中条目、删/改明日计划对应条目 |
| 待调试 | 标题进度标（待调试），交付:无，预计:调试通过后部署测试 |
| 本地自测完成 | 标题进度标（本地自测完成），交付:无，预计:待部署测试 |
| 交付：无 | 交付:无（未部署；标题保留进度标注如（开发完成）/（本地跑通）） |
| 交付：本地跑通 | 按用户指示，一般改「交付:无」（本地跑通≠交付，8-24 确认过） |
| 交付：部署正式 / 交付发布 / 交付生产 | 承诺交付:09-03 18:00（明日目标时刻），交付物行写部署生产环境 |
| 交付：部署测试 / 交付测试 | 承诺交付:09-03 18:00，交付物行写部署测试环境 |
| 预计：8.25 / 8-25 | 预计:08-25（补零、统一格式） |
| 删除 / 不要 | 删除被引用条目（或其中指定的小点，如"- xxx"后跟"删除"） |
| 责任人：A、B、C（或"A、B、C - 条目"） | 责任内联格式化为 责任人:A+B+C |
| 润色/扩写 | 按规范卡点/协调六要素补齐：分类+需协助+对接人+期望解决+影响 |

> 注：交付/承诺/预计的时间写法 9-02 晚按规范回归为日期（产出=真实完成日期，编不出时:分就写到月-日；承诺/预计=目标日期可带 18:00 时刻）；部署状态词一律改放「交付物:」行。此表仅保留"状态怎么联动"的语义，落地格式以上方责任内联条目为准。

**联动清理规则**：交付状态从「待交付」变「已部署」时，同步删除/更新关联的「待验证/待提测/待合码」进行中条目与明日计划条目——避免日报里「已部署」和「待提测」并存矛盾（8-24 经验：尺码上线后删了 3 条旧待办；8-31 验证：色布选色/包装校验/PDD 失败原因/Ozon 物流回显四条「已部署」均联动移产出区+删进行中+删/改明日计划）。

**产出区编号**：多项目分区块，一个项目一个小节。两种编号方式用户都用过：8-31 为**全局连续 1~N**；**9-01 用户两次手动改成各区块从 1 独立起号**（A 项目 1 / B 项目 1·2 / C 项目 1），说明当前更倾向区块内起号。生成时默认按**区块内从 1 起号**，用户若要求全局连续再改；不要在用户手改后擅自改回。

**标准强制自检**：日报生成完成时必须逐条检查——明日计划每条是否带「标准:量化标准」、产出每条是否带「交付物+标准」。缺标准 = 不合规，补上才能交付（8-24、8-25 连续两天因漏标准被用户批评，已立为铁律；明日计划标准写法见偏好区）。

**提交前机械自检（9-03 沉淀，生成完必跑，逐条 grep 级检查，不靠"记得"）**——每天翻车的点全部固化在这里，命中任何一条先改再交付：
1. **失误栏**：整个第四节只允许「- 返工:X｜Bug:X」一行。多出任何行（尤其「说明:…不属交付后失误」）= 违规，直接删。
2. **产出区+失误栏 grep**：`修掉|修复了|事故|小问题|连环` → 命中即违规（开发期修复不进产出/失误，要用中性交付表述；进行中/卡点区描述"正在修"的遗留问题不在此限）。
3. **全文 grep**：`待填|待你|拍板|待补充` → 命中即违规（占位符、第二人称旁白不进提交件；9-04 计划骨架这类工作文件除外）。
4. **标准齐备**：产出每条带「交付物+标准」、明日计划每条带「标准:」，缺即补。
5. **整块替换指令**：用户说「X 作为产出/复盘/某区块」默认指**整个区块替换**，不是合并进现有条目（9-03 复盘要求换录音内容时曾只揉进一条被二次纠正）。
6. **参与默认规则**：所有事项除非用户明确指出与他无关，写负责人/对接人必带何成标，不以"别人牵头"为由把他摘出去。

**模块顺序**：以用户最新指示为准（8-24 曾把「五异常/六明日」互换为「五明日/六异常」；默认按上面偏好区的顺序，用户改过就按改的来）。

## 何时使用

- 用户要求"写日报 / 周报（周评）""按规范出一份周报""日报模板"。
- 用户提到"责任内联、返工率、Bug 分级、延期天数、时间浪费、失误四要素"等规范字段。
- 用户要求"检查这份汇报合不合规""为什么被扣分"。

## 工作流程

1. **判断类型**：确认是日报还是周评（周报以周评表第一部分提交）。**月报不写**——除非用户明确要求，才回 spec §7 与本文「月报结构铁律」处理。
2. **数据源覆盖核对（周评必做，日报可选）**：写周评前先盘点数据源是否覆盖整个周期，逐日核对，缺天立即向用户索要，不得用已有天数冒充完整周期。数据源共三类，各有边界：
   - ① **飞书汇报里的日报**：用户日常日报提交在「飞书汇报」应用里，**不在云文档体系（docx/wiki/表格）内，AI 无法用 drive +search 搜到**，必须由用户导出/截图提供（建议用户每周六整理周报时把飞书汇报当周日报复制到 `data/daily/` 归档）；
   - ② **飞书周评表/周报**：位于云文档，可用 `lark-cli drive +search --query "" --as user --created-by-me --doc-types docx,wiki` 检索（注意：周评表制度可能从某周才开始，更早的周没有）；
   - ③ **本地日报归档**：`<技能目录>/report-pipeline/data/daily/日报_YYYY-MM-DD.md`（由 `report-pipeline` 采集层产出），但本地归档可能不连续（如从月中才开始），不能当作完整数据源。**历史归档若在别处**（用户换过工具或早已有归档目录），按用户指的位置一并读，不要因为不在 `data/` 就当没有、也不要擅自搬动用户的文件。
   - 教训实例：2026-08 月报前两版只用了本地日报（最早 8-14）+ 飞书周评表（8/10 起），漏掉飞书汇报里的 8-3~8-7、8-11~8-13 整段上旬，被用户指出"月报看着都是最近两周"。补救靠用户截图。铁律：**周期数据缺源不生成，先补齐再写。**
3. **收集信息**：用结构化提问补齐必要字段（见下"必问字段"），不要凭空编造数字。
4. **套用模板**：读取 `references/templates.md` 对应类型的模板，按结构填充。
5. **责任内联**：每条产出/计划末尾强制插入 `【责任人:姓名｜交付/承诺交付:月-日 时:分】`。
6. **量化错误**：凡有返工/Bug/延期/时间浪费，按 `references/spec.md` 第三节口径量化，缺填视为不合规。
7. **合规自检**：逐条对照"五大红线"与"红线闸门清单"，不通过则提示用户补正。
8. **输出**：给出最终可提交的汇报文本，并附一句本次合规结论。

## 责任内联标注格式（铁律，每条必带）

```
产出类：【责任人:姓名｜交付:月-日 时:分】＋交付物＋量化标准
计划类：【责任人:姓名｜承诺交付:月-日】＋内容＋标准:量化标准（标准必带）
多人协作：【责任人:甲+乙｜交付:月-日 时:分】
```

示例：完成登录接口联调【张昆｜交付:08-04 18:00】，交付可用接口，3 个异常分支覆盖，响应≤200ms

一条工作项没有责任人 = 没写；没有交付/承诺时间 = 没排期。

> **9-02 晚「按规范来」统一口径（用户逐条给时刻实证）**：交付字段 = 完成日期/时刻（真实发生，09-02 19:00 / 13:30 等，编不出时:分就写到月-日）；承诺交付/预计 = 目标日期/时刻（如 09-03 18:00，承诺性质可给）；部署状态词（已部署测试/生产、已交付某人使用、未走部署流程）一律放「交付物:」行。纯依赖外部无日期的（等后端支持/随版本）如实写条件，不硬编日期。卡点含「分类(技术/对接/需求/资源)+需协助:是/否」。失误栏无失误显式写「返工:无｜Bug:无」，**不加说明行（9-03 定稿）**。

## 必问字段（编写前补齐，禁止虚构）

- **日报**：今日核心产出、进行中未完成、卡点阻碍（分类+影响天数）、明日单日计划、失误与影响。
- **周报**：本周单日达标复盘、进度偏差天数、卡点汇总、返工率+Bug清单+延期合计+时间浪费、下周单日排期。
- **月报**：月度量化成果、整体进度复盘（原计划/逾期天数）、系统性问题根治、缺陷汇总、下月拆解。

若用户未提供具体数据，先提问补齐关键字段，再生成；不得用占位符或编造的姓名、天数、Bug 等级冒充真实内容。

## 五大红线（逐项自查）

| 红线 | 要求 | 禁止 |
|-|-|-|
| 颗粒度 | 最小单元=1天，长任务拆到单日 | 跨天模糊排期、整块周/月笼统任务 |
| 交付 | 执行内容+交付物+交互结果+量化标准 | 只写干活、无产出无标准 |
| 真实 | 进度/问题/卡点/错误如实暴露 | 虚报进度、隐瞒卡点/错误、敷衍"正常推进" |
| 权责 | 明确个人/协同/对接人，内联责任 | 大锅饭描述、匿名产出 |
| 责任内联 | 每条末内联责任人+交付时间 | 无责任人/无交付时间 |

## 红线闸门（命中即重罚，独立于维度分）

- 出现"正常推进/暂无问题/一切正常"等敷衍话术 → 风险与影响分 ≤40 并标红
- 失误栏填"无"但周报/卡点暴露问题或 Bug 未修复 → 犯错影响分 ≤30 + 标虚报
- 颗粒度违规 → 完整性扣 10~20 分
- 交付红线缺失 → 进度可信度扣 10~20 分
- 责任内联缺失 → 责任可追溯扣 10~20 分

最终总分 = 加权分 − 闸门罚分（封底 0 分）。
