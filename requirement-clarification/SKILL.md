# 需求澄清

在信息不足时 **先问清、再文档化**。核心产出是澄清表，不是完整 PRD。本 skill **不改业务源码**。

## 触发时机

- 「需求澄清」「先把需求问清楚」「帮我梳一下需求」
- 「这需求还不清楚」「口头需求整理一下」
- 用户只丢：一句话、会议碎片、截图、竞品链接、含糊「做个 XX」
- 写 PRD/故事前发现关键字段缺失（目标、范围、角色、成功标准）

## 与相邻 skill 的边界

| Skill | 何时用 |
|---|---|
| **本 skill** | 澄清；三栏清单；必要时短问卷 |
| `prd-authoring` | 已足够清晰，或澄清后写正式 PRD |
| `user-story-acceptance` | 澄清后拆故事与 AC |
| `plan-discussion` | 技术怎么做的方案讨论 |
| `competitive-or-feature-brief` | 做不做/方案取舍决策简报 |
| `meeting-to-action` | 会议记录 → 决策与待办（偏执行跟踪） |

⚠️ **禁止**：需求仍大面积待确认时，假装已定稿并写满「假精确」PRD。  
可先输出澄清稿，经用户确认后再调用 `prd-authoring`。

## 工作流程（强制顺序）

1. **复述**：用 2～4 句复述当前理解（角色、诉求、场景）。
2. **分类填充**：「已确认 / 待确认 / 假设」三栏（见模板）。
3. **提问**：对待确认项一次抛出 **最多 5～8 个** 高杠杆问题（优先：目标用户、成功标准、非目标、端/仓依赖、上线时间与约束）。
4. **等用户答**：未回答前不写定稿 PRD；可维护「澄清中」文档。
5. **更新三栏**：根据答复把项移入「已确认」，删除或改写假设。
6. **出口建议**：已确认足够支撑开发时，建议下一步：`prd-authoring` 或 `user-story-acceptance`。

## 落盘位置（可选）

| 场景 | 路径 |
|---|---|
| 默认 | `Docs/需求澄清/YYYY-MM-DD-{中文主题简称}.md` |
| 已有方案主题 | `Plans/{主题}/需求澄清.md` |
| 仅对话 | 用户未要求则可不落盘 |

同名冲突时加 `-2`、`-3`。标题与章节默认中文。

## 提问原则

- 先边界（非目标、不做），再细节（字段、文案）。
- 截图需求：问清 **页面是哪端**、**谁可操作**、**成功/失败长什么样**、**是否已有接口**。
- 多仓产品：必问涉及 **来图 / 设计器 / 工厂端 / 后端** 中的哪些（或项目等价边界）。
- 不要一次问 20 个细节问题；分轮进行。
- 把猜测放进「假设」，不要放进「已确认」。

## 质量检查

- 三栏都存在；「已确认」无来源不明的臆造。
- 「假设」均标注验证方式或风险。
- 未获确认前，不把假设改写成需求定论。

## 对话交付摘要

1. 复述一句话  
2. 待确认 Top 3  
3. 本轮问题列表  
4. 若已落盘：路径
