# 代码审查 · 智能分级（full-code-review）

一句话触发，**自动选级**：小任务轻量、大任务全量，把审查力花在刀刃上。

> **第 33 轮口径：本技能是「独立按需动作」，默认不主动跑。** 开发完成后 agent **直接提交并推送**（推送前只过 `生成提交` 的核验），**审查不卡在交付路径上** —— 一般由用户提出（"审查一下 / 全面审查 / 看下这个改动 / 影响面 / 回归"）才执行。**不被点名就不跑，也不要"顺手审一下"。**

## 两大用途（先分流）

| 用途 | 何时走 | 怎么走 |
| --- | --- | --- |
| **① 审查**（只审不代改） | 用户说「审查一下 / 快速看一下 / 全面审查 / 提交前检查 / full review」 | 本文 L0–L3 全流程 |
| **② 改后收尾**（影响面 + 回归交付） | **用户说「影响面 / 回归测试 / 测什么 / 改动范围」时才做**（**第 33 轮起不再默认附带** —— 审查是独立按需动作，不自动挂在每次改动后面） | **只派「影响面与回归」这一个维度**（无子代理能力则主代理自查）：标准见 `references/影响面与回归.md`，GitNexus 查一次 |

## 第一步：解析审查对象（所有级别通用）

| 用户说 | 审查范围 |
| --- | --- |
| 「当前修改 / 最近的改动 / 我这个变更」 | `git diff`（含已暂存与未暂存）；最近一次提交视上下文纳入 |
| 「xx 代码 / 某文件 / 某模块 / 某个目录」 | 指定文件、路径或目录 |
| 「xx 分支 / 对比主分支」 | `git diff <base>...<branch>`（base 按项目约定） |

范围不明时取「最近一次改动」为默认，并在报告开头注明。只审范围内内容，不整库扫描。

## 第二步：分级（自动判定；用户可手动覆盖）

| 级别 | 判定信号（满足其一） | 执行方式 | 成本 |
| --- | --- | --- | --- |
| **L0 免审** | 纯文案 / 注释 / 格式 / 样式；锁文件、自动生成产物；≤10 行且无逻辑 | 不派代理：跑 lint / typecheck（如 `pnpm check`）自查即可 | 最低 |
| **L1 快审** | ≤2 个文件、≤50 行；单点小逻辑；用户说「快速 / 简单看一下」 | **单代理**：code-reviewer（通用，0–100，只报 ≥80） | 低 |
| **L2 定向审** | 中等改动（≤5 文件 / ≤300 行），或命中 L2 类型路由 | **按类型路由 2–3 个维度**（见下表） | 中 |
| **L3 全量** | >5 文件或 >300 行；高风险路径（鉴权 / 支付 / 数据迁移 / 权限 / 并发）；分支合入或提 MR 前；用户说「全面审查」 | **5 个子代理全量**（通用 / 静默失败 / 类型契约 / 测试质量 / 影响面与回归）；**重档**把「测试质量」拆成 2 个（覆盖 / 变异）→ 6 个 | 高 |

手动覆盖优先级最高：「全面」→ 强制 L3；「快速 / 简单」→ 强制 L1（若改动实为高风险，报告里会附一句「建议按 L3 重审」）。

### L2 类型路由表（只上有用的维度）

| 改动命中 | 加上的维度 |
| --- | --- |
| 错误处理 / 异常 / 异步链路 | silent-failure-hunter |
| 类型 / 数据模型 / 接口契约 | type-design-analyzer |
| 测试文件 / 核心口径模块（校验 / 计算 / 状态映射） | test-quality（覆盖 + 变异） |
| 注释 / 文档块 | code-reviewer 的附加清单 comment-analyzer |
| 逻辑复杂度明显上升 | code-reviewer 的附加清单 code-simplifier |
| 共享组件 / 公共 API / 路由 / 全局状态 / 多处引用的 util | impact-regression（影响面与回归） |
| （任何 L2 都默认包含） | code-reviewer |

## 维度标准（内置 references/）

**五个维度的审查标准**都内置在本技能 `references/` 下：派遣子代理时把对应文件原文注入单子；降级自查时逐维 Read。它们是本技能的内部资料——工具只认 `<技能目录>/SKILL.md`，不会被当作独立技能发现，对外始终只有 `代码审查` 一个入口。

| 维度 | 标准文件 | 管什么 |
| --- | --- | --- |
| code-reviewer | `references/code-reviewer.md` | 通用审查：0–100 打分，只报 ≥80。**另带两份附加清单**：`references/comment-analyzer.md`（注释质量）+ `references/code-simplifier.md`（简化机会）—— **不再单独占子代理**，由通用代理一并看；L2 路由命中时才单独强调 |
| silent-failure-hunter | `references/silent-failure-hunter.md` | 静默失败 / 错误处理 |
| type-design-analyzer | `references/type-design-analyzer.md` | 类型与接口契约 |
| test-quality | `references/test-quality.md` | **测试质量：一问「测到了吗」（覆盖）+ 一问「测得硬吗」（变异 / Stryker）**；重档要求两问由两次独立执行 |
| impact-regression | `references/影响面与回归.md` | 影响面清单（对象/关系/风险）+ 必测/建议测回归方法；改后收尾（用途②）只派这一维 |

**维度数量上限：5 个（不再新增）** —— 判据与技能合并同一条：**能并进既有维度的，就不单开。** 已合并两处：① `comment-analyzer` + `code-simplifier` **并进 `code-reviewer`**（洁癖项，不单占子代理）；② `pr-test-analyzer` + `mutation` **并为 `test-quality`**（同一份材料、同一个问题："测试够不够"）。

> 维度加得越多，L3 的子代理越多、重复查越多、噪音越大 —— 所以**只增"答不同问题"的维度，不增"答同一个问题"的维度**。

**维度间分工（防重复查）**：GitNexus 的 `detect_changes` / `impact` 结论由主代理查**一次**，同时注入 `type-design-analyzer`（管爆炸半径的**审查判断**：这么改的设计对不对）与 `impact-regression`（管**交付清单**：伤到哪、怎么测）两维——前者评设计，后者出清单，各写各的结论，不各自再调 MCP。

## GitNexus MCP 辅助（L2 / L3 · 有则用，无则降级）

L2 / L3 审查**尽可能用 GitNexus MCP** 把盲读换成结构化查询；工具或索引不可用时**直接按原流程走**，不报错、不阻塞、不重试。L0 / L1 保持零依赖，不碰 MCP。

| 能力 | 用在哪儿 |
| --- | --- |
| `detect_changes` | L3 开审前把 diff 映射到改动符号与受影响执行流程，圈定高风险文件，按维度分组后下发 |
| `impact`（上游 / 下游） | L3「类型与设计」维度：评改动爆炸半径（d=1 必坏 / d=2 波及） |
| `explain`（污点） | 「静默失败」维度：列 source→sink 传播链，对照改动找未处理的错误路径 |
| `context` / `trace` | 审查中理解调用链、找调用方，替代反复 grep + 盲读文件 |

- 前提：目标仓库已 `gitnexus analyze` 建过索引。没建过且本次值得 L3 → 顺手建一次再查；建索引代价过高（超大仓 / 只读环境）就跳过，报告注明「未用 GitNexus（原因）」。
- **Skill 协同**（按需转接，不在本技能内展开）：审查结论要展开成正式影响面清单与回归清单 → 用途②（Read 本技能 `references/影响面与回归.md`）；查远端合入 / 发版状态 → **公司库** `CNB推送审计`（`lingchuang-skills`，没装就跳过）；修完提交并推送 → `生成提交`（**其「推送前核验」会读本技能的测试质量与影响面结论**）。

## 第三步：执行

- **派遣数量**：L1 = 1（通用）；L2 = 2–3（按路由表）；**L3 = 5**（重档 6 —— 「测试质量」拆成覆盖 / 变异两个）。降级自查时同数量、顺序做。
- **有子代理能力** → 并行派遣（Claude Code / Codex / ZCode / AutoClaw / Trae 各自机制）；**无或不可用（如额度限制）** → 主代理按同一套维度标准顺序自查并注明——注意 L1 / L2 本身维度少，降级代价也小。
- 每个子代理的单子 = 维度 + 审查范围 + 审查标准（Read 本技能 `references/<维度>.md` 原文注入）+ 输出格式（位置[文件:行] / 问题 / 影响 / 建议）+「只审不代改」；L2 / L3 若用了 GitNexus，把对应查询结论（影响面 / 污点链 / 调用链）一并注入相关维度的单子，别让子代理重复查。
- **需求类审查（改动为落地某个需求）**：**单子必须含需求原文与一致性比对要求**（2026-10-13 用户口径）——需求原文取 `<工作区根>/Docs/需求拆解/**/*<需求id>*` 需求目录下的 `原文.md`（末尾嵌有截图引用）与 `截图*.png`（拆解需求时已存档，见 `创建分支`），注入每个相关维度的单子，要求子代理**逐条对照原文核实现行为**：未覆盖、擅自偏离、私自扩圈都要报。找不到原文 → 报告开头注明「无需求原文，未做一致性比对」，不靠记忆猜需求。
- 成本纪律：只审 diff；跳过锁文件、生成文件、快照（除非用户点名）；每维度输出 Top-N（默认 10 条）；子代理失败重试 1 次，仍失败由主代理补位并标注缺口。

## 第四步：汇总（按级别给不同篇幅）

- **L1**：一段话 + 问题清单（若有）；
- **L2**：分类列表（问题 + 建议），注明选了哪些维度；
- **L3**：完整报告——按严重度排序、评分摘要、**建议先修的三件事**、模式与缺口注明。

## 约束

- 只审查、不代改（除非用户明确要求「修」）。
- 聚焦范围内改动；范围外的既有问题最多一句话提及，不展开。
- 语言与用户一致（默认中文）；专有名词保留原文。
- 用户说「不用审查 / 跳过」→ L0，一句话确认即可。
