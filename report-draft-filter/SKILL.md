# Report Draft Filter（工作小结 → 日报草稿前置过滤器）

## Overview

本技能解决一个问题：何成标每天发来的「工作内容总结」是口语化原材料（含 AI 旁白、专业术语、git 动作、需求编号、"还没做"的待办、"明天要做"的计划），不能直接进日报。先按本技能**去噪 + 归类 + 合并**，输出一份干净的"可写内容"，再交给 `report-writer` 技能套 v2 七模块模板。

**先当分拣员，后当排版员。** 分拣是本文的活，排版是 report-writer 的活。

**上游采集层**：日常"边做边攒"的素材卡由 `report-pipeline` 技能负责采集与机械映射；本技能处理的是这些素材（或用户直接发来的小结）到日报草稿之间的去噪归类。

## 何时使用

- 用户发来一段或多段"每日工作内容总结 / 工作流水"，要求整理成日报草稿。
- 用户问"这些内容哪些该写、哪些不该写进日报"。
- 用户要求把工作小结转化为符合技术部 v2 规范的日报结构。

## 工作流程

### Step 1：通读归类

把小结里的每一条内容打上标签，落到日报的对应栏位：

| 内容性质 | 落到日报栏位 |
|---|---|
| 本人/前端，已完成且部署 | 一、产出 |
| 做了但没完 | 二、进行中 |
| 计划明天做 | 五、明日计划 |
| 卡住 / 等别人 / 依赖 | 三、卡点 |
| 交付后出现 / 影响使用的问题 | 四、失误（无也要写） |
| 讨论 / 协调 / 方案变更 | 六、异常与协调 |
| 心得 / 踩坑复盘 | 七、个人复盘 |

铁律：产出只放**已经交出去**的（已部署上线，或已交付某人使用）；没做完、还在等对齐、只做了边界、还在排期的，一律不放产出——**整条挪到「二、进行中」，不是只把百分比改小**。

**09-17 收紧后的完成口径**：**只有已部署生产环境才算完成、才标（100%）**；**只部署测试环境也算产出**（用户原话「只上测试也算产出」），但标「（未完成，已部署测试环境）」、不标（100%）；开发完成未部署的标「（未完成，未部署）」。

### Step 2：逐条剔除（不需要写）

对照以下清单删除（详细示例见 `references/gather-to-draft.md`）：

- AI 旁白注释（"（属同一个任务）"）、内部核对整节（"昨日计划完成度核对"）
- 凭空新项目名（改回前文已出现的称呼）
- 实现边界说明（"只改某端、设计器不动"）
- 专业术语（Phase/方案/创建分支 → 改白话）
- git 细节（已提交/已推送远程/分支名）
- 需求编号写错位置（**09-17 改口径**：需求编号改成 TAPD id，放**标题尾部括注**，开发性工作必带、沟通交流与检查类也带；旧规则「不写需求编号」作废）
- 产出里写"修了小问题"（开发复查发现并修复 ≠ 交付后失误，产出和失误栏都不写）
- 产出里写"还没做"（移到进行中）
- 交付字段填计划/排期时间（交付只填**完成日期 月-日**；部署状态、交付给谁写进「交付物:」行；排期/计划不是交付）
- 顶部/文末元信息（"已按你的要求…""待补充信息""合规自检"）
- 非本人 / 非前端内容（Java 后端、服务费评审等）

### Step 3：同类合并

同一事项的多个子项合成一条写（如手工单事项含配对弹窗、数量金额修改、会议遗留等），不拆碎。

### Step 3.5：过写形态清单（09-16 实证，写之前先照一遍）

以下六种「agent 自己长出来的结构」是被删得最多的，生成草稿时就要避免，别等用户逐条点掉：

| 过写形态 | 表现 | 正确做法 |
|---|---|---|
| **按动作拆条** | 一件工作拆成「画流程图 / 出方案 / 更新文档索引 / 核代码差异」四条 | 按工作事项合一条，交付物并列 |
| **把没交付的放进产出** | 方案还在等对齐、功能还没部署，先挂个低百分比 | 整条挪「二、进行中」 |
| **留存量条目** | 早前收的、与当期重点无关的卡点/协调继续挂着 | 只留当期真正卡住交付的 |
| **与别处重复** | 同一条信息在产出、卡点、异常里各写一遍 | 留一处，其余删（信息不重复承载） |
| **机器味标签** | 内部编号、分期后缀（一期/二期）、字段名清单、问题名清单、角色归因（"由后端更新"） | 一个统一称呼；点名到人；不罗列 |
| **日期留空** | 卡点「期望」、进行中「预计」、明日「承诺交付」写「暂无确定日期」 | 三处对齐同一日期；明日一律写次日 |

**贯穿的判据**：用户删的几乎不是"事实"，而是 agent 给事实套的"结构"——事实留下，架子拆掉。**一句话标准：领导只关心"推进了什么 / 卡在哪 / 下一步"，不关心工作分解结构（WBS）。**

### Step 4：标注责任内联 + TAPD id

每条开发性工作（含沟通交流、检查类）的**标题尾部括注 TAPD id**（如「工厂账号预充值（100%）｜TAPD 1002816」）；拿不到 id 就问一句，不要编。

每条产出补 `【责任人:姓名｜交付:月-日】`（只填完成日期；部署状态等实情写进「交付物:」行）+ 交付物（含交付给谁/谁可用）+ 量化标准（如"本地自测通过、无报错"）。卡点必须带 对接人 + 期望时间 + 影响，写具体姓名，不写"后端/平台端"。

### Step 5：白话重写 + 交付 report-writer

术语转大白话，非技术读者能看懂；然后调用 `report-writer` 技能套七模块模板、做红线自查（颗粒度/交付/真实/权责/责任内联）。

## 输出要求

- 交付物是一份已去噪、已归类、已合并、带责任内联的日报草稿。
- 失误无也要显式写（`返工:X｜Bug:无`）。
- 提交件不含元信息，只留规范七模块。
- 项目名沿用前文称呼，不造新总名。
