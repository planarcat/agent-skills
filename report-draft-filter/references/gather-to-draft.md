# 日报编写指导性文档：从「工作小结」到「日报草稿」

> 定位：本文是 report-writer 技能的**前置过滤器**。技能规定"日报长什么样"，本文规定"拿到何成标发来的工作小结后，哪些写进日报、哪些剔除"。
> 适用：何成标（技术部前端）每日发来口语化的工作小结，AI 据此整理成符合 v2 规范的日报草稿。

## 0. 流转链路（为什么需要这份文档）

```
当日完成某项工作
   ↓
你（何成标）发来「每日工作内容总结」  ← 口语、含旁白/术语/git动作/待办/计划，未经筛选
   ↓
【指导性文档（本文）】               ← 先把噪音剔除、归类、合并
   ↓
AI 总结工作内容（七模块结构）
   ↓
AI 出日报草稿（套 report-writer 模板 + 责任内联）
```

你发的小结 ≠ 日报。小结是原材料，本文是分拣规则，技能是成型模具。三者顺序是：先按本文分拣，再套技能模板。

---

## 1. 输入与输出约定

- **输入（你的工作小结）**：口语化、可能包含——AI 旁白注释、专业术语（分支/Phase/方案）、git 动作（提交/推送/分支名）、需求编号、"还没做"的待办、"明天要做"的计划、实现边界说明（"只改某端"）。
- **输出（日报草稿）**：report-writer v2 七模块（产出 / 进行中 / 卡点 / 失误 / 异常与协调 / 明日计划 / 复盘），每条带 `【责任人:姓名｜交付/承诺交付:状态】`。
- **本文与技能的关系**：不冲突。本文做"去噪+归类"，技能做"成型+责任内联+红线自查"。先过本文，再过技能。

---

## 2. 总判定原则（一句话分流）

| 小结里的内容性质 | 落到日报的哪一栏 |
|---|---|
| 本人/前端，已完成且部署 | **一、产出** |
| 做了但没完 | **二、进行中** |
| 计划明天做 | **六、明日计划** |
| 卡住 / 等别人 / 依赖 | **三、卡点**（必须点名） |
| 交付后出现 / 影响使用的问题 | **四、失误**（无也要写） |
| 讨论 / 协调 / 方案变更 | **五、异常与协调** |
| 心得 / 踩坑复盘 | **七、个人复盘** |

**铁律**：产出只放"已完成并部署"的；没做完、只做了边界、还在排期的，统统不放产出。

---

## 3. 应该写（保留清单）

1. **本人 / 前端工作**：只写你做的前端相关产出。后端 Java、服务费评审、裁片库限制等非你非前端内容，不写。
2. **产出每条必备三件套**：`【责任人:姓名｜交付:部署状态】` + 交付物 + 量化标准。
   - 交付状态只填：**已部署生产环境 / 已部署测试环境**。
   - 量化标准举例："本地自测通过、无报错""3 个异常分支覆盖""导出请求必须带上品牌字段"。
3. **进行中**：未完待续的项，标 `预计:月-日 时:分`，不写进产出。
4. **卡点**：必须带 **对接人 + 期望时间 + 影响 + 协调动作**，写具体姓名（曹银峰、邓志豪、袁广杰…），不写"后端/平台端"角色归因。
5. **失误**：`返工:X｜Bug:无` 也要显式写；真有 Bug 按"责任人+根因+已修复+影响"量化。
6. **异常与协调**：讨论、方案变更、暂缓实施，点名协调方。
7. **明日计划**：`承诺交付` 填部署目标（部署线上 / 部署测试环境），不写 git 过程。
8. **项目名沿用前文**：POD 二创 + 虾皮上架同属"虾皮 POD Agent 搭建"，用已出现的称呼，不凭空造新总名。
9. **白话表述**：非技术读者能看懂。"创建分支"→"把功能单独复制到一个新版本里保留下来"。
10. **同一事项合并**：一个事项的多个子项合成一条（如手工单事项含配对弹窗、数量金额修改、会议遗留等），不拆碎。

---

## 4. 不需要写 / 必须剔除（关键清单）

| 类别 | 典型例子（来自实际修订） | 处理 |
|---|---|---|
| **AI 旁白注释** | "（属同一个任务）""（内部核对用）" | 整段删，领导不看 |
| **内部核对整节** | "昨日计划完成度核对" | 整节删 |
| **凭空新项目名** | "POD 自动化铺货项目" | 改回前文已出现的名（虾皮 POD Agent 搭建） |
| **实现边界说明** | "只改灵创设计器不动""只改某端" | 删，边界不是产出 |
| **专业术语** | "Phase 1""create branch""方案" | 改白话 |
| **git 细节** | "已提交 / 已推送远程 / 同步到远程仓库" | 删，不写提交过程 |
| **需求编号** | 1002665 等 | 标题不带 |
| **产出内写"修了小问题"** | "修了俩小问题" | 删；开发复查发现并修复属正常闭环、≠失误，所以产出和失误栏都不写 |
| **产出里写"还没做"** | 把未做内容塞进产出 | 移到"进行中" |
| **交付字段填计划/排期** | "交付:08-18 19:00""08-20 上生产" | 交付只填部署状态；排期放标题或明日计划 |
| **元信息** | 顶部"已按你的要求…"、文末"待补充信息""合规自检" | 全删，只留七模块 |
| **非本人 / 非前端** | Java 后端事项、服务费评审 | 不写 |

|---|---|---|

## 6. AI 处理工作小结的标准动作（checklist）

收到你的小结后，按顺序执行：

1. **通读归类**：把每一条标成 产出 / 进行中 / 计划 / 卡点 / 失误 / 协调 / 复盘。
2. **逐条剔除**：对照第 4 节，删掉旁白、边界、术语、git 细节、需求编号、元信息、产出里的"小问题"和"未做项"。
3. **同类合并**：一个事项的多个子项合成一条，不拆碎。
4. **项目名校正**：不造新名，沿用前文称呼。
5. **套七模块 + 责任内联**：每条补 `【责任人:姓名｜交付:部署状态】` + 交付物 + 标准。
6. **白话重写**：术语转大白话，非技术读者能懂。
7. **红线自查**：过 report-writer 五大红线（颗粒度 / 交付 / 真实 / 权责 / 责任内联），不通过则补正。

---

## 7. 一句话总结给 AI

> 拿到何成标的工作小结，**先当分拣员后当排版员**：把旁白、边界、术语、git、编号、未做项、排期时间、元信息全部剔除；只留本人前端的已完成部署（进产出）、未完（进进行中）、卡点（点名+时间+影响）、失误（无也写）、协调（点名）、计划（部署目标）、复盘（心得）；同类合并、白话表述、责任内联，再套七模块。
