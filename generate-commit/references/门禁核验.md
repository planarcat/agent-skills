# 门禁核验（`生成提交` 的推送前环节）

> 本文件是 `生成提交` 技能的**推送前环节**细则（2026-10-14 由原「门禁核验」技能并入）。
>
> **核验不是独立角色，是推送的前置动作**：commit 完先核验，**通过才推**。

## 为什么挂在推送前，而不是单独立一步

| # | 理由 |
|:--|:--|
| 1 | **门禁的意义就在于挡在推送前面** —— 放得离推送越远，越容易走形式 |
| 2 | **同一步内完成，没有缝隙** —— 避免"核验完到推送之间被人改动"，白做一遍 |
| 3 | **统一入口天然存在** —— 所有交付都必须经过 `生成提交`（提交即推），不必再造一个入口技能 |

## 核验项（缺一不可，逐项贴证据）

| 核验项 | 看什么 |
|:--|:--|
| **测试结果** | 本档要求的测试跑没跑、结果如何（贴命令与输出） |
| **类型检查** | 该档要求时，`typecheck`（或 `pnpm check`）跑没跑、结果如何 |
| **变异得分** | 有 stryker 配置的仓，得分是否 ≥ `break` 阈值 |
| **改动范围自述** | **一句话**：这次改了哪些文件 / 目录 / 模块 —— 用来判"有没有超出该档预期" |
| **跳过清单** | 本档要求但**没做**的项，逐条写明为什么 |

### 为什么不看「影响面」（第 33 轮）

**影响面与回归是 `代码审查` 的产出，而审查已移到推送之后、且按需触发** —— 核验发生在推送前，那时影响面清单**按需还不存在**。所以核验**不要求、也不等**它，改为 agent 自己**一句话自述改动范围**（够用来判"改超没超该档"）。要完整影响面清单 → 由人提"审查 / 影响面"，走 `代码审查`。

## 判定（缺证据二分）

| 情况 | 判定 | 能不能推 |
|:--|:--|:--|
| 有能力、有要求，但**没跑 / 没给证据** | **未完成** | ❌ **不推**，打回补齐 |
| 仓**根本没有该能力**（无 vitest / 无 stryker 配置），且**已贴证据** | 记「**跳过（无能力）**」 | ✅ 可推，但 ① 必须进收工报备 ② 该档纪律记**「未覆盖」**，**不算达标** |

- **跳过 ≠ 通过** —— 措辞上不许说"通过了"，只能说"跳过（无能力）"。
- 核验**不通过** → **不推**；补齐后**重新核验**。
- 例外只在「仓无此能力 → 未覆盖」这一类上需要人拍板；其余 agent 自己判。

## 汇报格式

```text
推送前核验：
  测试结果   ✅ pnpm test → 42 passed
  类型检查   ✅ pnpm typecheck → 通过
  变异得分   ⚠️ 跳过（无能力）—— 本仓无 stryker.config.json
  改动范围   3 文件（src/views/erp/xxx.vue、src/api/biz/xxx.js）
  跳过清单   变异（仓无能力）
  → 结论：可推（1 项未覆盖，记入收工报备）
```

## 红线（三条）

1. **核验不通过就不推** —— 不许"先推了再补"，也不许 `--force` 绕。
2. **必须贴证据** —— 不许写"应该没问题""本地试过"这类无凭据的话。
3. **跳过必须写清是"无能力"还是"没做"** —— 两者判定完全不同（前者可推但记未覆盖，后者**不推**）。

## 与 `代码审查` 的分工（第 33 轮：顺序反转）

| | 本环节（推送前 · 第 6 步） | `代码审查`（推送之后 · 第 8 步 · **按需**） |
|:--|:--|:--|
| 干什么 | **给判决**（推不推的关卡） | **出意见**（质量维度：有没有问题、问题在哪） |
| 产出 | 核验结论（可推 / 不推） | 审查报告 + 影响面与回归清单 |
| 关系 | **不看**审查结论（审查还没做） | 可读核验那次的测试 / 变异结果当输入 |
| 触发 | **每次推送前**（自动） | **由人提出才做**（独立动作、默认不跑） |
