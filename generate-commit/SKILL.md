# 生成 Commit

## 触发时机

当用户在开发过程中说出以下或相近表达时，使用本 skill：

- "生成 commit"
- "生成提交"
- "创建 commit"
- "写 commit"
- "写一个 commit"
- "帮我 commit"
- "commit 一下"

## 核心目标

根据仓库的修改情况，生成一条通俗易懂的中文 commit message 并提交；**提交完默认自动推送到当前分支的远程上游**（见下「推送规则」）。

---

## 工作流程

```
1. 检查暂存区 → 2. 确定变更范围 → 3. 生成 commit message → 4. 执行 commit → 5. 汇报结果
```

---

## 第一步：检查暂存区状态

执行以下检查：

```bash
git diff --cached --stat     # 查看已暂存的文件
git status --short           # 查看完整状态
```

### 情况 A：暂存区有内容

以暂存区的修改为蓝本生成 commit。不再关心工作区未暂存的改动。

### 情况 B：暂存区为空

根据当前对话中讨论/修改过的文件，**只暂存这些相关文件**，然后生成 commit。

**重要约束：**
- 只暂存当前对话中明确涉及、修改过的文件
- 不得将仓库中其他不相关的改动一并暂存
- 如果对话上下文不足以确定哪些文件被修改了，先用 `git diff --stat` 查看所有改动，向用户确认后再暂存

---

## 第二步：确定变更范围

确定了目标文件后，获取变更详情用于撰写 commit message：

```bash
git diff --cached              # 查看已暂存的详细差异（情况 A）
# 或
git diff                       # 查看未暂存的详细差异（情况 B，暂存前）
```

如果变更超过 500 行，只取前 200 行和后 100 行以及关键改动区域，避免上下文溢出。

---

## 第三步：生成 Commit Message

根据变更内容，按以下规范生成中文 commit message：

### 格式

```
<类型>: <简短概述>

<详细说明（可选，复杂变更时添加）>
```

### 类型

| 类型 | 说明 |
|:---|:---|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `refactor` | 重构（不改变外部行为） |
| `style` | 格式/样式调整 |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `chore` | 杂项（依赖、构建、配置等） |
| `perf` | 性能优化 |

### 要求

1. **概述使用中文**，一句话说清楚做了什么
2. **语言通俗易懂**，让阅读者能够直观地理解修改了什么内容，但也要做到尽量精确
3. **不捏造内容**：如果上下文中看不到某些变更，不要在 commit message 中编造
4. **长度控制**：概述行尽量控制在 50 个中文字符以内
5. **详细说明**：当一次 commit 涉及多个文件或多项修改时，使用 `-` 列表简要列出每项变更

### 示例

```
feat: 新增用户登录日志记录功能

- 在 login 接口中增加日志写入逻辑
- 新增 login_logs 表及对应迁移脚本
- 管理后台增加登录日志查询页面
```

```
fix: 修复编辑页保存按钮偶发无响应的问题
```

```
refactor: 将剪贴板同步逻辑从 App 组件中抽取为独立模块
```

---

## 第四步：执行 Commit

生成 commit message 后**直接执行，不等确认**（2026-10-09 用户口径：自动提交推送，不让用户重复确认）：

```bash
git commit -m "<commit message>"
```

随后按「推送规则」推送；在最终汇报里展示完整 message 与推送去向，用户事后可打回。说"只提交/先别推"则只 commit 不推。

### 安全边界

- ✅ 执行 `git add`（仅情况 B）+ `git commit`；**按「推送规则」自动 push**
- ❌ **绝不执行 `git push --force`** 或任何带 `--force` 的操作
- ❌ **绝不自动执行 `git rebase`、`git reset --hard`、`git clean`** 等破坏性操作
- ⚠️ 用户明确说"只提交/先别推" → 只 commit，不 push

---

## 推送规则（开发规范 · 2026-10-09 用户口径：自动推送，不要让用户重复说）

**commit 后默认自动推送当前分支到它的远程上游**，用户说"只提交""先别推"才止步。判据：

| 当前分支 | 怎么做 |
|---|---|
| **需求分支**（有同名远程上游，且上游不是主分支） | commit 后**直接 `git push`**（推给它自己的上游） |
| **主分支**（有上游） | commit 后**直接 `git push`**（2026-10-09 口径：自动推送，不用每次确认） |
| **无上游** | 只 commit；汇报里说明无上游，用户点头再 `git push -u origin HEAD` 建上游 |
| 用户说"只提交""先别推" | 只 commit |
| 仓库文档（`AGENT.md` / `CLAUDE.md` / `AGENTS.md`）另有推送规定 | 按文档走 |

- push 只推**当前分支**：`git push`（已设上游）；**绝不 `--force`**。
- 推送前把目标分支写清楚（`push → origin/<分支名>`）。
- 推送失败（无权限、被拒、网络）→ 如实汇报失败与原因，**本地 commit 保留**，不要改用强制推送。

---

## 防腐烂提醒（知识沉淀联动 · 2026-10-09）

生成 commit 的同一轮，若工作区根存在 `Knowledge/`：把本次变更文件清单与 `Knowledge/modules/<仓>/` 各模块卡 frontmatter 的 `module` 覆盖路径比对，命中 → 在最终汇报末尾追加一行：

> 知识沉淀提醒：本次改动命中模块卡「<卡名>」，建议按 `知识沉淀` 更新（说跳过就跳过）。

- 只提醒不强制、不展开、不阻塞提交
- 无命中或 `Knowledge/` 不存在 → 静默跳过

---

## 第五步：汇报结果

提交（并按需推送）后，汇报：

```
已完成：

  commit: <commit-hash-short>
  branch: <current-branch>
  message: <概述>
  push:   <origin/<分支名>（已推送）｜未推送（原因：…）>
```

## 特殊情况处理

### 没有任何变更

如果仓库是干净的，没有文件被修改：

- 告知用户："当前工作区是干净的，没有需要提交的变更。"
- 不做任何操作

### 合并冲突

如果检测到仓库处于合并冲突状态：

- 告知用户："检测到仓库处于合并冲突状态，请先解决冲突再生成 commit。"
- 不做任何操作
- 若用户接着要求解决冲突：改走 `解决合并冲突`（fetch 对照 + 在修改分支手改；禁止合入对方/测试分支，禁止整树覆盖）

### 用户说"生成 commit 并推送"

与默认行为一致（commit 后自动推送），照「推送规则」执行即可：

- 仅 `git push`，不加 `--force`；推送去向在汇报里写清楚
- 无上游的分支借机建上游前先问一句（`git push -u origin HEAD`）
- 仍受「安全边界」约束：绝不 `--force`，绝不执行 rebase / reset --hard / clean

### 修改文件过多无法确定范围

如果对话中涉及的文件较多，或者不确定哪些文件是用户想提交的：

- 列出所有有改动的文件
- 让用户选择要提交哪些

## 触发示例

以下说法都应触发此 skill：

- "生成 commit"
- "生成一个 commit"
- "帮我写个 commit message"
- "创建提交"
- "commit 一下"
- "写 commit"

**配合推送的示例**：
- "生成 commit 并推送"
- "生成 commit 然后 push"

**反例**（不应触发）：
- "git status" — 直接执行即可
- "查看提交历史" — 直接执行 `git log` 即可
- "推送" / "push" — 单独的推送操作，不需要生成 commit
