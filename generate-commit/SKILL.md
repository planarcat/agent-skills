# 生成 Commit

## 触发时机

当用户在开发过程中说出以下或相近表达时，使用本 skill：

- "生成 commit"
- "生成提交"
- "创建 commit"
- "写 commit"
- "写一个 commit"
- "帮我 commit"
- "commit 一下"

## 核心目标

根据仓库的修改情况，生成一条通俗易懂的中文 commit message 并提交；**在需求分支上开发时，提交完直接推送到该分支的远程同名分支**（见下「推送规则」）。

---

## 工作流程

```
1. 检查暂存区 → 2. 确定变更范围 → 3. 生成 commit message → 4. 执行 commit → 5. 汇报结果
```

---

## 第一步：检查暂存区状态

执行以下检查：

```bash
git diff --cached --stat     # 查看已暂存的文件
git status --short           # 查看完整状态
```

### 情况 A：暂存区有内容

以暂存区的修改为蓝本生成 commit。不再关心工作区未暂存的改动。

### 情况 B：暂存区为空

根据当前对话中讨论/修改过的文件，**只暂存这些相关文件**，然后生成 commit。

**重要约束：**
- 只暂存当前对话中明确涉及、修改过的文件
- 不得将仓库中其他不相关的改动一并暂存
- 如果对话上下文不足以确定哪些文件被修改了，先用 `git diff --stat` 查看所有改动，向用户确认后再暂存

---

## 第二步：确定变更范围

确定了目标文件后，获取变更详情用于撰写 commit message：

```bash
git diff --cached              # 查看已暂存的详细差异（情况 A）
# 或
git diff                       # 查看未暂存的详细差异（情况 B，暂存前）
```

如果变更超过 500 行，只取前 200 行和后 100 行以及关键改动区域，避免上下文溢出。

---

## 第三步：生成 Commit Message

根据变更内容，按以下规范生成中文 commit message：

### 格式

```
<类型>: <简短概述>

<详细说明（可选，复杂变更时添加）>
```

### 类型

| 类型 | 说明 |
|:---|:---|
| `feat` | 新功能 |
| `fix` | 修复 bug |
| `refactor` | 重构（不改变外部行为） |
| `style` | 格式/样式调整 |
| `docs` | 文档变更 |
| `test` | 测试相关 |
| `chore` | 杂项（依赖、构建、配置等） |
| `perf` | 性能优化 |

### 要求

1. **概述使用中文**，一句话说清楚做了什么
2. **语言通俗易懂**，让阅读者能够直观地理解修改了什么内容，但也要做到尽量精确
3. **不捏造内容**：如果上下文中看不到某些变更，不要在 commit message 中编造
4. **长度控制**：概述行尽量控制在 50 个中文字符以内
5. **详细说明**：当一次 commit 涉及多个文件或多项修改时，使用 `-` 列表简要列出每项变更

### 示例

```
feat: 新增用户登录日志记录功能

- 在 login 接口中增加日志写入逻辑
- 新增 login_logs 表及对应迁移脚本
- 管理后台增加登录日志查询页面
```

```
fix: 修复编辑页保存按钮偶发无响应的问题
```

```
refactor: 将剪贴板同步逻辑从 App 组件中抽取为独立模块
```

---

## 第四步：执行 Commit

生成 commit message 后，**先展示给用户确认**，格式如下：

```
建议的 commit：

  feat: 新增用户登录日志记录功能

  - 在 login 接口中增加日志写入逻辑
  - 新增 login_logs 表及对应迁移脚本

提交并推送到 <远程分支>？
```

然后执行：

```bash
git commit -m "<commit message>"
```

### 安全边界

- ✅ 执行 `git add`（仅情况 B 且经确认）+ `git commit`；**在需求分支上按「推送规则」再 push**
- ❌ **绝不执行 `git push --force`** 或任何带 `--force` 的操作
- ❌ **绝不自动执行 `git rebase`、`git reset --hard`、`git clean`** 等破坏性操作
- ⚠️ 用户明确说"只提交/先别推" → 只 commit，不 push

---

## 推送规则（开发规范）

**开发任务完成后，提交即推送到当前需求分支的远程同名分支。** 判据：

| 当前分支 | 怎么做 |
|---|---|
| **需求分支**（有同名远程上游，且上游不是主分支） | commit 后**直接 `git push`**（推给它自己的上游），不用每次都问 |
| 主分支 / 无上游 / 上游是主分支 | **不推**，只 commit，并说明原因（主分支不直接推） |
| 用户说"只提交""先别推" | 只 commit |
| 仓库文档（`AGENT.md` / `CLAUDE.md` / `AGENTS.md`）另有推送规定 | 按文档走 |

- push 只推**当前分支**：`git push`（已设上游）或 `git push origin HEAD`；**绝不 `--force`**。
- 推送前把目标分支写清楚（`push → origin/<分支名>`）。
- 推送失败（无权限、被拒、网络）→ 如实汇报失败与原因，**本地 commit 保留**，不要改用强制推送。

---

## 第五步：汇报结果

提交（并按需推送）后，汇报：

```
已完成：

  commit: <commit-hash-short>
  branch: <current-branch>
  message: <概述>
  push:   <origin/<分支名>（已推送）｜未推送（原因：…）>
```

---

## 特殊情况处理

### 没有任何变更

如果仓库是干净的，没有文件被修改：

- 告知用户："当前工作区是干净的，没有需要提交的变更。"
- 不做任何操作

### 合并冲突

如果检测到仓库处于合并冲突状态：

- 告知用户："检测到仓库处于合并冲突状态，请先解决冲突再生成 commit。"
- 不做任何操作
- 若用户接着要求解决冲突：改走 `resolve-merge-conflict`（fetch 对照 + 在修改分支手改；禁止合入对方/测试分支，禁止整树覆盖）

### 用户说"生成 commit 并推送"

即使是主分支/无上游的分支，用户明确说了"推送"也照做——但**先说明会推到哪里**：

- commit 完成后，执行 `git push`（仅 `git push`，不加 `--force`）
- 推送前提示用户即将推送到的远程分支名称
- 仍受「安全边界」约束：绝不 `--force`、绝不推主分支（除用户明确要求，且要再确认一次）

### 修改文件过多无法确定范围

如果对话中涉及的文件较多，或者不确定哪些文件是用户想提交的：

- 列出所有有改动的文件
- 让用户选择要提交哪些

---

## 触发示例

以下说法都应触发此 skill：

- "生成 commit"
- "生成一个 commit"
- "帮我写个 commit message"
- "创建提交"
- "commit 一下"
- "写 commit"

**配合推送的示例**：
- "生成 commit 并推送"
- "生成 commit 然后 push"

**反例**（不应触发）：
- "git status" — 直接执行即可
- "查看提交历史" — 直接执行 `git log` 即可
- "推送" / "push" — 单独的推送操作，不需要生成 commit
