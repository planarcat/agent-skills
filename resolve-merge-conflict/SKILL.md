# 手动解决合并冲突（禁止覆盖本地分支）

本地**修改分支**与远程（或其他）分支有冲突时，只能通过**拉取对照 + 比对差异 + 在修改分支上手改文件**解决。

**核心原则：本地修改分支上的工作成果不可被整树覆盖；远程内容只能作为对照，不能作为整包替换源。**

## 触发时机

- 「解决冲突」「处理合并冲突」「有冲突帮我合一下」
- 「同步远程有冲突」「pull 冲突了」「merge 冲突了」
- 「别覆盖本地」「不要用远程盖掉我的分支」
- Agent 发现 `git status` 处于合并/变基冲突，或推送/合并因冲突失败

**反例**：无冲突的普通 pull/merge；用户明确只要「看一下 diff、先别动」。

---

## 硬性禁止（违反即停）

下列做法**一律禁止**，即使用户口头说「用远程的」「直接覆盖」「快一点」也要先拒绝并说明本 skill 规则；仅当用户**再次书面明确授权「允许整树覆盖 / reset --hard」**时才可例外，且须复述风险。

| 禁止操作 | 典型命令/行为 |
|---|---|
| 用远程/其他分支整树覆盖当前修改分支 | `git reset --hard origin/<branch>`、`git checkout <other> -- .`、`git restore --source=<other> :/` |
| 检出其他分支再强推盖掉修改分支 | 切到远程分支后 `push --force` 到修改分支名 |
| 合并时无脑全盘采用对方 | `git merge -X theirs`、对冲突文件一律 `git checkout --theirs`（未逐文件核对内容） |
| pull 策略丢弃本地修改 | `git pull -X theirs`、会丢弃本地提交/工作区的强制同步 |
| 用其他分支工作区直接替换本分支目录 | 复制粘贴整仓、删光再 checkout 其他分支文件树 |

**一句话：不能把「别的分支」整包盖到「本地修改分支」上。**

---

## 正确流程（必须按序）

全程保持在**本地修改分支**上操作（不要为了「解决冲突」先切走再切回覆盖）。

### 1. 确认身份与状态

```bash
git branch --show-current
git status
git remote -v
```

记下：当前修改分支名、冲突对方（如 `origin/main`、`origin/dev/...`）、是 merge / rebase / 未开始合并。

### 2. 将远程分支拉取到本地（只作对照，不覆盖）

```bash
git fetch origin
```

需要本地可读的对照分支时：

```bash
# 更新远程跟踪引用即可，足够做 diff
# 或显式建只读对照分支（不要 checkout 覆盖当前工作区）
git branch -f _conflict_ref origin/<对方分支>
```

- ✅ `fetch`、更新 `origin/*`、建对照分支/引用  
- ❌ `checkout` 对方分支并带走/丢掉当前修改分支的提交或工作区

### 3. 比对差异（先看清再改）

在**仍停留在修改分支**的前提下比对：

```bash
git diff HEAD...origin/<对方分支> --stat
git diff HEAD...origin/<对方分支> -- path/to/file
# 或
git diff <修改分支> _conflict_ref -- path/to/file
```

产出清单：哪些文件仅我方改、仅对方改、双方都改。优先处理双方都改的文件。

### 4. 只在修改分支上改对应文件

对每个冲突文件：

1. 打开当前修改分支上的该文件  
2. 对照对方版本（diff / 只读查看对方 blob，**不要**整文件 `checkout --theirs` 除非已通读且确认应全文采用，且仍算「看过差异后的手改决策」）  
3. **手动编辑**合并双方意图：保留本地必要改动，纳入对方必要改动  
4. 若已处于 merge 且出现 `<<<<<<<` / `=======` / `>>>>>>>`：在本文件内手改消除标记，保存后 `git add <file>`

重复直到：

- 无冲突标记  
- `git status` 无 unmerged paths  
- 需要完成合并时再 `git commit`（仅在用户要求提交时；本 skill 默认解决到工作区干净/可继续开发即可）

### 5. 验证

```bash
git status
# 可选：再 diff 一次确认未误删对方关键改动
git diff origin/<对方分支> -- path/to/resolved-files
```

向用户简要说明：改了哪些文件、如何取舍（本地保留 / 纳入远程 / 手工合并）。

## 与「merge / rebase」的关系

| 场景 | 做法 |
|---|---|
| 尚未开始合并，只是发现会分叉 | fetch → diff → 在修改分支手改对齐；或开始 `git merge origin/<对方>` 后按第 4 步逐文件手解 |
| 已在 merge 冲突中 | **留在当前修改分支**，逐文件手解 → `git add` → 完成 merge commit（若用户要） |
| 已在 rebase 冲突中 | 同样逐文件手解；禁止 `rebase --abort` 后改用 hard reset 盖分支来「假装解决」 |

允许使用 `git merge` / `git rebase` **作为进入冲突状态的手段**；不允许用它们搭配「全盘 theirs / hard reset」当作解决手段。

## 自检清单（改完必勾）

```
- [ ] 全程未离开「用覆盖方式同步」的禁令
- [ ] 已 fetch，并用 diff 对照过对方分支
- [ ] 所有改动都发生在本地修改分支的对应文件上（手改）
- [ ] 无冲突标记，git status 无 unmerged
- [ ] 未执行 reset --hard / checkout 对方整树 / 无脑 --theirs
```

---

## 对用户的话术（拒绝覆盖时）

> 按冲突处理规范，不能用远程分支直接覆盖本地修改分支。我会先拉取远程作对照，比对差异后，在你当前修改分支上逐文件手改，直到没有冲突。

## 触发示例

| 用户说 | 行为 |
|---|---|
| 「pull 有冲突，帮我解决」 | fetch → diff → 修改分支手改 |
| 「直接用远程的盖过去」 | 拒绝；说明只能手改合并 |
| 「和 main 冲突了」 | 对照 `origin/main`，在当前分支改文件 |
| 「checkout 远程文件到本地得了」 | 禁止整树；可对单文件在核对 diff 后谨慎采纳并仍视为手改决策 |
