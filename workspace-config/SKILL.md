# 工作区配置（技能的「工作区适配层」）

**一句话**：技能只写**怎么做**；工作区特有的**在哪、是谁、叫什么**全部放配置里。**agent 开工前先读配置，缺什么问用户一句、问到就写回配置，再动工。**

## 一、配置放哪

| 项 | 位置 |
|---|---|
| 配置文件 | `<工作区根>/Docs/工作区配置.md`（Markdown 分节，人机共读） |
| 配套资源 | `<工作区根>/Docs/工作区配置/`（规范源文件、脚本、映射表等"大件"放这里，配置里只写文件名） |
| 进不进 git | **不进**（工作区在 git 里时把 `Docs/工作区配置*` 加进 `.gitignore`） |

**为什么用 Markdown 而不是 JSON**：人要读得懂、agent 好读好写、懒初始化时**直接追加一节**即可，不用维护 JSON 语法；值多是路径 / 名称 / 命令，不需要严格类型。

## 二、字段清单（配置的「标准节」——缺哪节补哪节）

| 节 | 写什么 | 谁在读 |
|---|---|---|
| `仓库与端` | 端前缀字母 ↔ 仓库目录 / 远程仓库；生产分支、测试分支 | 创建分支、分支合入检查、清理分支 |
| `服务与端口` | 起服务指令（如工作区 `dev <id后4位>`）、端口分配规则、进程管理方式 | 创建分支、自测验收 |
| `落盘路径` | 各类产物路径：需求拆解、日报（素材 / 成稿）、知识库、方案、改动记录 | 需求拆解、日报三件套、知识沉淀、改动记录、方案 |
| `人员与角色` | 需求负责人 / 开发 / 测试 / 组长或审批 / 对接人 | 日报（协同人）、需求拆解（owner）、上线相关 |
| `外部系统` | 需求系统（项目名 + 连接器）、代码托管（组织 / 仓库列表）、CI 与部署入口 | 需求类、推送审计类、部署 |
| `测试` | 测试环境卡路径、**测试账号（一个身份一行：role / 账号 / 密码 / 说明）**、各仓跑测命令、门禁能力（有无 test / vitest / 变异） | 类人测试、测试用例编写、需求拆解定级 |
| `规范源` | 各方规范文件的位置（日报填写规范、设计规范、命名规范…） | 日报三件套、界面设计规范 |
| `脚本` | 工作区提供的脚本（建分支、清理、部署…）与调用方式 | 创建分支、清理分支 |

## 三、懒初始化流程（**每个技能的第一步都是它**）

1. **读** —— 要碰工作区特有内容之前，先读 `<工作区根>/Docs/工作区配置.md`
2. **对** —— 本次要用的那一节在不在、值是不是空的
3. **缺 → 停下来问**（**只问缺的那一项**，别一次问一堆）。**可以带建议，但不能替用户决定**，固定这个句式：
   > 我建议把 <配置项> 设为 `<推荐值>`（理由：<…>）。要我写进配置吗？
   然后**等用户点头**（"可以 / 就这个 / 改成 Z"）才算定了。
4. **用户给了明确的值（或同意你的建议）→ 才写回配置** → 当次就用 → **下次不再问**
   用户没回 → **停下等**，不自行推进、不拿"临时值"先干着
5. **都不缺 → 直接动工**
6. **不做**：不猜、不假设、不用"上次记得好像是…"顶替配置

### 缺项铁律（2026-10-20 用户口径 · 硬约束）：**可以建议，不可以先斩后奏**

配置里**没有**某条信息时：

✅ **允许**（建议 + 问句 + 等点头）：

> 我建议把「日报素材目录」放在 `<路径>`（理由：<…>）。要我改这个配置吗？

❌ **禁止**（自己拍值 → 写进配置 → 按它开工）：

> 配置里没有日报素材目录条目，我觉得应该放 `<路径>`，**我现在主动把配置写上**，然后去写素材放到这个目录下。

**和「素材即意图」的边界（别搞混——两者管的事不同）**：

| 问题 | 规矩 |
|---|---|
| **做什么**（任务本身：解冲突、建分支、修缺陷、拆解需求） | 素材已经回答了 → **不反问，直接干** |
| **用什么值**（工作区特定值：路径 / 人名 / 端口 / 仓名 / 规范文件） | 配置里没有 → **必须停下问**；可以建议，**不许自行落地** |

**值的来源只有两个**：① 配置里已有 ② **用户明确给的**。agent 自己的推断**不算来源**——可以提出来，但不能据此行动。

## 五、铁律

1. **技能正文里不得出现工作区特有的具体值**（具体仓名、端口、人名、项目号、路径）——一律写成「读配置 `X` 节」。
2. **配置只有一份**（工作区根 `Docs/工作区配置.md`），所有技能共用，不各存一份。
3. 缺配置就**停下来问**，不要边猜边开工；问到就**写回配置并当场继续**。
4. 首次在某工作区干活的技能，把「有没有这份配置」当作**第一动作**检查。

## 六、这就是技能能通用的原因

把技能拷到别的工作区 / 别的公司时：**技能一个字节都不用改**，只需在新工作区准备一份 `Docs/工作区配置.md`（没有就用懒初始化问用户建一份）。
**配置是工作区的东西，技能是通用引擎。**
