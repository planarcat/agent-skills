# 工作区配置（技能的「工作区适配层」）

**一句话**：技能只写**怎么做**；工作区特有的**在哪、是谁、叫什么**全部放配置里。**agent 开工前先读配置，缺什么问用户一句、问到就写回配置，再动工。**

## 一、配置放哪（双文件制 · 2026-10-22 用户口径）

| 项 | 位置 | 放什么 |
|---|---|---|
| **数据源**（脚本与技能读值） | `<工作区根>/Docs/工作区配置.json` | 仓库与端映射、分支名、端口、落盘路径、需求系统项目、测试账号、脚本参数 |
| **规矩与说明**（人读） | `<工作区根>/Docs/工作区配置.md` | 端/仓前缀口径、分支命名口径、起服务方式、人员与角色、规范源、脚本清单、取用纪律 |
| 配套资源 | `<工作区根>/Docs/工作区配置/` | 规范源文件、映射表等"大件"，配置里只写文件名 |
| 进不进 git | **不进**（`Docs/工作区配置*` 加进 `.gitignore`） | — |

**两条纪律**：

1. **值只写在 json**。md **不重复抄值**——同一个值出现两处，迟早漂移。md 里要提值，只写 `见 json › <键>`。
2. **脚本读 json，agent 读两边**：脚本取数只认 json；agent 取值读 json，读纪律/人员/规范源读 md。

**为什么拆两份**：脚本要机器可读、要稳定 schema，JSON 最合适；而"缺项怎么问、谁负责、规范在哪"是给人和 agent 看的规矩，Markdown 更清楚。混在一份里，脚本解析脆弱、人也不好看。

## 二、JSON 字段清单（缺哪个键补哪个键）

| 键 | 放什么 | 谁在读 |
|---|---|---|
| `repos` | 端字母 → 仓库 / 前端 / 后端 / 仓前缀 / 生产分支 / 测试分支（`null`＝未确认） | 创建分支、分支合入检查、清理分支、需求拆解落盘 |
| `tapdWorkspaces`（或对应需求系统的项目键） | 项目别名 → 项目 id | TAPD 待办查询、TAPD 需求撰写、需求拆解、日报撰写 |
| `paths` | 各类产物路径：需求拆解、日报、知识库、方案、改动记录 | 需求拆解、日报三件套、知识沉淀、改动记录、方案 |
| `devPorts` | 端口段位 / 分配规则（可带 `_note` 写明未定端） | 创建分支（起服务）、类人测试 |
| `testAccounts` | 数组，**一条＝一个身份**：`role` / `end` / `username` / `password` / `desc` / `since` | 类人测试、测试用例编写、需求拆解（接口查证） |

**不进 json、只在 md 的**（放 json 没有收益，且常变）：`人员与角色`（本人 / 主管 / 对接人）、`规范源`（规范文件位置）、`脚本`（脚本清单与调用方式）、各类**口径与纪律**。

## 三、懒初始化流程（**每个技能的第一步都是它**）

1. **读** —— 先读 `<工作区根>/Docs/工作区配置.json`；再按需读 `工作区配置.md` 的对应节
2. **对** —— 本次要用的那个键 / 那节在不在、值是不是空的（`null` 也算缺）
3. **缺 → 停下来问**（**只问缺的那一项**，别一次问一堆）。**可以带建议，但不能替用户决定**，固定这个句式：
   > 我建议把 <配置项> 设为 `<推荐值>`（理由：<…>）。要我写进配置吗？
   然后**等用户点头**（"可以 / 就这个 / 改成 Z"）才算定了。
4. **用户给了明确的值（或同意你的建议）→ 才写回配置** → 当次就用 → **下次不再问**
   - 写回 **json** 时保持**合法 JSON**：补键、补数组元素，不要破坏缩进与已有键；不确定就整段读出来改结构再写
   - 写回后**当场再读一遍**确认能解析（`python3 -m json.tool <文件> >/dev/null` 之类），别把坏 JSON 留给下一个 agent
   - 用户没回 → **停下等**，不自行推进、不拿"临时值"先干着
5. **都不缺 → 直接动工**
6. **不做**：不猜、不假设、不用"上次记得好像是…"顶替配置

### 缺项铁律（2026-10-20 用户口径 · 硬约束）：**可以建议，不可以先斩后奏**

配置里**没有**某条信息时：

✅ **允许**（建议 + 问句 + 等点头）：

> 我建议把「日报素材目录」放在 `<路径>`（理由：<…>）。要我改这个配置吗？

❌ **禁止**（自己拍值 → 写进配置 → 按它开工）：

> 配置里没有日报素材目录条目，我觉得应该放 `<路径>`，**我现在主动把配置写上**，然后去写素材放到这个目录下。

**和「素材即意图」的边界（别搞混——两者管的事不同）**：

| 问题 | 规矩 |
|---|---|
| **做什么**（任务本身：解冲突、建分支、修缺陷、拆解需求） | 素材已经回答了 → **不反问，直接干** |
| **用什么值**（工作区特定值：路径 / 人名 / 端口 / 仓名 / 规范文件） | 配置里没有 → **必须停下问**；可以建议，**不许自行落地** |

**值的来源只有两个**：① 配置里已有 ② **用户明确给的**。agent 自己的推断**不算来源**——可以提出来，但不能据此行动。

## 五、铁律

1. **技能正文里不得出现工作区特有的具体值**（具体仓名、端口、人名、项目号、路径）——一律写成「读 `工作区配置.json` 的 `<键>`」或「读 `工作区配置.md` 的 `<节>`」。
2. **值只有一份，在 json**；md 只写规矩。**不许两边双写**。
3. **写回 json 必须保持合法 JSON**，写完自检一次能不能解析。
4. 缺配置就**停下来问**，不要边猜边开工；问到就**写回配置并当场继续**。
5. 首次在某工作区干活的技能，把「有没有这份配置」当作**第一动作**检查。

## 六、这就是技能能通用的原因

把技能拷到别的工作区 / 别的公司时：**技能一个字节都不用改**，只需在新工作区准备 `Docs/工作区配置.json` + `工作区配置.md`（没有就用懒初始化问用户建）。
**配置是工作区的东西，技能是通用引擎。**
