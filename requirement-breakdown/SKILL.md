# 需求拆解（开发前的需求理解）

**定位**：把一条需求拆成「能开工、能验收、能填日报」的粒度。**不写代码、不改代码、不做方案设计**（要技术方案走 `plan-discussion`）。

**为什么存在**：日报 v3 硬规则——需求**首次进「开发中」之前必须写过一次需求理解**（边界 / 歧义 / 待确认点）。本技能就是把这个动作变成有产出的步骤。

## 何时用

- `create-requirement-branch` 建完分支之后、动手开发之前（**流程上的固定一站**）
- 需求首次要进「开发中」之前（日报硬规则）
- 用户说「需求拆解」「拆解一下这个需求」「写需求理解」

**反例**：需求本身就模糊、连要什么都说不清 → 先走 `requirement-clarification`（澄清），别硬拆。

## 输入

- **TAPD 需求 id / 链接**（优先）：用 tapd 连接器拉详情（`get_stories_or_tasks` 按 id，取 name / description / owner / 迭代 / 关联子需求）
- 没给 id：问一句要拆哪条；连需求文本都没有 → 让用户贴，**不编造**

## 流程

1. **拉需求原文**：TAPD 详情 + 相关评论；口头补充的需求点单独标注"口头补充，未落单"。
2. **拆功能点**：拆成可独立开发、可独立验收的最小单元。每个点标注：
   - 改哪端（用户端 / 工厂端 / 平台端 / POD 服务端）
   - 涉及页面 / 组件 / 接口
   - 依赖（后端接口、设计稿、其他人的活）与依赖状态
3. **写四栏**（这是本技能的核心产出）：
   - **边界**：做什么 / **明确不做什么**（最容易漏）
   - **歧义**：同一句话可能有两种理解的点，写清两种理解分别是什么
   - **待确认**：要问谁（**真名**）、问什么、期望什么时候有答案
   - **验收标准**：可执行的功能性核对（"工厂端删除规格后用户端不再展示"这种），**不写用例数量**
4. **输出「需求理解」短文**：一段可直接填进日报②栏的文字（边界 + 歧义 + 待确认点），**不写漂亮话、不复述需求原文**。
5. **落盘（按日期归档）**：放**工作区根目录**的 `Docs/` 下 —— `Docs/需求拆解/{拆解当月：YYYY-MM}/{短id后4位}-{短标题}.md`
   - **统一落在工作区根目录**（工作区级文档）：不放进单个仓库 / worktree；目录不存在就创建。
   - 按拆解当天所在**月份**建子目录归档（同月的需求在一个文件夹里，找"9 月拆的"直接进 2026-09/）。
6. **不随代码提交**：拆解文档是工作区级文档、与代码解耦，无需随需求分支 commit / push；要另行备份或提交，用户说了算。
7. **有待确认点 → 先分流，别一律卡住**（2026-09-21 用户口径）：只有**会影响架构 / 接口契约 / 数据模型**的点需要现在定（≤2 条，一次问完）；其余标成「边做边定」，给出**默认处理 + 影响面**，**不阻塞开工**。确认结果回填文档并同步 TAPD。

## 产出模板

```markdown
# 需求拆解：{需求标题}（{短id}）

> 来源: TAPD {id} ｜ owner: {谁} ｜ 拆解时间: YYYY-MM-DD HH:mm

## 功能点
1. {功能点}（{哪端}）——依赖：{接口/设计稿/他人，状态}

## 边界
- 做：…
- 不做：…（及为什么）

## 歧义
- {原话}：可理解为 A，也可理解为 B → 按 {X} 处理，因为…

## 待确认
- [ ] {问题} → 问 {真名}，期望 {时间}

## 验收标准
- {可执行的功能性核对，逐条}

## 需求理解（日报②栏可直接用）
{一段话：边界 + 歧义 + 待确认点，白话、不复述原文}
```

## 已在开发中：走增量确认（不阻塞）

**判断**：需求已进「开发中」、或已建需求分支、或已在改代码 → **不要发起一轮"澄清"，也不要改回澄清中状态**。

| 做法 | 说明 |
|---|---|
| 代码事实优先 | 现有接口参数、现有页签与容器实现这类问题**自查代码**，不要拿去问用户（例：`GET /productorder/page` 支持哪些参数 → 翻接口定义就行） |
| 问题分两栏 | **必须现在定**（影响架构/接口契约/数据模型，通常 0~1 条）／**边做边定**（默认怎么实现 + 影响的页面范围） |
| 不阻塞 | 除"必须现在定"的那 1~2 条，其余**先按默认实现往前走**，边界出现时再问一句 |
| 状态不后退 | 已开发中的需求保持「开发中」；澄清产物写成**增量确认**附在需求/分支上，不单独设"澄清中" |
| 截图读不到时 | 不要围着截图开问题清单——按文字口径 + 代码现状推进，把关键假设写明，缺的点问 1~2 条即可 |

**产出形态**：一栏「已确认（代码事实）」+ 一栏「边做边定（默认处理）」+ 一栏「必须现在定（≤2 条）」。

## 红线

1. **不编造**：TAPD 上没有的细节不脑补；描述与口头说法不一致 → 以确认结果为准，并把不一致记进「待确认」。
2. **拆解不动代码**：本技能只产出文档与问题清单。
3. **不要用待确认卡住已在开发中的需求**（2026-09-21 用户口径）：需求一旦进入开发（或已建分支 / 已在改代码），**状态只前进不后退**（别退回「澄清中」）；口径不清的**按现状实现 + 显式标注假设**，边开发边解释。
4. 拆解结果**同步回 TAPD**（评论/子需求），日报②栏引用本技能的产出，别两处各写一套。

## 与其他技能的关系（条件引用）

| 技能 | 关系 |
|---|---|
| `create-requirement-branch` | 流程上前一站（建分支）；拆解的文件命名与它的分支名同源 |
| `requirement-clarification` | 需求**本身模糊**时先走它；澄清结论是本技能的输入 |
| `prd-authoring` | 大需求要写 PRD 时，本技能的功能点清单就是 PRD 的骨架 |
| `plan-discussion` | 需要技术方案时，拿拆解结果去讨论方案 |
| `plan-execution` | 拆解的功能点可直接变成 execution-plan 的任务清单 |
| `report-writer` | 日报②「需求理解与方案输出」直接引用本文档的「需求理解」短文 |
| `tapd-todo-query` | 拉 TAPD 详情 / 回写确认结果（需 tapd 连接器） |

## 触发示例

- 「需求拆解 1140677205001002792」→ 拉详情 → 产出拆解文档 + 日报②栏短文
- 「把 WB 颜色分组这个需求拆一下，我要开工了」
- 「写一下这个需求的需求理解」（日报要用）
- 建完分支后提醒一次（不说日报）：「开工前先把这条需求的边界与待确认点定下来，要现在做吗？」
