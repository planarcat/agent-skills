# 用户故事 + 验收标准

将需求拆成 **用户故事（User Story）** 与 **验收标准（AC）**，可选附带测试用例提纲。本 skill **只写文档/对话产出，不改代码**。

## 触发时机

- 「拆故事」「写用户故事」「补用户故事」
- 「写 AC」「写验收标准」「验收怎么写」
- 「给测试用例提纲」「列出测试点」「按 Given/When/Then 写」
- 已有 PRD/口述需求，只要故事与 AC，不要整份 PRD

## 与相邻 skill 的边界

| Skill | 何时用 |
|---|---|
| **本 skill** | 故事 + AC（+ 可选测试提纲） |
| `prd-authoring` | 完整 PRD（含背景/埋点/依赖仓等） |
| `requirement-clarification` | 范围不清，先澄清 |
| `test-case-authoring` | 在仓库里编写/运行自动化测试代码 |
| `plan-discussion` | 技术方案讨论 |

需要落盘自动化测试文件时，交给 `test-case-authoring`，本 skill 只给 **提纲**。

## 落盘位置（可选）

| 场景 | 路径 |
|---|---|
| 独立文档 | `Docs/用户故事/YYYY-MM-DD-{中文主题简称}.md` |
| 依附 PRD/方案 | 同目录下 `用户故事与验收.md`，或写入 PRD「用户故事/验收」章节 |
| 仅对话交付 | 用户未要求落盘则可不建文件 |

❌ 禁止改业务源码。

## 工作流程

1. 确认角色、目标行为、成功样子；信息不足先短问。
2. 拆故事：每条一个价值点；标 P0/P1/P2。
3. 为每条故事写 AC：**强制 Given / When / Then**。
4. 可选：输出测试用例提纲（手工或 E2E 思路，非代码）。
5. 标出依赖其他故事或「待确认」项。

## 输出模板

```markdown
# {主题} — 用户故事与验收

## 范围摘要
- 做：…
- 不做：…

## 故事列表

### US-01 [{P0|P1|P2}] {短标题}

**故事：** 作为 {角色}，我想要 {能力}，以便 {价值}。

**验收标准：**

1. **Given** {前置/上下文}
   **When** {操作}
   **Then** {可观察结果}

2. **Given** …
   **When** …
   **Then** …

**备注 / 待确认：**（可选）

---

### US-02 …

## 测试用例提纲（可选）

| 编号 | 覆盖故事 | 类型 | 步骤摘要 | 期望 |
|---|---|---|---|---|
| TC-01 | US-01 | 主路径/异常/边界 | | |
```

## 强制规则

1. **每条 AC 必须是 Given/When/Then**（可用中文「给定/当/则」，结构不可缺）。
2. **Then 必须可观察**：界面文案、状态、列表数据、接口错误码、文件是否生成等；禁止「体验流畅」「比较友好」「性能好」等空话，除非附带可测定义（如「3 秒内出结果」「列表不少于 N 条」）。
3. **一条故事不应塞进多个无关价值**；过大则拆分。
4. **异常与权限**：P0 故事至少考虑无权限、空数据、失败提示之一（若适用）。
5. **不编造**产品未确认的规则；不确定标「待确认」。

## 反例 → 正例

❌ Then：页面体验更好。  
✅ Then：提交成功后 Toast 显示「保存成功」，并返回列表页且新记录出现在第一行。

❌ Then：性能优化。  
✅ Then：在约定测试账号下，打开详情页至首屏关键信息可见的时间 ≤ 2s（本地/测试环境约定）。

## 对话交付摘要

1. 故事条数与 P0 列表  
2. 仍待确认项  
3. 若已落盘：文件路径
