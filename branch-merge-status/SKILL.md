# 分支合入检查

**只读**：本技能只查、只报，不做任何删除 / 修改。要清理转 `清理分支`。

一句话口径：**「计数为 0」不等于「合入了」**——空壳分支的计数也是 0。必须走完第 3 步才能下结论。

## 仓库与分支地图（写反就是 404）

| 称呼 | 生产分支 | 测试分支 | 仓库路径（查开放 MR 用） |
|---|---|---|---|
| 灵创用户端 `lingchuang-front` | `main2` | **`main_test`（下划线）** | `lcpod/lc/lingchuang-front` |
| 灵创工厂端 `factory-front` | `main2` | **`main-test`（连字符）** | `lcpod/lc/factory-front` |
| 设计器 `laitu-designer` | `main` | 无 | `lcpod/Laitu/laitu-designer` |
| ShopAgent `shop-agent` | `develop` | 无 | `lcpod/lc/shop-agent` |

- 分支名实际以 `git ls-remote --heads origin` 为准；上表对不上时按远端实际分支走，判不了**问一句**。
- 需求分支命名：`{U|F|D|S}{id后4位}-{标题}`；合并分支：`{U|F|D|S}{id后4位}-To-test`。
- 老格式残留（`dev/hcb/1002668_…`、`20260901-…`）不算当前规范分支，但**常是本需求真正的交付分支**（见第 3 步交叉验证）。

## 第 1 步：对齐远程

```bash
git fetch --prune origin
```

- 每个仓各跑一次；**先 fetch 再看**，否则结论全是旧的。
- 本机 commit 多了以后 `git branch -vv` 列宽会被中文撑歪，**不要 grep 解析**，一律用 `for-each-ref --format`。

## 第 2 步：两把尺子，先分四类（机器可判）

逐条本地分支算两个数（分支名含中文/全角括号，**shell 里必须加引号**）：

```bash
for b in $(git for-each-ref --format='%(refname:short)' refs/heads); do
  A=$(git rev-list --count "origin/<生产分支>..$b")   # 还没进生产的提交数
  B=$(git rev-list --count "origin/<测试分支>..$b")   # 还没进测试线的提交数
  echo "$b | 未进生产:$A 未进测试:$B"
done
```

| A 未进生产 | B 未进测试 | 类型 | 含义 | 可清理 |
|---|---|---|---|---|
| 0 | 0 | ✅ **已进生产** | 分支所有提交都在生产分支历史里 | **可能可清（还要过第 3 步）** |
| 0 | 0 | 🫥 **空壳** | 计数也是 0，但**分支上一行没改**——只是停在基线快照上 | ❌ 不可清 |
| 0 | >0 | 🏭 **只进生产** | 分支带了生产线独有的提交（双向分叉的产物） | 视同「已在生产」，可清 |
| >0 | 0 | 🧪 **只进测试线** | 待验收 / 待发版 | ❌ 不可清 |
| >0 | >0 | 🚧 **未合入 / 开发中** | 还在做，或提了但没合 | ❌ 不可清 |

- `A == 0` 的唯一含义是「分支的提交都已在生产分支里」；**它不能区分「真合入」和「空壳」**，下一步专治这个。
- 没有测试分支的仓（设计器 / ShopAgent）只看 A 一列。

## 第 3 步：区分「真合入」与「空壳」（本技能的核心）

对 A / B 都是 0 的分支，取三个特征（**①② 命中任一即判「疑似空壳」**）：

**特征① 多分支共指 tip**（最强的空壳信号——多条不相干分支指向同一提交 = 基线快照）

```bash
TIP=$(git rev-parse "<分支>")
git for-each-ref --format='%(objectname)' refs/heads | grep -c "^$TIP"     # ≥2 → 命中
```

**特征② tip 是「别人的合并提交」**（平台合并提交落在别人的分支名上）

```bash
git log -1 --format=%s "<分支>"      # 形如「合并来自 <别的分支> 的合并请求 #N」→ 命中
```

**特征③ 找不到本需求的合并记录**（辅助信号，单独命中**不**作结论）

```bash
git log --all --oneline --grep="合并来自 <分支名> 的合并请求" | head -1
git log --all --oneline --grep="合并来自 <端><id后4位>-To-test 的合并请求" | head -1
```

**反面证据（出现任一条 → 不是空壳，直接判真合入）**

- 分支 tip 是普通开发提交（`feat:` / `fix:` / `style:` …），且**只被这一条分支指向**
- 分支上能查到本需求的提交：`git log --oneline "<分支>" | grep -E "<id后4位>|<标题关键词>"`
- 存在「合并来自 <本分支名> 的合并请求」或「合并来自 <本 To-test> 的合并请求」的记录

**交叉验证（判疑似空壳后必做，不许跳过）**

```bash
git log --all --oneline --grep="<id>" | head -10     # 全库找本需求的真实交付记录
```

- 若命中一条形如「合并来自 `dev/hcb/<id>…` 的合并请求 #N」的记录 → **本需求其实由那条旧命名分支交付**，报告里点名「实际交付分支」，当前分支是空壳。
- 若全库完全查不到 → 空壳 + **从未交付**（标注出来，这是需求管理的信号，不只是清理问题）。
- 仍然判不了 → 标 **「疑似空壳，待确认」**，把三条特征的实际输出一起给用户，**不猜**。

## 第 4 步：附加核查（一并报，缺一项结论就不完整）

| 项 | 命令 | 要报什么 |
|---|---|---|
| **双向分叉** | `git rev-list --count origin/<测试>..origin/<生产>`（生产独有）与反向（测试待发版） | 生产线有测试线没有的提交 → **危险信号，必须单独点出**（往往是 revert / 直接进生产造成） |
| 本地 vs 远程 | `git rev-list --left-right --count "<分支>...origin/<分支>"` | 非 `0 0` = 本地没推 / 远程有新提交 |
| 上游 | `git rev-parse --abbrev-ref "<分支>@{u}"` 报错 | 没设上游（远程分支可能仍在） |
| worktree ↔ 分支 | `git worktree list` | 目录名与分支名不一致的、目录已丢但分支还在的 |
| pm2 服务 | `~/Library/pnpm/pm2 ls`（**沙箱外**跑） | 在跑的服务对应哪条分支；「分支已合入但服务还开着」要报 |
| 开放 MR | `cnb pulls list-pulls --repo <路径> --state open --page-size 50`（需 cnb 连接器） | 有未合入提交却**没有开放 MR** → 要点出（多半忘了提） |

## 输出格式

按仓分表，一行一条分支，**证据列必填**：

```
## <仓名>（生产 <生产分支> / 测试 <测试分支>）
测试线待发版：N 个提交 ｜ 生产线独有：M 个提交
开放 MR：0 条

| 分支 | 未进生产 | 未进测试 | tip | 类型 | 备注 |
|---|---|---|---|---|---|
| U-2931-【新增店铺】… | 4 | 4 | 4124492b | 🚧 未合入 | 无开放 MR |
| U-2961-【选品库】样品实拍图展示 | 0 | 0 | 119221cc | ✅ 已进生产 | 有本需求提交（style: …） |
| 2668-【手工单…】 | 0 | 0 | a97963dd | 🫥 空壳 | 共指 6 条；实际交付分支 dev/hcb/1002668_…（MR#424） |
```

表后给「要点」：**可清理清单**（只列 ✅ 且非空壳）、**空壳清单**、**双向分叉**、**其他异常**（未推 / 没上游 / 服务还开着 / 缺 MR）。

- 每条结论都要能指到「哪个命令、哪个计数、哪个 SHA」。
- **找不到就说找不到**，不要用「应该已合入」这类推断填坑。

## 坑（都是踩过的）

- `main_test` 是用户端、`main-test` 是工厂端，写反直接 404。
- 分支名含中文与全角括号 → 不加引号会被 shell 拆开；`git rev-parse` 报 `ambiguous argument` 多半就是这个。
- **空壳分支的计数也是 0**，只报「0 = 已合入」＝ 误判，必定要过第 3 步。
- 空壳的成因是**从基线拉到一半的旧快照**：同一天批量建的多条分支会共指同一个提交（实测 6 条共指 `a97963dd`、4 条共指 `88a0bf33`）——共指就是最硬的证据。
- 已合入的分支**合并记录可能挂在自己的 To-test 分支上**（`合并来自 U-2961-To-test 的合并请求`），只查自己的分支名会误判成「没交付」。
- 老命名分支（`dev/hcb/<id>_…`）常是真交付分支；只按新命名找会得出「这条需求从没做过」的错误结论。
- 双向分叉是常态但危险：生产线独有提交意味着**测试环境复现不了生产问题**，必须报。
- `pm2` 与 `git push` 的动作要**沙箱外**跑；只 `pm2 ls` 读取时同样建议沙箱外（要读 `~/.pm2`）。
- 判断不了**问一句**，不要猜着往下走。
