# 发版说明（PM）

把版本变更整理为 **对用户 / 对运营 / 对研发** 三套说明。本 skill **只写文案/文档，不改代码、不做 git commit**。

## 触发时机

- 「写发版说明」「写版本更新说明」「出 release notes」
- 「写 changelog」「对内对外发版文案」
- 「这个版本对外怎么说」「给运营一版更新点」

## 与相邻 skill 的边界

| Skill | 何时用 |
|---|---|
| **本 skill** | 产品向发版说明（三套受众） |
| `generate-commit` | Git commit message |
| `record-change-log` | 开发过程短日志（`Logs/`） |
| `record-development-blog` | 问题/需求复盘长文（`Blogs/`） |

## 输入

优先使用：用户粘贴的变更列表、PR 标题、`Plans/`/`Docs/`、对话中的已完成项。  
信息不足时追问：版本号、发布日期、平台（来图/设计器/工厂端/后端）、是否含破坏性变更。

## 落盘位置（可选）

- `Docs/发版说明/YYYY-MM-DD-{版本号或主题}.md`
- 或用户指定路径

同名加 `-2`、`-3`。❌ 禁止改业务源码。

## 工作流程

1. 收集变更，按 **新功能 / 优化 / 修复 / 已知问题 / 破坏性变更** 归类。
2. 过滤：对用户不可见的纯内部重构，默认只进「对研发」；除非用户要求对外宣传技术亮点。
3. 产出三套语气（见模板）；专有名词首次可「中文（English）」。
4. 落盘或对话交付；标出版本与日期。

## 输出模板

```markdown
# 发版说明 — {产品/端} {版本号}

| 项 | 内容 |
|---|---|
| 日期 | YYYY-MM-DD |
| 范围 | 来图 / 设计器 / 工厂端 / 后端 / 其他 |

---

## A. 对用户（对外）

语气：简洁、受益导向、少行话；不提内部模块名。

### 新功能
- …

### 体验优化
- …

### 问题修复
- …（用户能感知的）

### 注意事项（若有）
- 需重新登录 / 旧数据需迁移 / 某入口变更 等

---

## B. 对运营（对内业务）

语气：讲清「对业务动作的影响」、配置/开关、文案与活动注意点。

### 可对外沟通要点
- …

### 运营动作
- 是否改培训/话术/FAQ
- 是否依赖配置后台、白名单、灰度

### 风险与客服预案
- 可能收到的反馈 & 建议回复

---

## C. 对研发（对内技术）

语气：准确、可检索；可含模块路径、接口、迁移、开关默认值。

### 变更列表
| 类型 | 说明 | 仓/模块 | 备注 |
|---|---|---|---|
| feat/fix/refactor | | | |

### 破坏性变更 / 迁移
- …

### 发布与回滚
- 顺序、依赖服务、feature flag、回滚注意

### 回归建议（摘要）
- …
```

## 语气对照（强制区分）

| 受众 | 要 | 不要 |
|---|---|---|
| 用户 | 能多做什么、哪里更顺 | 仓名、类名、Jira 号堆砌 |
| 运营 | 影响谁、怎么配合、话术 | 大段技术实现 |
| 研发 | 精确变更与风险 | 营销形容词 |

## 质量要求

- 三套都要有；若某受众「无内容」，显式写「本版本无单独对用户可见变更」等，禁止空复制同一段到三处充数。
- 破坏性变更必须在 B、C 出现；对用户有感则 A 也要有「注意事项」。
- 不泄露未公开的安全细节、密钥、内网地址。

## 对话交付摘要

1. 版本与范围  
2. 对用户 Top 变更（≤3 条）  
3. 是否有破坏性变更  
4. 若已落盘：路径
