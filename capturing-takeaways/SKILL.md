# Capturing Takeaways

对话结束即遗忘是模型物理；这个 skill 把「值得记住的结论」在遗忘前捞出来。
业界同款模式（ChatGPT/Mem0 的自动抽取、Anthropic 记忆工具的"边干边记"）的库内落地，
按 Mem0 最佳实践加一道**人审确认**：商家的生意结论，写入前必须点头。

## 启动 SOP

0. 自动迁移与同步（后台执行，成功不必汇报；**失败必须告知用户一句**——sync 失败
   意味着本地与远端/企业库脱同步，静默吞掉只会让两边越漂越远）：
   ```bash
   [ -d ~/kb/.git ] && kb migrate
   [ -n "$KB_BACKEND_URL" ] && kb sync
   ```
1. 检查 `~/kb/REGISTRY.md` 是否存在，并读取表中是否有库条目。
   REGISTRY 不存在或表里没有任何库（只有表头）时，按「还没有知识库」处理。
   - 询问用户是否先建库（引导 initializing-kb）；用户不想建就不沉淀，别硬来；建库前不继续选库或写入。
2. 读 `~/kb/REGISTRY.md` — 获取所有 active 的 KB 列表
   `local_dir` 列是该库在 `~/kb/` 下的目录名（自己的库 = slug；同事的库 = `<作者>--<slug>`），下文的 `<local_dir>` 都指它。
3. 确定目标 KB：
   - 用户点名了库 → 使用 REGISTRY 中对应的库
   - 只有一个 active KB → 用它
   - 多个 active → 按系统提示『企业知识库』一段的库名与标题判断与本次对话的相关性
   - 仍无法判断 → 列出让用户选

## 什么值得沉淀（判定标准）

**持久、且未来某个时刻会再用到**的结论，每次至多 3 条：

- 数字红线与阈值（「服饰退货率超 12% 亏本」）
- 拍板过的打法与偏好（「新品冷启动预算三七开」「主图一律不要贴纸风」）
- 踩坑教训（「火山引擎拒真人首帧，走素材库」）
- 反复用得上的事实（供应商账期、平台规则的适用结论）

**不沉淀**：一次性细节（某单号/某次报价）、闲聊、随手可再查的公开事实、
未经用户确认的推测。

**先查重再提议**：对每条候选，先 `grep -ril "<核心词>" ~/kb/<local_dir>/wiki/`——
库里已有同主题结论的，提议改为「更新既有页面」而不是新增（去重是记忆系统的
基本功；无脑追加只会制造互相矛盾的旧账）。

## 提议与确认（不点头不落盘）

把候选逐条列给用户，原话式、可勾选：

> 这次对话里有 N 条值得记住的结论，要记入知识库「<name>」吗？
> 1. <一句话结论>
> 2. …
> （存入待整理区，之后知识库体检时会归位到正式页面，可随时删除。）

- 用户确认哪几条就写哪几条；否 → 不写，不再追问第二遍。
- 用户主动说「记住这个」时同样过一遍判定（帮他把口语压成一句可复用的结论），
  但确认可以省略——他已经表过态了。

## 写入待整理区

每条一页，落 `~/kb/<local_dir>/wiki/inbox/YYYY-MM-DD-<takeaway-slug>.md`：

```markdown
# <一句话结论（可独立成立，别写"如上所述"）>

- 依据：<一句话来源/推理，如「2026-09 投放复盘，3 组 A/B」>
- 记录于：YYYY-MM-DD，来自「<本次对话主题一句话>」
```

inbox 是**待整理区**：不要求互链、不进 index（lint 对 inbox 豁免这两条）——
把「记下来」的成本压到最低，归位的活留给整理趟（linting-the-wiki 会检测
inbox 积压并逐条归入正式页型）。

## Git 同步

```bash
cd ~/kb/<local_dir>
git remote get-url origin &>/dev/null && kb git pull --rebase
git add -A && git commit -m "capture: <N 条 takeaway 主题>"
git remote get-url origin &>/dev/null && kb git push
```

   > **冲突与红线**：`kb git pull --rebase` 冲突时——先 `git rebase --abort` 回到冲突前，改用
   > `kb git pull --no-rebase` 合并；在冲突文件里**保留双方内容**并加一行「⚠️ 冲突待人工裁决」，
   > commit 后告知用户哪几处需要裁决，绝不静默丢弃任何一方。
   > push 失败（4xx/网络）→ 把错误原样报给用户，按提示重试或拆分；**绝不用
   > `git filter-branch` / `push --force` 等重写历史的手段解决推送问题**——#45 实锤：
   > 那会永久抹掉用户 raw/ 里的原件。
   > `kb git` 报 `Unknown command: git`（容器里还是旧版 CLI）时改跑 `kb sync`（带认证先拉后推），并照实告诉用户推送结果。

## 交付话术（两态，不可混）

- 「已把 N 条结论记入知识库「<name>」的**待整理区**（下次体检时归位）。」
- **绝不**宣称「已整理进 wiki/已更新综述页」——那是整理趟的活，没做就不说。

## 最小交付标准

- 用户确认过的每一条都落了 inbox 页并推送成功（或失败已如实告知）
- 没确认的一条都没写
- 回复里指明写进了哪个库
